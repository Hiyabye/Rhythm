# rhythm-collector (server collector)

Area instructions for `crates/collector/`. The root `AGENTS.md` (project-wide rules) applies too. This file is the single home of the collector's design and of the public-board crawl rules; `docs/ARCHITECTURE.md` points here.

## Approval rules

- Live runs need explicit approval and a temporary state file. Live R2 checks use their own test prefix, never `state/`; a live publish uses a test prefix (never `feed/`) and needs approval.
- `--embed` sends public notice text to Cloudflare: a live check needs approval. Tests use a fake `Embedder`.
- The maintainer generates the production signing key; tests use the RFC 8032 seeds.
- Production runs come only from `rhythm-fetch/collector` (below); never run against `state/` or `feed/` yourself.

## Run and CLI

`crates/collector/` (`rhythm-collector`, #174) crawls the public boards and publishes the feed. `main.rs` is one bounded run: `rhythm-collector <state.sqlite3> [--r2 <prefix> [--init] [--publish <prefix> [--reset-feed]]] [--embed [--reset-canary]] [--pages N] [--articles N] [--history-minutes N]` crawls `public_boards()` (every supported board but Cybercampus) into that state file with the v1 client's user agent (`Rhythm/<collector version> (local university notice archive)`, #166 O16, user decision), then the academic calendar (`calendar.rs`, below). A failed board is recorded and printed but does not fail the run; the run log also prints each server group's new-notice time and, through the `measured.rs` transport wrapper, request counts and times per host. Transport deadlines per attempt: 20 s to the headers and between body reads, 90 s for the body. It depends on `rhythm-sources` without `studium`: built alone (`-p rhythm-collector`) it has no native-tls, while a workspace build unifies the app's feature into it.

**Production** runs come only from `.github/workflows/collect.yml` in the separate `rhythm-fetch/collector` repository (#176, user decisions 2026-11-18): scheduled every 30 minutes, which GitHub fires only about hourly (#218, accepted 2026-11-24), built from one pinned Rhythm `main` commit (`RHYTHM_REF`; upgrading production is a PR there), always `--r2 state/ --publish feed/ --embed --articles 150`, secrets of its `collector` environment only in the run step; its README has the operations (first run, upgrade, canary reset, rollback). A collector change reaches production only when that pin moves.

## State and R2

- `state.rs` owns the SQLite state, with no originals, HTML, revision history or downloaded resources (#166 O19); `revision_hash` leaves out HTML, so a markup-only change is not a revision. Migrations: `001_initial.sql` (`boards` checkpoints and health, `notices` with the current revision only, `skipped`); `002_notice_dates.sql` (`notice_dates` and `notices.dates_version`, #166 O1: `upsert` re-extracts a new or revised notice in its transaction and `refresh_dates` backfills every notice of another extractor version at the end of each run); `003_deletions.sql` (`notices.missing_since`/`removed_at`, skipped `attempts`/`collector_version`); `004_embeddings.sql` (`embeddings`, `ai_usage`, `canary`, `canary_checks`); `005_classifications.sql` (`prototypes`, `classifications`); `006_feed.sql` (`feed`, `feed_notices`, `feed_records`, `feed_files`, read and committed by `state/feed.rs`); `007_transient_failures.sql` (per-notice runs of transient fetch failures); `008_calendar_events.sql` (`calendars` health, `calendar_events`, `feed_events`, read and written by `state/calendar.rs` and `state/feed.rs`).
- With `--r2` the file is a new working copy (an existing file is refused) of the newest version under that prefix in the private `rhythm-state` bucket (`remote.rs`, #166 D23). Versions are `<prefix><YYYYMMDDTHHMMSSZ>.sqlite3.zst` (zstd level 9 with frame checksum, SHA-256 in `x-amz-meta-sha256`, checked on download). After the crawl a `VACUUM INTO` snapshot that passed `quick_check` is uploaded as a new version, refused if another version appeared since the download or the clock is behind; then all but the newest 48 are deleted (user decision). A run that fails before upload writes nothing. An empty prefix is an error unless `--init`, which is refused when a version exists (user decision).
- `r2.rs` is a hand-written SigV4 client (GET/PUT/LIST/DELETE, region `auto`, credentials from `CF_ACCOUNT_ID`/`R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`), tested against the `aws-c-auth` signing suite and AWS's S3 examples in `r2/tests.rs`. `hmac` 0.13 needs `sha2` 0.11, so the collector uses that version (hex through `sha256_hex`).

## Crawl

`crawl.rs` is the only implementation of the public-board crawl rules since #178 removed the app's crawler (a port of the app's `archive/sync/{listing,articles}.rs`, user decision, #174, without resources, PDF bodies, Cybercampus or the job controller); the app keeps the parsers, robots policy and transport it fetches opened notices with. robots.txt loads once per origin and run (`Policies`; a failed load is not kept). Tests are in `crawl/tests.rs` (fake transport on the committed fixtures).

- **Per run** (`run_boards`, #80, user decisions 2026-11-22): boards are grouped by the server their host resolves to (`Transport::server`, the lowest public address; an unresolved host is its own group); at most `rhythm_sources::transport::MAX_HOSTS` (3) servers run at once, one board per server. First every board's incremental pass and then `upkeep`, so new notices never wait for a backfill; then the history backlog only for boards whose incremental pass succeeded and whose `history_complete` is false, in turns of at most `--articles` notices per board, least progress (`next_page`, then source ID) first, each server one round at a time before going back to the end of the queue (`take_turns`; a server never holds a worker for the whole window), until `--history-minutes` after the crawl started. A turn the deadline stops is `limited`, never a failure, and keeps its checkpoint; without the flag each board gets one turn. `run_board` is one board's incremental pass, upkeep and one history turn.
- **New boards:** of boards that never finished a first pass, only the first `crawl::NEW_BOARDS_PER_RUN` (20) in catalog order start per run; the rest wait without a health row, so adding many boards at once never pushes a run past its timeout (user decision, #80 step 3).
- **Historical:** start at the persisted `next_page`, follow public pagination and deduplicate pins and IDs (a page listing the same IDs as an earlier one stops the board, unless it lists only pins: a board whose newest notices are all pinned shows the same pins on several pages). Checkpoints advance only when no article on the page failed transiently. Existing text is not refetched. Mark `history_complete` only at the last public page, never at a test or safety limit.
- **Incremental:** start at page one and recheck recent pages and pins with ETag/Last-Modified validators. The edit window (known notices refetched for edits) is the first three pages capped at 30 regular rows (`EDIT_ROWS`, user decision, #80: the main site's 50-row pages read only page one); known notices past it are not refetched, and discovery must continue past it while regular records are new, until a page of known regular records marks the frontier. Repeated pins never establish the frontier. A sitemap-backed family (`mechanical`) instead lists the complete article set in one page and skips entries whose recorded `lastmod` still matches. k2web rows carry their listed title (`ListingEntry::title`; the CMS honours no validators): a known k2web notice in the window is refetched only while that title differs from the stored one (lists cut long titles at about 44–50 characters, so a listed title that begins the stored one counts as unchanged) or the notice was reported missing/removed; body-only edits arrive through the deletion audit (user decision, #80 step 3: re-reading the window of every k2web board on their one server would take about 49 minutes per run).
- **First incremental seed:** with no local documents, fetch at most three pages as historical records, without counting them as new or marking history complete. Incremental sync is not an audit of old edits; the deletion audit is separate.
- **Transient failures** (network, deadline, server error, cancellation, redirect, or a wrong content type; keep that one transient, it is more likely a block page than the notice) hold the page checkpoint, fail the board and are retried next run. A notice failing transiently on `TRANSIENT_RUNS` (3) runs in a row (at least ten minutes apart) is skipped instead of holding its page (user decision 2026-11-23: from the GitHub runner a few 1–17 MB pages timed out on every run and stopped their boards); success, a skip or "not found" resets the count.
- **Permanent failures** belong to the response: the body does not parse, its encoding is unsupported, or the notice is over `parser::article_limit` (16 MiB on main and k2web, else 4 MiB; user decision, #80 step 3). The notice is recorded in the collector's `skipped` table (reason and response SHA-256), keeps last-good content and does not hold the checkpoint (user decision, #78); it is never dropped silently and is removed once a fetch archives or confirms it.
- **Skipped retries** (in `upkeep`): at most 3 skipped notices per board and run are retried once a day, up to 7 attempts per collector `VERSION` (bump it to retry after a parser fix); a "not found" drops the row and a transient failure uses an attempt. Retries never change the board's status, counters, checkpoint or last success. Passes never refetch a skipped notice, except that the history pass refetches one an older `VERSION` skipped (at or past its checkpoint); for the incremental frontier a skipped notice counts as known, so it never pages a pass into unimported history.
- **Deletion audit** (in `upkeep`, user decisions 2026-11-17): `rhythm_sources::parser::missing` counts only HTTP 404/410 on main, engineering, mechanical and WordPress and the exact missing-post page on k2web, computing, scec and admission (never community, semiconductor or klec, whose answers are generic or match a members-only post). A first answer sets `missing_since`, one at least a day later sets `removed_at` (the feed tombstone); any successful fetch clears both, and a removed notice listed again is fetched and restored. Transient failures never count. At most 3 audits per board and run re-fetch notices published within 90 days about weekly (a reported one after a day); mechanical audits only notices absent from the complete sitemap, at any age. A notice gone between listing and fetch is reported missing and is neither a failure nor a skip.
- Counters describe the current attempt; checkpoint and history state are cumulative.

## Academic calendar

`calendar.rs` (#319, user decisions 2026-11-25) fetches the school's published 학사 일정 once per run, after the boards: `rhythm_sources::calendar::ACADEMIC_CALENDAR_URL` (Outlook) under `Access::Calendar`, which reaches only that URL and its host's robots.txt. That host has no robots.txt (a redirect to its mail login, then 417), which the transport reads as no rules for this access only; a real policy there is still obeyed. The ICS must be `text/calendar`, at most 1 MiB, named `서강대학교 학사일정` and hold at least `MIN_EVENTS` (10) events, or the fetch fails: a failure increments `calendars.consecutive_failures`, keeps every event and never fails the run. A successful fetch is the whole current list (`State::calendar_apply`): new and changed events are stored, an absent one gets `missing_since` and is removed (`removed_at`, the feed's `event.remove`) only by a fetch at least a day later that still lacks it, and an event that ended before the fetched calendar's earliest event aged out of its window and stays. Recurring, cancelled or malformed events are skipped and counted. Publish carries changed events (`event.upsert`) in the run segment and every current one in the snapshot (docs/FEED.md, format 1.2). Never fetch another Outlook route, and never widen this host's robots reading to another access or host.

## Embedding (`--embed`)

Credentials `CF_ACCOUNT_ID`/`CF_AI_TOKEN`. `embedding::run` follows the crawl (#166 D15, D25–D27; user decisions 2026-11-17/18): `workers_ai.rs` sends the exact `rhythm_embed::input` strings through the `text` field of `@cf/qwen/qwen3-embedding-0.6b` in batches of 10, checks and normalizes every 1,024-dim vector and stores it as little-endian f16 with its revision and scope (model + `config_hash`).

- Order per run: the drift canary once per UTC day (the 28 committed inputs in `src/canary.json`, measured in #170; the first check records the reference; min cosine ≥ 0.9995 normal, < 0.9970 stops new vectors and latches until `--reset-canary`, between warns); then new notices (not historical) and revisions of vectors in the current scope; then the backfill, never-embedded notices newest first and then other scopes, at most 1,000 per run and only while the UTC day stays below 9,000 Neurons.
- Then every current vector of the scope without a classification of that vector is classified (#166 O9) with `rhythm_embed::classify_with` against the category prototypes, embedded through Workers AI once per scope and cached as f16 in `prototypes` (`reset_canary` clears them); scores are clamped to [-1, 1] against f16 rounding.
- Any Workers AI error (429, quota, auth, an unusable response, 5xx after retries) stops embedding for the run and is recorded in `ai_usage.last_error`; cached prototypes still classify the vectors already stored, but none are embedded after an error; crawling and upload continue. Removed notices are never embedded; Cybercampus never reaches the collector.

## Publish (`--publish <prefix>`)

Needs `--r2` (user decisions 2026-11-18). `publish.rs` writes the signed feed of `docs/FEED.md` to that prefix of the public `rhythm-feed` bucket with the same R2 credentials, signing with the PEM PKCS#8 key in `RHYTHM_FEED_SIGNING_KEY`.

- `prepare` (before the state upload) verifies the live manifest with that key and refuses on a seq beyond the state's `feed.next_seq`, a manifest not older than the run's clock or another key; deletes files retired a day ago that the live manifest no longer lists and every object under the prefix no `feed_files` row names; on a new UTC day compacts earlier days' run segments (records kept in `feed_records`) into one daily segment per day and writes a snapshot (an unchanged one is redated, not rewritten); publishes each notice, vector and category whose digest changed (a removal clears the digests, so a restored notice is published again) as one run segment with int8 vectors from the stored f16; uploads the files and commits.
- `finish` (after the state upload) writes the manifest from the unretired `feed_files`, checks it with `Manifest::parse` and uploads it and then its `.sig`. Daily segments older than 30 days are retired.
- `--reset-feed` (the restart after a state rollback, user decisions 2026-11-18, #256) needs a live manifest that verifies: `State::feed_restart` forgets what the state published, retires every known file and the live manifest's files for a day and sets `next_seq` after the live manifest's last seq; that run publishes no segment, only a snapshot beyond every old seq (refused when the state has no notice), so any old cursor takes FEED.md's snapshot path.
- Tests (`publish/tests.rs`) run an independent client written from FEED.md against an in-memory bucket.
