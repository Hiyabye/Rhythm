# Rhythm development

## Scope and architecture

Rhythm is a Korean-first, local-first Tauri 2 desktop command center. Current product support and distribution target **macOS Apple Silicon (arm64) and Windows 11 x64** (user decision, added from contributor PR #1); Linux/Intel Mac code and CI/runtime observations are historical, not current support. Both platforms share the bundle identifier `io.github.hiyabye.rhythm`; platform code lives behind `cfg(target_os = "macos")`/`cfg(windows)` and must not remove the other platform's path. Windows evidence in `docs/WINDOWS_VALIDATION.md` was collected by the contributor; apart from the PR #63 AI/installer and #36 in-app update runs (validation identifiers), it predates the merged build. Read `docs/ARCHITECTURE.md` before changing component boundaries and `docs/ROADMAP.md` before adding product scope. Current implementation is v2.4.1 (stable): the server collector and signed notice feed (#166; public boards arrive only through the feed, an opened notice fetches its body and files from the school, Cybercampus is the only source the app collects), the feed's categories, vectors and dates, local embedding for search queries and Cybercampus notices (AI summaries and the remote engine were retired, #226), an archive upgraded in place from v1 (migrations 037–042; user state kept) and deterministic personalization, the 기회 page (opportunity categories by deadline, #87), opt-in lifecycle/scheduling/notifications, an opt-in local calendar with todos and the school's academic calendar from the feed (#319), an opt-in 식단 page for the dormitory menu from the feed (#318), opt-in manual and app-open automatic Studium seat checks with favorites, seat alerts, a mini window and a relative seat map, versioned single-file backup/restore. Backups exclude model weights and are not encrypted; restore retains managed models only when local weights match expected size/SHA-256. Confirmed restore quits Rhythm; the next manual launch finalizes it and reports the outcome.

**Distribution policy (user decision):** release artifacts are an ad-hoc-signed (hardened runtime) `Rhythm.app` in `Rhythm_<version>_aarch64.dmg` plus a SHA-256 checksum file generated from the final DMG. Developer ID signing and Apple notarization are intentionally excluded; do not treat their absence as a task, request Apple membership, create Developer ID/notary credentials, bypass Gatekeeper, strip quarantine, or describe ad-hoc as trusted/notarized. Gatekeeper rejects these builds; that is expected and README says how to open the app. `scripts/macos-release.mjs` (Developer ID path) is retained for a possible future decision and refuses to run without credentials. **In-app updates (user decision, #30):** the Tauri updater signature (minisign/Ed25519) is separate from OS code signing and needs no Apple or Microsoft account, so releases carry signed updater packages and a `latest.json` while the builds themselves stay ad-hoc (macOS) or unsigned (Windows). The updater signature proves origin to the app; never describe it as OS trust, signing or notarization. The endpoint is `https://github.com/Hiyabye/Rhythm/releases/latest/download/latest.json`, which sees only published releases: an update goes live when the maintainer publishes the draft. The app trusts only the key compiled in through `option_env!("RHYTHM_UPDATER_PUBKEY")`; builds without it (local builds, CI) show manual update steps. v1.1.0 and earlier embed no key, so users install the first keyed release manually. Before installing, `updater_restart` stops and reaps the classifier's embedding `llama-server` (maintenance alone does not, and the Windows plugin exits through `process::exit`, skipping `RunEvent::Exit`). macOS in-place update and the Windows passive NSIS update are verified only under validation identifiers with a loopback manifest (`docs/ROADMAP.md#verification-status`, `docs/WINDOWS_VALIDATION.md#in-app-update`, one PC each). Do not claim either beyond those records. Never test with or overwrite `/Applications/Rhythm.app` or the real profile.

**Windows distribution (current state, unsigned by user decision, #85):** an unsigned per-user NSIS installer; SmartScreen warnings are expected and README says how to proceed. No Authenticode signing exists by that decision; do not treat it as a pending task or describe the installer as signed or trusted. The updater package is the setup executable itself with a `.sig`, run in passive mode; uninstall preserves user data and models. What ships (custom NSIS template and hooks, bundled llama.cpp CPU build and VC runtime, passive-update behavior, the `llama\vulkan` cleanup, install folder, WebView2 bootstrapper) and the `src-tauri/tauri.windows.conf.json` overrides are in `docs/WINDOWS.md` "What ships".

**Release outputs:** a default `npm run desktop:build` (release, no `--bundles`/`--no-bundle`) deletes `target/release/bundle/` first, then writes a fresh `target/release/distribution/`: on macOS `Rhythm_<version>_<arch>.dmg` and `<dmg>.sha256`; on Windows `Rhythm_<version>_x64-setup.exe` and `<exe>.sha256` (both in `shasum -a 256` format, computed from that file). With both `TAURI_SIGNING_PRIVATE_KEY` and `RHYTHM_UPDATER_PUBKEY` set (`scripts/updater-signing.mjs`; one without the other fails before staging) it also passes `createUpdaterArtifacts` and the public key to Tauri (on macOS also the `app` target: a DMG-only build creates no updater archive, only a bundler warning) and adds the updater files: macOS `Rhythm.app.tar.gz` and its `.sig` (Tauri's name, which the signature binds), Windows `<exe>.sig`. Without the key the output stays exactly two files. Per-file `.sha256` covers the DMG/installer only; updater packages are covered by their signatures (user decision: no `SHA256SUMS`). Publish only distribution files plus the generated `latest.json`; never pick artifacts from `target/release/bundle/`. `.github/workflows/release.yml` automates this on a pushed `v*.*.*` tag: it requires the tag commit to be reachable from `main` and to match every version field, refuses an existing release, runs `npm run desktop:build` on `macos-15` and `windows-latest` with the signing key, verifies each updater signature (`verify-update.mjs artifact`), the macOS archive contents and the embedded key (`bundle`, `binary`), checks that exactly the seven distribution files exist and match their checksums, generates `latest.json` (`scripts/update-manifest.mjs`: `darwin-aarch64[-app]` and `windows-x86_64[-nsis]`), verifies it against the staged files (`verify-update.mjs manifest`), and creates a **draft** release only; the maintainer publishes it. Missing signing secrets fail the release (user decision) rather than dropping updater files. The private key and password are secrets of the reviewer-gated `release` environment, used only in the two build steps; the public key is the repository variable `RHYTHM_UPDATER_PUBKEY`. `contents: write` exists only in its release job. Its `desktop`/`windows` job IDs and Cargo env match `ci.yml` so the tag build can restore main's rust-cache (restore only). The Windows MSVC environment setup lives in `.github/actions/windows-build-tools`, shared by both workflows. To release: set the same version in `package.json`, `package-lock.json`, `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml` (and `Cargo.lock`), merge to `main`, then push tag `vX.Y.Z` on a `main` commit. Pushing tags and publishing releases change remote state: ask first. Release builds pass `--remap-path-prefix` for `$HOME`, `CARGO_HOME` and the checkout via `CARGO_ENCODED_RUSTFLAGS` (appending any existing `RUSTFLAGS`/`CARGO_ENCODED_RUSTFLAGS`) so binaries carry no builder paths; check with `strings <binary> | grep "$HOME"`. Cargo `trim-paths` is unstable on stable Rust. Debug builds keep real paths.

**Dependency advisories (reviewed for v1.0.0):** the backup code (`rhythm-core`) uses `zip` 9.2.2, the only `zip` in `Cargo.lock`. `deepmerge` (dev-only via `@sveltejs/vite-plugin-svelte`, no fixed release) and Linux-only `glib` 0.18.5 (needs Tauri 3) are accepted by user decision; their Dependabot alerts (numbers 7 and 1) are dismissed as tolerable risk. A new advisory for either package opens a new alert that needs its own review.

**Free tiers only (user decision, 2026-11-28):** the project must never cost money. Use only free services, plans and options (Cloudflare R2, Workers and Workers AI, GitHub Actions and anything new); never pick a paid option, enable billing or design a change that relies on usage beyond a free tier. When a change could push usage toward a free-tier limit (storage, requests, Neurons, minutes), estimate it, prefer a free alternative and ask before going ahead. The collector's free-tier budgets are in `crates/collector/AGENTS.md`.

## Setup and commands

Use stable Rust **1.90+**, Node.js **22.12+**, npm and the [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/) for the host. Keep `cargo` and `rustc` on PATH. Use committed root `Cargo.lock` and `package-lock.json`. Desktop app scripts accept macOS and Windows 11 x64 (MSVC host) and reject other hosts; Rust/frontend-only development may still use other hosts but does not imply product support. Windows builds additionally need Visual Studio C++ tools; see `docs/WINDOWS.md`. The desktop scripts and CI run `scripts/stage-llama.mjs` before Clippy/tests; direct Tauri invocation on a fresh checkout bypasses this step. Staged binaries are ignored; icons are committed. ### Personalization invariants

The specification (tables, evidence and learning rules, weights, the similarity term, candidate slices, ordering) is `docs/ARCHITECTURE.md` "Personalization and ranking"; change it with the code. Rules that must hold:

- Never rewrite migration 004. Preserve legacy `settings.interests` until an explicit personalization reset. Interests, provenance, feedback, evidence and results stay in SQLite and never enter network calls or diagnostics.
- Ranking is deterministic and bounded and must work without an installed/loaded model or network access. AI classifications and extracted dates never create ranking urgency or personalized reasons. The only AI input is the similarity term (#177 PR 7, user decisions 2026-11-20): stored vectors only, never a model call, only while the `ai` extension is on, in both the list and notification scores.
- `interested` and save are the only evidence; read/open/search never are. Negative feedback stays document-scoped: it must not unsubscribe, hide categories or create inferred dislike. Do not rescan unchanged evidence on every view.
- Explicit interests are never replaced by learned ones; keep the backend caps on interests and aliases; match Korean/English terms through bounded aliases, not a large ontology. Recommendation explanations must derive from score contributions. Learned topics come only from titles and original categories, never body text or AI output; keep the lexical sensitive-term exclusions.
- Reset removes personalization state but preserves archive, saved/read state and AI results. Re-enabling a source's extension (`source_extensions`) restores its history without duplicating evidence; its archive, feedback and saved state stay accessible while it is off.
- The feed mirrors every public board, so subscription decides what the feed pages show: 오늘 (recommendations), 받은 소식, 기회, the unread/new counts and the calendar's every-notice deadlines keep to subscribed sources (`ArchiveQuery.subscribed_only`, `archive_summary`, the recommendation candidate CTE, `calendar_notice_dates`); 검색, 보관함 and 휴지통 cover the whole archive (user decision, 2026-11-24).
- Initial historical backfill must not gain freshness from collection time. Candidate retrieval never transfers the full archive to Svelte.

## Data and lifecycle invariants

- Persist through Rust/SQLite, not frontend localStorage. Browser previews must state desktop-only limitations instead of simulating success.
- Database is `<data>/rhythm.sqlite3`, with `<data>` the Application Support folder on macOS and the non-roaming `%LOCALAPPDATA%` folder on Windows, each named by the bundle identifier; `rhythm_core::paths` resolves it, the resource directory and `run/embedding/` exactly as Tauri's `app_data_dir()`/`app_local_data_dir()`/`resource_dir()` did for v2.x (an update must find the same profile), so change them only with a migration plan; resources use generated paths below `resources/`. The private `run/` directory (`0700` on Unix) holds only the classifier's embedding server socket or per-launch key and, on Unix, its pid file (`run/embedding/`); backup and restore never read it. Managed model files are generated under the default `models/` directory or the model's recorded custom destination; resolve them through `model_storage.rs`. External model references stay at canonical original paths and must never be deleted by unregister. Never hardcode home paths or use remote filenames as filesystem paths.
- Acquire the process-lifetime OS data-directory lock **before** opening/recovering the store. Controller admission additionally allows one archive (Cybercampus) or resource-retry job. Do not open a second live production store to inspect progress: `Store::open` recovers running source jobs and interrupted model downloads.
- **Calendar dates (user decisions, #226):** `crates/sources/src/dates.rs` finds dates in a notice's current title + body by literal patterns and Korean keywords only (no model, no network): a missing year comes from `published_at` (90 days before to 275 days after), a written weekday never drops a date, a deadline before publication becomes an ordinary date, and replaced/cancelled clauses are skipped. A range whose end is a deadline (an application period) is a `start` row plus a `deadline` row; any other range up to `MAX_SPAN_DAYS` (366) is one `date` row with `end_day`, shown on every day it covers, and the calendar query includes spans that overlap its range. A label naming a period (`기간`) or an action outweighs the wider clause when deciding deadline vs. date. The label is at most three words before the date without asides, numbering or weekday residue; the calendar and week pane lead with the notice title and show the label beside it. A sign-off date at the end of the text, on or before publication, and a `기준` (as-of) date are skipped, as is a date whose own label is page metadata (`작성일`, `게시일`, `수정일`, also with `자`/`시`; `등록일` as the whole label, or with other words only on the publication day, since `신입생 등록일` is an event). A length of time is never a date or time (`3일간`, `3일 이내`, `3일 동안`, `3일 안에`, `3일 내` after `부터`; `3시간`, `30분간`), a day-only range end (`~ 7일`) must come after the start's day, and an end written before its start keeps only the start. `upsert_article` and `fill_body` re-extract in the same transaction; `archive::run_notice_dates` backfills missing rows and rows whose `content_hash` or `EXTRACTOR_VERSION` differs once per launch, in batches with the store unlocked between them. Bump `dates::EXTRACTOR_VERSION` (in `crates/sources`) with any rule change; the app and the collector both extract through `dates::extract_notice` (title + newline + body) and re-extract rows of another version. Each feed notice record carries the version, so once the collector pin reaches a bump it republishes every notice once. The calendar and week pane show every date of saved notices, plus the deadlines of every notice of a subscribed source only while `settings.calendar_all_deadlines` is on (default off); both apply `NOT_TRASHED`. They also show the school's academic calendar (학사 일정, #319) from the feed while `settings.calendar_academic` is on (default on; the week pane only while the `calendar` extension is on): `calendar_events`, dates and titles only, which like notice dates never feed ranking, notifications or network calls. Dates never feed ranking, notifications or network calls (the 기회 page's deadline order is display only), and a todo is created only through the editable form. Measured on synthetic fixtures (`crates/sources/src/dates/tests.rs`) and on a copied archive (`archived_dates_evaluation`, ignored, read-only; never point it at the live profile; results in `docs/ROADMAP.md`); English dates and image-only notices are not handled.
- Document identity is `(source_id, external_id)`. Preserve original fetched representations, sanitized/normalized content, meaningful revisions and independent read/saved state. Fetch/parse/resource failures must not replace good content or erase user state.
- `sogang_notices` is operational but opt-in and source subscriptions are separate. Restoring/enabling preferences starts no network work. `stop` signals cancellation; the owning async disable/exit path waits without holding the SQLite lock. Hide source controls while disabled, reject new downloads, retain archives/subscriptions and allow local read/search/save.
- Never retain SQLite mutex guards across async network/worker/filesystem operations. Check cancellation/extension enablement at commit boundaries.
- Backup and restore follow `docs/ARCHITECTURE.md` "Backup, restore and updater". Never make restore relaunch the app (a relaunched instance races the exiting one for the single-instance socket and data lock and exits silently); `recover_pending_restore` finalizes on the next launch, and a recovery error must keep the journal and previous data.
- Windows restore has extra volume, reparse-point and Cloud Files checks (same section). The subprocess fault test is `cargo test --locked -p rhythm-core backup::tests::windows_restore_recovers_after_process_abort_at_each_transition -- --exact --nocapture`. CI runs `scripts/prepare-windows-restore-ci.ps1` first, which may enable/attach `CldFlt` only on GitHub-hosted runners. Locally use only its read-only `-CheckOnly` mode; never skip or bypass the check in tests.
- For native macOS backup/restore checks, create an isolated profile with `RHYTHM_NATIVE_PROFILE_DIR=<fresh HOME>/Library/Application\ Support/io.github.hiyabye.rhythm cargo test --locked -p rhythm-core write_populated_native_profile -- --ignored` and launch the bundle executable with that `HOME`. LaunchServices/Finder launches ignore a temporary `HOME` and open the real profile.

## Security and implementation constraints

- Keep user-facing UI, feedback and errors in natural Korean. Internal IDs/docs may use English. Keep `src/lib/types.ts` and Rust payloads synchronized; validate backend inputs.
- A window may invoke only the app commands its capability grants. The `main` capability lists exactly the commands the main window invokes, and `studium-mini` cannot reach backup, extension or credential commands. Do not add a grant before the code that invokes it.
- Automatic fetches use exact approved HTTPS hosts/routes (`network::Access::Source`), public DNS with pinned answers, same-origin redirects authorized by robots before every hop, pacing, cancellation, size/deadline/retry limits. Transport returns redirect targets; only the sync policy layer may follow them. Completed resource response bytes consume the job budget even if format validation or filesystem persistence fails. Preserving HTTP(S) resource metadata is not permission to fetch it. Exception (user decision, #78): an image embedded in an archived notice (`Access::EmbeddedImage`) may come from any other public HTTPS host name on port 443, never an IP literal, plain HTTP or another route on a `*.sogang.ac.kr` host; that host's robots.txt applies (cached per job; 4xx means no rules, other failures block), redirects stay same-origin and bytes must be a verified raster. Third-party attachments stay blocked. Running out of the job's resource budget leaves files `pending`, never `too_large`. No authentication/access-control bypass or downloaded-code execution.
- Render only sanitized reader content; original responses are archive data. No script/style/iframe/event-handler content or remote-image fallback. Local images require bounded raster bytes and SHA-256 verification. External HTTP(S) links require explicit user action through the OS browser. File reveal must not execute attachments.
- Retain MIME/size/hash/state metadata, generated paths and last-good verified resource references. Retry must repair corrupt bytes rather than assume a hash filename proves integrity. Report failed/oversized/unsupported resources without discarding useful text.
- No telemetry or cloud storage of user data. Network use is limited to approved archive sources, the opt-in Cybercampus session, explicit or explicitly enabled automatic Studium seat checks, images embedded in archived notices (above), explicit model downloads, the signed notice feed (`feed/transport.rs`, requests carry no user data), and the updater's GitHub release endpoint. The app sends no notice text, query, personalization or personal data to an AI service; the only AI provider is the collector's Workers AI, which receives public notice text only. Local inference runs only in a child process that Rhythm starts, owns and stops. That process may serve HTTP only on a Unix socket in a `0700` app-data directory, or, where Unix sockets are unavailable, on 127.0.0.1 with a random per-launch API key; it must never listen on another interface or be usable by other processes without that key. The server process owns the loaded model; its stdout is discarded and its stderr is drained as bounded diagnostics. App startup needs no weights or GPU tooling. Compiled backend, loaded backend, artifact integrity, actual embedding and classification accuracy are distinct verification claims.
- Rhythm is GPL-3.0-or-later (user decision; v1.7.1 and earlier were released under MIT). New dependencies, vendored code and bundled files must be GPLv3-compatible; keep upstream notices for vendored/ported code and bundle third-party license texts under `assets/licenses/` (the bundled list and attribution facts are in `docs/ARCHITECTURE.md` "Licensing").
- Use Rustfmt; frontend code must pass `npm run check` without warnings. No separate frontend formatter/linter is configured.
