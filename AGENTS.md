# Rhythm development

## Scope and architecture

Rhythm is a Korean-first, local-first Tauri 2 desktop command center. Current product support and distribution target **macOS Apple Silicon (arm64) and Windows 11 x64** (user decision, added from contributor PR #1); Linux/Intel Mac code and CI/runtime observations are historical, not current support. Both platforms share the bundle identifier `io.github.hiyabye.rhythm`; platform code lives behind `cfg(target_os = "macos")`/`cfg(windows)` and must not remove the other platform's path. Windows evidence in `docs/WINDOWS_VALIDATION.md` was collected by the contributor; apart from the PR #63 AI/installer and #36 in-app update runs (validation identifiers), it predates the merged build. Read `docs/ARCHITECTURE.md` before changing component boundaries and `docs/ROADMAP.md` before adding product scope. Current implementation is v1.8.0 (stable): archive, optional local or user-configured remote AI and deterministic personalization, opt-in lifecycle/scheduling/notifications, an opt-in local calendar with todos, versioned single-file backup/restore. Backups exclude model weights and are not encrypted; restore retains managed models only when local weights match expected size/SHA-256. Confirmed restore quits Rhythm; the next manual launch finalizes it and reports the outcome.

**Distribution policy (user decision):** release artifacts are an ad-hoc-signed (hardened runtime) `Rhythm.app` in `Rhythm_<version>_aarch64.dmg` plus a SHA-256 checksum file generated from the final DMG. Developer ID signing and Apple notarization are intentionally excluded; do not treat their absence as a task, request Apple membership, create Developer ID/notary credentials, bypass Gatekeeper, strip quarantine, or describe ad-hoc as trusted/notarized. Gatekeeper rejects these builds; that is expected and documented in README. `scripts/macos-release.mjs` (Developer ID path) is retained for a possible future decision and refuses to run without credentials. **In-app updates (user decision, #30):** the Tauri updater signature (minisign/Ed25519) is separate from OS code signing and needs no Apple or Microsoft account, so releases carry signed updater packages and a `latest.json` while the builds themselves stay ad-hoc (macOS) or unsigned (Windows). The updater signature proves origin to the app; never describe it as OS trust, signing or notarization. The endpoint is `https://github.com/Hiyabye/Rhythm/releases/latest/download/latest.json`, which sees only published releases: an update goes live when the maintainer publishes the draft. The app trusts only the key compiled in through `option_env!("RHYTHM_UPDATER_PUBKEY")`; builds without it (local builds, CI) show manual update steps. v1.1.0 and earlier embed no key, so users install the first keyed release manually. Before installing, `updater_restart` stops and reaps a loaded `llama-server` (maintenance alone does not, and the Windows plugin exits through `process::exit`, skipping `RunEvent::Exit`). macOS in-place update and the Windows passive NSIS update are verified only under validation identifiers with a loopback manifest (`docs/ROADMAP.md#verification-status`, `docs/WINDOWS_VALIDATION.md#in-app-update`, one PC each). Do not claim either beyond those records. Never test with or overwrite `/Applications/Rhythm.app` or the real profile.

**Windows distribution (current state, unsigned by user decision, #85):** an unsigned per-user NSIS installer (`installMode: currentUser`, custom `scripts/installer-template.nsi` and `installer-hooks.nsh`) that bundles the pinned llama.cpp Vulkan and CPU builds (each with its own copy of the VC runtime DLLs it imports) and the app-local Microsoft VC runtime DLLs; SmartScreen warnings are expected and documented in README. No Authenticode signing exists by that decision; do not treat it as a pending task or describe the installer as signed or trusted. The updater package is the setup executable itself with a `.sig`; `tauri.windows.conf.json` sets `plugins.updater.windows.installMode: passive` (the plugin passes `/P /UPDATE /R`; the custom template then skips the uninstall and desktop-shortcut steps and relaunches the app); observed on one PC under a validation identifier (#36). Uninstall preserves user data and models. Windows config overrides live in `src-tauri/tauri.windows.conf.json` (Tauri JSON-merge-patches it over `tauri.conf.json`; arrays replace).

**Release outputs:** a default `npm run desktop:build` (release, no `--bundles`/`--no-bundle`) deletes `target/release/bundle/` first, then writes a fresh `target/release/distribution/`: on macOS `Rhythm_<version>_<arch>.dmg` and `<dmg>.sha256`; on Windows `Rhythm_<version>_x64-setup.exe` and `<exe>.sha256` (both in `shasum -a 256` format, computed from that file). With both `TAURI_SIGNING_PRIVATE_KEY` and `RHYTHM_UPDATER_PUBKEY` set (`scripts/updater-signing.mjs`; one without the other fails before staging) it also passes `createUpdaterArtifacts` and the public key to Tauri (on macOS also the `app` target: a DMG-only build creates no updater archive, only a bundler warning) and adds the updater files: macOS `Rhythm.app.tar.gz` and its `.sig` (Tauri's name, which the signature binds), Windows `<exe>.sig`. Without the key the output stays exactly two files. Per-file `.sha256` covers the DMG/installer only; updater packages are covered by their signatures (user decision: no `SHA256SUMS`). Publish only distribution files plus the generated `latest.json`; never pick artifacts from `target/release/bundle/`. `.github/workflows/release.yml` automates this on a pushed `v*.*.*` tag: it requires the tag commit to be reachable from `main` and to match every version field, refuses an existing release, runs `npm run desktop:build` on `macos-15` and `windows-latest` with the signing key, verifies each updater signature (`verify-update.mjs artifact`), the macOS archive contents and the embedded key (`bundle`, `binary`), checks that exactly the seven distribution files exist and match their checksums, generates `latest.json` (`scripts/update-manifest.mjs`: `darwin-aarch64[-app]` and `windows-x86_64[-nsis]`), verifies it against the staged files (`verify-update.mjs manifest`), and creates a **draft** release only; the maintainer publishes it. Missing signing secrets fail the release (user decision) rather than dropping updater files. The private key and password are secrets of the reviewer-gated `release` environment, used only in the two build steps; the public key is the repository variable `RHYTHM_UPDATER_PUBKEY`. `contents: write` exists only in its release job. Its `desktop`/`windows` job IDs and Cargo env match `ci.yml` so the tag build can restore main's rust-cache (restore only). The Windows MSVC environment setup lives in `.github/actions/windows-build-tools`, shared by both workflows. To release: set the same version in `package.json`, `package-lock.json`, `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml` (and `Cargo.lock`), merge to `main`, then push tag `vX.Y.Z` on a `main` commit. Pushing tags and publishing releases change remote state: ask first. Release builds pass `--remap-path-prefix` for `$HOME`, `CARGO_HOME` and the checkout via `CARGO_ENCODED_RUSTFLAGS` (appending any existing `RUSTFLAGS`/`CARGO_ENCODED_RUSTFLAGS`) so binaries carry no builder paths; check with `strings <binary> | grep "$HOME"`. Cargo `trim-paths` is unstable on the pinned toolchain. Debug builds keep real paths.

**Dependency advisories (reviewed for v1.0.0):** the app's backup code uses `zip` 9.2.2, the only `zip` in `Cargo.lock`. `deepmerge` (dev-only via `@sveltejs/vite-plugin-svelte`, no fixed release) and Linux-only `glib` 0.18.5 (needs Tauri 3) are accepted by user decision; their Dependabot alerts (numbers 7 and 1) are dismissed as tolerable risk. A new advisory for either package opens a new alert that needs its own review.

The Cargo workspace has one member, `src-tauri`. Do not add a crate or generic extension/plugin infrastructure without a concrete need. Source-specific parsing stays outside generic storage and reader code.

## Setup and commands

Use stable Rust **1.90+**, Node.js **22.12+**, npm and the [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/) for the host. Keep `cargo` and `rustc` on PATH. Use committed root `Cargo.lock` and `package-lock.json`. Desktop app scripts accept macOS and Windows 11 x64 (MSVC host) and reject other hosts; Rust/frontend-only development may still use other hosts but does not imply product support. Windows builds additionally need Visual Studio C++ tools; see `docs/WINDOWS.md`. The app needs no CMake, Vulkan SDK or Metal Toolchain: `scripts/stage-llama.mjs` downloads the pinned upstream llama.cpp archives from GitHub releases (network access), caches them in `target/llama-cache/`, rejects any archive whose size or SHA-256 differs from `scripts/llama-cpp.json`, and replaces `src-tauri/binaries/llama/` with exactly that pin.

```sh
npm ci
npm run desktop                      # stage llama.cpp, then run the app in development
npm run desktop:build                # release app/DMG with the bundled llama.cpp build; distribution files in target/release/distribution/
npm run desktop:build -- --debug      # debug application/bundle
node scripts/stage-llama.mjs         # stage the pinned llama.cpp build only
npm run desktop:build -- --no-bundle  # native build without installer generation
npm run check                        # Svelte/TypeScript diagnostics
npm run build                        # frontend production build only
npm run test:ui                      # compiled frontend + mocked IPC, Chromium/WebKit
npm run screenshots                  # opt-in: regenerate docs/screenshots/*.png from synthetic data (tests/ui/screenshots.spec.ts, playwright.screenshots.config.ts, port 4179); not part of test:ui
npm run test:desktop                 # macOS script stubs (POSIX) and Windows build orchestration (any host)
npm run test:release                 # updater signature/manifest verifier and generator (disposable Tauri-signer keys), release preflight, release/CI workflow rules
cargo fmt --all
cargo clippy --locked --workspace --all-targets -- -D warnings
cargo test --locked --workspace
```

The Rust commands need `dist/` (`npm run build`) and the staged llama.cpp resources (`node scripts/stage-llama.mjs`); the Tauri build only checks that the resources exist.

CI (`ci.yml`) runs each concern once and only when its files changed: a `changes` job runs `scripts/ci-changes.mjs` (merge commit vs first parent on PRs, `before..after` on `main`, everything when unknown, on manual runs or when `.github/` changes) and gates `frontend` (check, build, Node script tests, Playwright), `rust-fmt`, and the macOS/Windows clippy+test jobs (`desktop`/`windows`; keep these IDs and their Cargo env in sync with `release.yml` for cache restore). Release builds in those jobs run only on `main` or manual runs when packaging inputs changed. Markdown files never trigger the Rust or packaging jobs. When Rust code or tests start reading a file outside `src-tauri/`, or a new top-level config appears, update the rules and `tests/ci-changes.test.mjs`; a missing rule silently skips checks. Tauri checks need the staged `src-tauri/binaries/llama/` resources (on Windows staged after `binaries/vc-runtime/`, whose DLLs each build needs). The desktop scripts and CI run `scripts/stage-llama.mjs` before Clippy/tests; direct Tauri invocation on a fresh checkout bypasses this step. Staged binaries are ignored; icons are committed. A change to the pin or the staging script runs the Rust jobs. The helper targets the host and assumes Cargo's default workspace `target/` directory. Notifications use the macOS-native UserNotifications APIs and the async `mac-usernotifications` 0.3.1 sender on macOS, and WinRT toasts with the installed AUMID and a verified per-user `rhythm-win:` protocol registration on Windows. Linux has no sender; do not imply a plugin-backed sender or support path. Request authorization only on explicit user action. Do not treat API handoff as evidence of OS authorization/display/receipt; keep to the native evidence and limits recorded in `docs/ROADMAP.md#verification-status`.

UI tests use the dev dependency `@playwright/test` and require its Chromium/WebKit binaries (`npx playwright install chromium webkit`; CI also installs OS prerequisites). `playwright.config.ts` builds/serves the actual frontend at 127.0.0.1:4178; tests mock only the Tauri boundary and must not be reported as native backend verification. Test output/traces stay under ignored `node_modules/.cache/`. Do not rely on a running preview server; the suite owns its server. Maintain meaningful keyboard/focus, failure-state, paging and reader regressions alongside Rust/native checks. The frontend picks platform-specific controls and wording from the WebView user agent (`src/lib/platform.ts`, never for security decisions); `tests/ui/windows.spec.ts` runs with a Windows user agent and the fixture's `windows: true` defaults, and every other spec exercises the macOS path.

`intelligence::tests::real_server_lifecycle_without_model_weights` runs the staged real `llama-server` (or `RHYTHM_LLAMA_TEST_DIR`) and returns early when neither exists; a passing suite alone does not establish process integration. Other process tests use the fake `llama-server` in `src-tauri/src/intelligence/test_worker.rs` (same flags, log lines, socket/loopback listener, API-key check and response shapes): compiled once per test process from fixed source, with first launch completed before any request deadline, then hard-linked per test with its `mode` and control files beside it. macOS holds each newly created executable before its first instruction for an execution-policy check; per-test unique binaries launched in parallel exceeded the 8-second status deadline. Pass per-test behavior through files beside a hard link, never by baking paths into source. Do not raise request deadlines to hide launch latency. Actual-model inference is separately ignored and opt-in via `RHYTHM_TEST_MODEL`; never claim it verified without real output.

**Inference engine:** Rhythm supervises upstream `llama-server`, pinned to one llama.cpp build number with per-archive size/SHA-256 in `scripts/llama-cpp.json` (macOS arm64 Metal; Windows Vulkan and CPU). Change the build and all checksums together, then rerun the real-model checks. `server.rs` starts one generation process per loaded model with `--no-webui --no-slots --jinja --reasoning-budget 0 -np 1 -lv 4` (level 4 logs the device and offloaded layers), waits for `/health`, and sends `/v1/chat/completions` with greedy sampling and thinking disabled. An embedding process replaces those chat flags with `--embedding --pooling <model> --embd-normalize 2 --batch-size 2048 --ubatch-size 2048`, uses an 8K context, and sends bounded batches to `/v1/embeddings`; it uses its own `<app data>/run/embedding/` socket/key directory. An installed projector adds `--mmproj <file> --image-min-tokens 1024 --image-max-tokens 2048`; vision is reported only after the log shows `loaded multimodal model`. It listens on `<app data>/run/llama.sock` when that path fits the 103-byte Unix socket limit, otherwise on 127.0.0.1 port 0 with a per-launch key file that is deleted once the server is ready (Windows always uses loopback). Responses need an exact `Content-Length`. Loading another model, unloading and cancelling kill and reap the process.

**GPU selection:** macOS tries Metal and falls back to CPU (`-ngl 0 --device none`) for the session after a load or request failure. The Windows execution mode (`auto`/`cpu`/`gpu`, schema 8) picks the build: the Vulkan build runs only on an NVIDIA device from `--list-devices` and reports a GPU load only after the log shows every layer offloaded; `gpu` reports errors; `auto` falls back to the independent CPU build for the session, but a context-overflow rejection (`토큰 한도를 넘습니다`, 8192-token Vulkan context; CPU/Metal use 32768) retries only that request on CPU. On other platforms the mode is ignored. `intelligence::gpu_tests` run only on Windows against the fake server; hosted CI has no NVIDIA GPU. Through `llama-server` b12068, pinned Qwen3.5 2B and 4B Q4_K_M produced useful structured Korean output on macOS Apple Silicon/Metal (4B: 18/18 completed, 15/18 passed every screening check), as did Gemma 4 E2B/E4B (18/18 completed, 12/18 and 14/18 passed; macOS Metal only), and 2B/4B ran the synthetic evaluation on Windows with one GTX 1650 (Vulkan) and on CPU (4B CPU: 4 fixtures); 2B also ran all 18 fixtures on macOS CPU through the fallback launch (7/18 passed every screening check), so macOS CPU quality is measured for 2B only, and other GPUs remain unverified. Do not download weights implicitly. See `docs/AI_EVALUATION.md`.

### Intelligence and personalization verification and invariants

Focused deterministic checks:

```sh
cargo test --locked -p rhythm storage::intelligence_tests
cargo test --locked -p rhythm intelligence::analysis
cargo test --locked -p rhythm intelligence::remote
cargo test --locked -p rhythm intelligence::classification
cargo test --locked -p rhythm intelligence::models
cargo test --locked -p rhythm intelligence::maintenance
cargo test --locked -p rhythm intelligence::commands
cargo test --locked -p rhythm intelligence::operations
cargo test --locked -p rhythm intelligence::tests
cargo test --locked -p rhythm intelligence::server
cargo test --locked -p rhythm storage::personalization_tests
cargo test --locked -p rhythm ranking_candidate_retrieval_is_bounded -- --nocapture
```

Normal tests must not download weights. The explicitly ignored `real_curated_model_install` exercises the production downloader with a pinned catalog entry only for validation. With approved weight/disk budget, set `RHYTHM_MODEL_INSTALL_ID` and `RHYTHM_MODEL_INSTALL_DIR` to a dedicated test directory. Never target production app data. Use `RHYTHM_MODEL_EVAL_ROOT`/`RHYTHM_MODEL_EVAL_ID` and `RHYTHM_AI_EVAL_REPORT` (with the staged build or `RHYTHM_LLAMA_TEST_DIR`, e.g. a bundle's `Contents/Resources/llama`) for ignored `actual_qwen35_analysis_evaluation`; details and bounds are in `docs/AI_EVALUATION.md`.

- Catalog entries are pinned immutable repository revisions/files/size/SHA-256, not arbitrary URLs. Each entry may also pin an optional same-revision `mmproj-F16.gguf` vision projector (file/size/SHA-256/memory estimate) with its own inventory row and digest; installing or removing it is a separate explicit action, a missing or failed projector leaves the model text-only, and its managed bytes are removed with the model. Restore marks a projector `missing` unless its file is still present with the recorded identity under a still-installed model. Do not promote `experimental` to `verified` without real artifact/backend inference and useful-output evidence. 2B/4B are promoted with an explicit qualification (macOS Apple Silicon/Metal; Windows on one GTX 1650/Vulkan and CPU), and Gemma 4 E2B/E4B with macOS Apple Silicon/Metal only; catalog IDs allow only ASCII alphanumerics and `-`. 9B (`qwen35-9b`, never run) and 0.8B (`qwen35-0-8b`, failed the synthetic evaluation, #74) were removed from the catalog: existing inventory rows with a catalog ID absent from the catalog must still open, select, remove and restore, and the UI labels them as no longer offered; never delete their bytes implicitly.
- Embedding classification is deterministic local similarity, not generation. `intelligence/classification.rs` embeds an instruction + title + first 1000 body characters, compares the unit vector against authored Korean prototypes, stores the raw score/margin and prototype config hash per revision, and maps a best score below `0.50` to `기타` with a low-confidence marker. The raw score stays in SQLite. A model SHA-256 or config-hash change is a new scope; stored vectors allow reclassification without re-embedding. When `engine=openai-compatible`, `remote_embeddings` and consent are all on, the same bounded inputs and prototypes go to the remote `/v1/embeddings` endpoint instead; the identity becomes the derived embedding hash and local vectors/classifications stay valid. Remote classification is automatic, so it has its own switch and must stay off without consent. Stored vectors also back reader similar notices and list cross-post grouping (`Store::ai_similar_notices`): compare only latest-revision vectors under one model hash within the newest `SIMILARITY_WINDOW` (2000) notices, and require an identical normalized title and identical body digit runs for a duplicate; grouping folds copies under an expandable row and never removes a notice. Semantic search (`archive_ranked_query`, #127) embeds the query locally with `SEARCH_INSTRUCTION`, never through the remote endpoint (search text is user input, not public notice text), only while classification is on with an installed, unfailed local model, and fuses it by reciprocal rank with the text ranking; no model means text-only relevance ranking. Every text match must still appear exactly once across pages; the 0.20/0.08 cut-off was measured only on synthetic fixtures (`actual_semantic_search_evaluation`). Never feed classification or similarity into ranking urgency, notifications, learned topics or network calls, and never delete archive content or analysis results when removing the embedding model. The embedding artifact is a separate explicit install (catalog `kind: "embedding"`); classification runs automatically only after that install and can be switched off. macOS Metal/CPU was measured on 18 synthetic fixtures; Windows and broader accuracy are unverified. Prompt 5 no longer generates category, so old results with a category remain readable but their category is ignored.
- Opt-in remote engine (`intelligence/remote.rs`, user decision #77). The local engine remains the default and fully supported. Remote analysis stays off until the user selects `engine=openai-compatible`, saves a normalized base URL and model, and records explicit consent bound to that origin; changing the origin clears consent, automatic work and remote classification. Requests contain only the analysis prompt (notice title/body source objects and the fixed instructions) — never personalization, profile, feedback, saved/read state, archive IDs or device identifiers — and never archived image bytes, so remote analysis is text-only. The API key lives only in the OS credential store (keyring on macOS/Windows; no plaintext or file fallback) and is never written to SQLite, backups, diagnostics or logs. HTTPS is required; plain HTTP is limited to loopback (`127.0.0.1`, `::1`, `localhost`); proxies and redirects are disabled, and the key is sent only to the configured origin. On HTTP 400/422 the request falls back from `json_schema` to `json_object`, then plain text; the negotiated format is cached for the session. All existing validators and the one-repair limit are unchanged.
- Remote results have no artifact hash. `model_sha256` is a derived hash of the engine id, normalized origin and model, and the configuration hash adds the origin, model and timeout; local and remote results therefore remain separate cache entries and the local pinned hash is unchanged. The result records and the UI shows the engine, model and host. Automatic remote work is a separate opt-in with a persisted per-local-day cap; direct user requests are not counted. Never add implicit remote use, remote vision, telemetry or a provider beyond the user-configured OpenAI-compatible endpoint without a new decision.

- For native macOS backup/restore checks, create an isolated profile with `RHYTHM_NATIVE_PROFILE_DIR=<fresh HOME>/Library/Application\ Support/io.github.hiyabye.rhythm cargo test --locked -p rhythm write_populated_native_profile -- --ignored` and launch the bundle executable with that `HOME`. LaunchServices/Finder launches ignore a temporary `HOME` and open the real profile.

## Security and implementation constraints

- Keep user-facing UI, feedback and errors in natural Korean. Internal IDs/docs may use English. Keep `src/lib/types.ts` and Rust payloads synchronized; validate backend inputs.
- Automatic fetches use exact approved HTTPS hosts/routes (`network::Access::Source`), public DNS with pinned answers, same-origin redirects authorized by robots before every hop, pacing, cancellation, size/deadline/retry limits. Transport returns redirect targets; only the sync policy layer may follow them. Completed resource response bytes consume the job budget even if format validation or filesystem persistence fails. Preserving HTTP(S) resource metadata is not permission to fetch it. Exception (user decision, #78): an image embedded in an archived notice (`Access::EmbeddedImage`) may come from any other public HTTPS host name on port 443, never an IP literal, plain HTTP or another route on a `*.sogang.ac.kr` host; that host's robots.txt applies (cached per job; 4xx means no rules, other failures block), redirects stay same-origin and bytes must be a verified raster. Third-party attachments stay blocked. Running out of the job's resource budget leaves files `pending`, never `too_large`. No authentication/access-control bypass or downloaded-code execution.
- Manual seat checks use the separate `Access::Studium`: only `https://libseat.sogang.ac.kr:444/robots.txt`, `/SEAT/domian5.asp` and `/SEAT/roomview5.asp?room_no=<one fixed catalog ID>` are allowed. For this access mode only, Reqwest selects native TLS (Windows Schannel, macOS Secure Transport), requires TLS 1.2 or newer and verifies hostname/certificate chain against the OS trust store. This is an explicit compatibility decision for the seat server's legacy TLS cipher support; no invalid-certificate acceptance, extra root, proxy or protocol downgrade is allowed. OS trust/cipher policy can still refuse the connection, and compatibility must be checked separately on each platform. Preserve pinned public DNS, robots, pacing and cancellation; page bytes are capped at 1,000,000. Redirects and extra/encoded query parameters are refused. A failed manual cycle is not automatically repeated; 401/403/429 must not receive short retries. Enabling Reqwest's `native-tls` feature changes its default backend: every other client must explicitly retain its Rustls backend so this exception remains seat-only.
- `archive/tls.rs` supplements only the exact `www.sogang.ac.kr`, `new-cms.sogang.ac.kr` and `eclass.sogang.ac.kr` intermediate chains (the same Sectigo OV R36 intermediate). Intermediates are **untrusted candidates**, not roots. Preserve Mozilla roots and normal WebPKI hostname/validity/signature/usage/path checks. Read `src-tauri/src/archive/certificates/README.md` before certificate changes; never repair connectivity by accepting invalid certificates or promoting intermediates to roots.
- Render only sanitized reader content; original responses are archive data. No script/style/iframe/event-handler content or remote-image fallback. Local images require bounded raster bytes and SHA-256 verification. External HTTP(S) links require explicit user action through the OS browser. File reveal must not execute attachments.
- Retain MIME/size/hash/state metadata, generated paths and last-good verified resource references. Retry must repair corrupt bytes rather than assume a hash filename proves integrity. Report failed/oversized/unsupported resources without discarding useful text.
- No telemetry or cloud storage of user data. Network use is limited to approved archive sources, the opt-in Cybercampus session, explicit Studium seat checks, images embedded in archived notices (above), explicit model downloads, the updater's GitHub release endpoint and the user-configured OpenAI-compatible endpoint when remote inference is explicitly enabled. Remote inference is off by default and sends only public notice analysis text; it never sends personalization or personal data. Local inference runs only in a child process that Rhythm starts, owns and stops. That process may serve HTTP only on a Unix socket in a `0700` app-data directory, or, where Unix sockets are unavailable, on 127.0.0.1 with a random per-launch API key; it must never listen on another interface or be usable by other processes without that key. The server process owns the loaded model; its stdout is discarded and its stderr is drained as bounded diagnostics. App startup needs no weights or GPU tooling. Compiled backend, loaded backend, artifact integrity, actual generation and useful Korean analysis are distinct verification claims.
- Rhythm is GPL-3.0-or-later (user decision; v1.7.1 and earlier were released under MIT). New dependencies, vendored code and bundled files must be GPLv3-compatible; keep upstream notices for vendored/ported code and bundle third-party license texts under `assets/licenses/`.
- Use Rustfmt; frontend code must pass `npm run check` without warnings. No separate frontend formatter/linter is configured.
