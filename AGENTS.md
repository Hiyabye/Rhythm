# Rhythm development

## Scope and architecture

Rhythm is a Korean-first, local-first Tauri 2 desktop command center. Current product support and distribution target **macOS Apple Silicon (arm64) and Windows 11 x64** (user decision, added from contributor PR #1); Linux/Intel Mac code and CI/runtime observations are historical, not current support. Both platforms share the bundle identifier `io.github.hiyabye.rhythm`; platform code lives behind `cfg(target_os = "macos")`/`cfg(windows)` and must not remove the other platform's path. Windows evidence in `docs/WINDOWS_VALIDATION.md` was mostly collected by the contributor before the merge and has not been re-run on the merged build. Read `docs/ARCHITECTURE.md` before changing component boundaries and `docs/ROADMAP.md` before adding product scope. Current implementation is v1.0.0 (stable): archive, optional local AI and deterministic personalization, opt-in lifecycle/scheduling/notifications, versioned single-file backup/restore. Backups exclude model weights and are not encrypted; restore retains managed models only when local weights match expected size/SHA-256. Confirmed restore quits Rhythm; the next manual launch finalizes it and reports the outcome.

**Distribution policy (user decision):** release artifacts are an ad-hoc-signed (hardened runtime) `Rhythm.app` in `Rhythm_<version>_aarch64.dmg` plus a SHA-256 checksum file generated from the final DMG. Developer ID signing and Apple notarization are intentionally excluded; do not treat their absence as a task, request Apple membership, create Developer ID/notary credentials, bypass Gatekeeper, strip quarantine, or describe ad-hoc as trusted/notarized. Gatekeeper rejects these builds; that is expected and documented in README. `scripts/macos-release.mjs` (Developer ID path) is retained for a possible future decision and refuses to run without credentials. Updates are manual app replacement; the production updater stays disabled (no production key, no update server, Developer ID/updater `release-draft.yml` not activated). The signed-updater code, `scripts/verify-update.mjs` and their tests remain for possible future use; without `RHYTHM_UPDATER_PUBKEY` Settings shows manual update steps. Never test with or overwrite `/Applications/Rhythm.app` or the real profile.

**Windows distribution (current state, signing not decided):** an unsigned per-user NSIS installer (`installMode: currentUser`, custom `scripts/installer-template.nsi` and `installer-hooks.nsh`) that bundles both AI workers and the app-local Microsoft VC runtime DLLs; SmartScreen warnings are expected and documented in README. No Authenticode signing exists; do not describe the installer as signed or trusted. Updates are manual reinstallation; uninstall preserves user data and models. Windows config overrides live in `src-tauri/tauri.windows.conf.json` (Tauri JSON-merge-patches it over `tauri.conf.json`; arrays replace).

**Release outputs:** a default `npm run desktop:build` (release, no `--bundles`/`--no-bundle`) deletes `target/release/bundle/` first, then writes exactly two files to a fresh `target/release/distribution/`: on macOS `Rhythm_<version>_<arch>.dmg` and `<dmg>.sha256`; on Windows `Rhythm_<version>_x64-setup.exe` and `<exe>.sha256` (both in `shasum -a 256` format, computed from that file). Publish only those two files; never pick artifacts from `target/release/bundle/`. `.github/workflows/release.yml` automates this on a pushed `v*.*.*` tag: it requires the tag commit to be reachable from `main` and to match every version field, refuses an existing release, runs `npm run desktop:build` on `macos-14` and `windows-latest`, checks that exactly the four distribution files exist and match their checksums, and creates a **draft** release only; the maintainer publishes it. It uses no secrets and has `contents: write` only in its release job. Its `desktop`/`windows` job IDs and Cargo/CMake env match `ci.yml` so the tag build can restore main's rust-cache (restore only). The Windows MSVC/Ninja/pinned Vulkan SDK/LLVM setup lives in `.github/actions/windows-build-tools`, shared by both workflows; change pinned versions/checksums there. To release: set the same version in `package.json`, `package-lock.json`, `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml`, `crates/ai-worker/Cargo.toml` (and `Cargo.lock`), merge to `main`, then push tag `vX.Y.Z` on a `main` commit; before publishing the draft, confirm the macOS job log reports the Metal backend. Pushing tags and publishing releases change remote state: ask first. Release builds pass `--remap-path-prefix` for `$HOME`, `CARGO_HOME` and the checkout via `CARGO_ENCODED_RUSTFLAGS` (appending any existing `RUSTFLAGS`/`CARGO_ENCODED_RUSTFLAGS`) so binaries carry no builder paths; check with `strings <binary> | grep "$HOME"`. Cargo `trim-paths` is unstable on the pinned toolchain. Debug builds keep real paths.

**Dependency advisories (reviewed for v1.0.0):** the app's backup code uses `zip` 9.2.2. `zip` 8.6.0 remains only through candle-core in the worker (mistral.rs v0.9.1, and still in v0.9.5); candle uses it for `.npz`/pickle loading, which the GGUF-only worker never reaches, so those Dependabot alerts were dismissed as not used. Move off it when an upstream mistral.rs release uses `zip` >= 9.0.5. `deepmerge` (dev-only via `@sveltejs/vite-plugin-svelte`, no fixed release) and Linux-only `glib` 0.18.5 (needs Tauri 3) are open by user decision.

- `src/`: Svelte 5 runes, TypeScript and Tailwind/custom CSS. `App.svelte` owns navigation/settings; `lib/ArchiveView.svelte`, `DocumentReader.svelte` and `SourceSettings.svelte` own archive surfaces; `PersonalizationSettings.svelte` manages profile/interests/memory; `AiSettings.svelte` and revision-keyed `AnalysisPanel.svelte` own AI management/results. `lib/types.ts` mirrors command payloads.
- `src-tauri/src/main.rs`: Tauri command registration, application state/startup/exit; `core/mod.rs` owns the data-directory lock and platform menu. Windows-only modules: `core/windows_autostart.rs` (HKCU Run/StartupApproved), `archive/windows_reveal.rs` (Explorer select, never executes), `proactive/windows_notification.rs` (WinRT toast, AUMID, `rhythm-win:` protocol), `storage/notification_activation.rs` (one-use token ledger), `backup_windows.rs` (fixed-NTFS checks and journaled moves). `platform_support.rs` reports per-platform feature availability to the UI.
- `src-tauri/src/archive/`: shared record models, catalog, independent native parsers, constrained HTTPS/TLS, manual job controller and archive commands. `fixtures/README.md` and `certificates/README.md` document source/certificate provenance.
- `src-tauri/src/storage/`: rusqlite settings/archive/personalization/AI inventory/job/result/proactive APIs, FTS and upgrade tests; ordered migrations through `009_ai_model_directory.sql` are in `src-tauri/migrations/`.
- `src-tauri/src/extensions/`: built-in metadata, registry and lifecycle; opt-in is separate from subscriptions/support.
- `src-tauri/src/intelligence/`: worker client, `models.rs`/pinned `catalog.json`, single `analysis.rs` queue, transient `operations.rs` owner, Tauri `commands.rs` and app-open `maintenance.rs`. Synthetic evaluation fixtures/tests are `evaluation.json`/`evaluation.rs`; opt-in read-only local-archive evaluation is `archived_evaluation.rs`. Collection never waits for AI.
- `src-tauri/src/proactive/`: `scheduler.rs` runs persisted source tasks while the app is open; `notification.rs` discovers, filters, batches and routes notification actions. `core/lifecycle.rs` owns tray/window/login behavior; settings and durable event/task state live in `storage/proactive.rs` and schema migrations 005–007.
- `crates/ai-worker/`: isolated JSON-lines executable. The default feature is the mistral.rs runtime (`metal`/`cuda` add accelerators); `--no-default-features --features gpu-inference` builds the Windows llama.cpp Vulkan worker (`src/gpu.rs`), shipped as a separate `rhythm-ai-worker-gpu` sidecar. Read its `README.md` before worker/inference changes.
- `scripts/desktop.mjs`: host worker build/staging and Tauri invocation; on Windows it delegates to `scripts/desktop-windows.mjs` (VC runtime staging via `stage-vc-runtime.ps1` first, then both workers and NSIS distribution). Staging runs under `RHYTHM_POWERSHELL` (default `powershell.exe`; `windows-env.ps1` exports its own host, CI passes its `pwsh`); never override execution policy or retry under another host. `scripts/setup-windows.ps1`/`windows-env.ps1` prepare a Windows toolchain (see `docs/WINDOWS.md`); `verify-windows-install.ps1` and `validate-gpu.mjs` are manual native verifiers.
- `scripts/macos-release.mjs`: Developer ID build, nested signing, notarization, stapling and Gatekeeper verification; refuses to run without credentials and never falls back to ad-hoc. `scripts/verify-update.mjs`: independent updater signature/manifest/archive verifier used by the release workflow.
- `assets/branding/beat.svg`: vector icon source; committed desktop icons are in `src-tauri/icons/`.

There are only two Cargo workspace members. Do not add a crate or generic extension/plugin infrastructure without a concrete need. Source-specific parsing stays outside generic storage and reader code.

## Setup and commands

Use stable Rust **1.90+**, Node.js **22.12+**, npm and the [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/) for the host. Keep `cargo` and `rustc` on PATH. Use committed root `Cargo.lock` and `package-lock.json`. Desktop app scripts accept macOS and Windows 11 x64 (MSVC host) and reject other hosts; Rust/frontend-only development may still use other hosts but does not imply product support. Windows builds additionally need Visual Studio C++ tools, and the GPU worker needs the Vulkan SDK, libclang, CMake, Ninja and a short `RHYTHM_GPU_TARGET_DIR` (≤32 characters); see `docs/WINDOWS.md`. `RHYTHM_AI_BACKEND=cpu` on Windows is for development or `--no-bundle` only; installers require both workers.

```sh
npm ci
npm run desktop                      # Metal if Apple Silicon tooling is available, otherwise CPU
npm run desktop:build                # release worker + app/DMG; distribution files in target/release/distribution/
npm run desktop:build -- --debug      # debug worker/application/bundle
npm run desktop:build -- --no-bundle  # native build without installer generation
npm run check                        # Svelte/TypeScript diagnostics
npm run build                        # frontend production build only
npm run test:ui                      # compiled frontend + mocked IPC, Chromium/WebKit
npm run test:desktop                 # macOS script stubs (POSIX) and Windows build orchestration (any host)
npm run test:release                 # updater signature verifier (disposable Tauri-signer keys), release preflight, release/CI workflow rules
cargo fmt --all
cargo clippy --locked --workspace --all-targets -- -D warnings
cargo test --locked --workspace
```

CI (`ci.yml`) runs each concern once and only when its files changed: a `changes` job runs `scripts/ci-changes.mjs` (merge commit vs first parent on PRs, `before..after` on `main`, everything when unknown, on manual runs or when `.github/` changes) and gates `frontend` (check, build, Node script tests, Playwright), `rust-fmt`, and the macOS/Windows clippy+test jobs (`desktop`/`windows`; keep these IDs and their Cargo/CMake env in sync with `release.yml` for cache restore). Release builds in those jobs run only on `main` or manual runs when packaging inputs changed. Markdown files never trigger the Rust or packaging jobs. When Rust code or tests start reading a file outside `src-tauri/`/`crates/`, or a new top-level config appears, update the rules and `tests/ci-changes.test.mjs`; a missing rule silently skips checks. Tauri checks need `src-tauri/binaries/rhythm-ai-worker-<host-triple>` (and on Windows also `rhythm-ai-worker-gpu-<host-triple>.exe` plus `binaries/vc-runtime/`). The desktop scripts create them; CI stages debug workers before Clippy/tests. Direct Tauri invocation on a fresh checkout bypasses this step. Generated sidecars are ignored; icons are committed. The helper targets the host and assumes Cargo's default workspace `target/` directory. Notifications use the macOS-native UserNotifications APIs and the async `mac-usernotifications` 0.3.1 sender on macOS, and WinRT toasts with the installed AUMID and a verified per-user `rhythm-win:` protocol registration on Windows. Linux has no sender; do not imply a plugin-backed sender or support path. Request authorization only on explicit user action. Do not treat API handoff as evidence of OS authorization/display/receipt; keep to the native evidence and limits recorded in `docs/ROADMAP.md#verification-status`.

UI tests use the dev dependency `@playwright/test` and require its Chromium/WebKit binaries (`npx playwright install chromium webkit`; CI also installs OS prerequisites). `playwright.config.ts` builds/serves the actual frontend at 127.0.0.1:4178; tests mock only the Tauri boundary and must not be reported as native backend verification. Test output/traces stay under ignored `node_modules/.cache/`. Do not rely on a running preview server; the suite owns its server. Maintain meaningful keyboard/focus, failure-state, paging and reader regressions alongside Rust/native checks. The frontend picks platform-specific controls and wording from the WebView user agent (`src/lib/platform.ts`, never for security decisions); `tests/ui/windows.spec.ts` runs with a Windows user agent and the fixture's `windows: true` defaults, and every other spec exercises the macOS path.

For core real-worker lifecycle/crash-isolation tests, build the worker and set `RHYTHM_WORKER_TEST_BIN` to its absolute executable path before `cargo test -p rhythm`. Without it, the core real-worker test returns early; a passing suite alone does not establish process integration. Worker process tests launch their own test-built executable. Controlled fake workers must be compiled through `src-tauri/src/intelligence/test_worker.rs`: once per test process, from fixed source, with first launch completed before any protocol deadline. macOS holds each newly created executable before its first instruction for an execution-policy check; per-test unique binaries launched in parallel exceeded the 8-second status deadline. Pass per-test behavior through arguments or files beside a hard link, never by baking paths into source. Do not raise IPC deadlines to hide launch latency. Actual-model inference is separately ignored and opt-in via `RHYTHM_TEST_MODEL`; never claim it verified without real output.

**Windows GPU worker:** `llama-cpp-2`/`llama-cpp-sys-2` pinned to `0.1.160` with Vulkan, NVIDIA-only device selection and observed layer offload before reporting a GPU load. CPU and GPU features are mutually exclusive (compile error); preserve the independent CPU fallback binary and never use `target-cpu=native`. The Windows execution mode (`auto`/`cpu`/`gpu`, schema 8) selects the sidecar: `gpu` reports errors; `auto` falls back to CPU for the session after a device/load/protocol failure, but a context-overflow rejection (`토큰 한도를 넘습니다`, an 8192-token GPU context) retries only that request on CPU. On other platforms the mode is ignored. GPU tests (`intelligence::gpu_tests`, worker `--features gpu-inference`) run only on Windows; hosted CI has no NVIDIA GPU, so they verify protocol and fallback, not GPU inference. Observed GPU inference is limited to one GTX 1650 (contributor evidence in `docs/WINDOWS_VALIDATION.md`).

Direct Cargo worker builds default to CPU inference with mistral.rs v0.9.1 pinned to release commit `11f255058573e085afe0a149f8a19cbd39aa1200`; this inspected release adds the required `qwen35` GGUF route. macOS desktop scripts default Apple Silicon to Metal only when the existing compiler probe succeeds, otherwise CPU; Intel Macs use CPU. `RHYTHM_AI_BACKEND=cpu|metal` overrides the desktop selection; an explicit `metal` still runs the probe and fails the build when `xcrun metal` is unavailable, and `release.yml` sets it after installing the Metal Toolchain on the runner if missing; the macOS script rejects CUDA; Windows NVIDIA support is the separate Vulkan worker above. Direct worker builds still have a CUDA feature, but it is not a supported product path. Apple Metal Toolchain was installed with explicit approval; an Xcode update can remove it (`xcodebuild -showComponent MetalToolchain`), after which desktop builds silently select CPU. Check the build log line before claiming a Metal bundle. Pinned Qwen3.5 2B/4B Q4_K_M produced useful structured Korean output on macOS Apple Silicon/Metal; this does not verify CPU, CUDA or 9B. Do not install toolchains or download weights implicitly. See `crates/ai-worker/README.md` and `docs/AI_EVALUATION.md`.

### Intelligence and personalization verification and invariants

Focused deterministic checks:

```sh
cargo test --locked -p rhythm storage::intelligence_tests
cargo test --locked -p rhythm intelligence::analysis
cargo test --locked -p rhythm intelligence::models
cargo test --locked -p rhythm intelligence::maintenance
cargo test --locked -p rhythm intelligence::commands
cargo test --locked -p rhythm intelligence::operations
cargo test --locked -p rhythm-ai-worker
cargo test --locked -p rhythm storage::personalization_tests
cargo test --locked -p rhythm ranking_candidate_retrieval_is_bounded -- --nocapture
```

Normal tests must not download weights. The explicitly ignored `real_curated_model_install` exercises the production downloader with a pinned experimental entry only for validation. With approved weight/disk budget, set `RHYTHM_MODEL_INSTALL_ID` and `RHYTHM_MODEL_INSTALL_DIR` to a dedicated test directory. Never target production app data. Use `RHYTHM_MODEL_EVAL_ROOT`/`RHYTHM_MODEL_EVAL_ID`, `RHYTHM_WORKER_TEST_BIN` and `RHYTHM_AI_EVAL_REPORT` for ignored `actual_qwen35_analysis_evaluation`; details and bounds are in `docs/AI_EVALUATION.md`. Build the specified worker executable explicitly before running process tests; a prior test or feature build may leave a different backend/lifecycle binary at the same path.

- Catalog entries are pinned immutable repository revisions/files/size/SHA-256, not arbitrary URLs. Do not promote `experimental` to `verified` without real artifact/backend inference and useful-output evidence. 2B/4B are promoted with an explicit macOS Apple Silicon/Metal qualification; 0.8B (`qwen35-0-8b`; IDs allow only ASCII alphanumerics and `-`) is experimental and installation-gated. 9B (`qwen35-9b`) was removed from the catalog after v1.0.0: existing inventory rows with a catalog ID absent from the catalog must still open, select, remove and restore, and the UI labels them as no longer offered; never delete their bytes implicitly.
- Model transport is separate from archive transport. Keep HTTPS exact-host/path checks, public DNS/pinned answers, reviewed CDN redirects, disabled proxies and committed digest validation. Safe resume requires strong ETag and exact range validation; use generated `.part` paths and atomic finalization. Disk admission reserves 1 GiB beyond remaining weights.
- One model/sequence and one analysis at a time. Never cancel serial IPC by dropping its future and reusing the pipe: persist analysis cancellation, stop/reap, then restart on demand. Unload reaps/restarts to reclaim process memory. Command-owned load/setup/register uses transient backend operation state; cancellation/exit must join cooperative blocking verification or stop/reap interrupted IPC before releasing admission. Do not persist operation status as new job kinds.
- Model registration computes identity, but preflight only accepts GGUF v2/v3 `qwen3`/`qwen35`; it is not complete tensor/runtime validation. Re-registering a changed external file must unload cached weights before output can claim its new hash. Preserve complete-file integrity checks; the approved `sha2` assembly feature applies only to macOS aarch64 and does not replace hashing with metadata or sampled bytes.
- Model-folder changes use `ai_choose_model_directory`/`ai_reset_model_directory`, never ordinary `ai_preferences`, and share AI/maintenance admission. `model_storage.rs` validates the native selection and resolves generated managed paths: on Windows it rejects links/junctions anywhere in the path, on macOS only a linked selected or `models` folder (system links such as `/var` are canonicalized). A new download captures its destination; existing models and interrupted downloads keep theirs. No implicit move/delete accompanies preference changes. A pre-existing final file in a chosen folder is adopted as managed only when that inventory already received every byte; otherwise installation is refused so removal can never delete bytes Rhythm did not write. Restore clears the preference and converts custom managed models to external/missing references without deleting their original files.
- Managed removal cleans ancillary partial bytes before weights, persists a conservative `missing` inventory state before irreversible unlink and reconciles failures. Do not restore selection to a noninstalled artifact. Unregister never deletes external bytes; model removal retains archived documents and results.
- Cache identity includes document/revision, task, artifact hash, prompt/schema versions and semantic configuration hash. Only Windows appends the runtime policy and execution mode to the configuration hash (`auto` admits a result from either engine, and each result records and shows its `loaded_backend`); elsewhere the hash input must stay byte-identical to v1.0 (`configuration_hash_keeps_released_v1_cache_identity`). Preserve previous good results on failed regeneration and after model deletion; never use a bounded terminal-history window as the authoritative active-job/deletion check. Revision-local job reads include all active jobs plus bounded terminal history (the reader requests 20). Stale-result warnings compare the current prompt/schema/configuration contract, not only model identity.
- Analysis uses capability-negotiated `analysis_json_v1` constrained decoding; setup stays ordinary text. Keep the worker's static generation schema aligned with compact analysis ingress, and include decoding/schema changes in semantic cache identity. Grammar is not a semantic-quality guarantee; all source validators and the one-repair limit remain mandatory.
- Prompt version 3 supplies explicit `{id,text}` source objects. Generation facts must contain exactly `kind`, `label`, `value`, `evidence_id`; direct generated evidence/date/uncertainty fields cannot bypass ingress validation. Resolve IDs to exact bytes before validating stored schema 1; historical schema-1 results remain readable. Preserve digit boundaries when matching dates and bind claimed clock times to source-supported dates/times. Missing/ambiguous dates remain unknown. Allow at most one bounded validation repair; literal grounding is not semantic entailment or calibrated confidence. No generated percentages, source-metadata replacement, tool calls or external actions. Render generated text only through escaped Svelte expressions.
- **Lifecycle behavior:** All lifecycle and proactive features default off: autostart, hidden login start, close-to-background, scheduler and notifications. Tray installation failure leaves the app usable but must reject close-to-background. Login registration changes only after explicit user command, is checked against actual OS state and is rolled back if persistence fails; never infer OS registration from stored preference. Single-instance handling runs before data-directory lock/store initialization. A login launch honors `start_hidden`; ordinary manual launch remains visible, explicit `--hidden` applies only to manual launch. Shutdown stops scheduler work and joins/cancels archive work. Do not assert tray, login registration or notification delivery works on unobserved operating systems.
- **Scheduler:** This is an in-process task loop while the app is open, waking every 15 seconds; it is not a persistent OS background service and performs no work while Rhythm is closed. Persisted per-source tasks are reconciled from supported + subscribed sources, scheduler enablement, and the `sogang_notices` extension being enabled. Interval `0` selects the energy-profile default (Eco 60, Balanced/default 30, Performance 15 minutes); explicit intervals are exact values from 15 through 720 minutes. Respect pause, retry/backoff, cancellation, task outcome and source toggles. Keep archive work serialized through the existing controller, and never hold SQLite mutex guards across async network/worker/filesystem work.
- **Notification pipeline:** Notifications are independently opt-in. Candidate/event identity is document + revision + kind; event states/attempts/defer/claim lease and dedupe survive app restarts, bounded history pruning does not permit replay. A migrated database establishes a revision ceiling so upgrades do not announce old notices. Do not notify during local quiet hours; defer rather than consume eligible events. Enforce bounded candidate batches and at most three notification attempts per ten-minute window. Sensitivity modes use the same deterministic personalization score: Important requires preferences and score ≥18; Interested requires explicit-interest match; All admits any otherwise eligible item. Negative feedback or negative-interest matches always suppress. Inactive/unsubscribed/disabled sources suppress. On macOS, a native UserNotifications handoff is only an attempt, not delivery; mark delivered only after an action callback. On Windows the final policy check, token creation, attempt reservation and synchronous WinRT handoff share one store lock (`handoff_validated`); a handoff is `attempted`, and only a validated one-use schema-7 activation token tied to the current attempt marks events delivered. Token hashes and bounded expiry stay local, restore invalidates them, and a click arriving during shutdown is refused. Windows discovery claims nothing unless authorization is `authorized` (verified install identity and protocol owner), even in quiet hours; macOS keeps its quiet-hours deferral. Do not add a provider beyond these two without an explicit product change. After an asynchronous macOS send, process the OS response independently of the scheduler's delivery cycle so waiting for a click/dismissal cannot stall future scheduler work; bound response waiting and stop handling. A macOS alert closes itself after 30 minutes, and the scheduler tracks at most 12 pending responses so an ignored alert cannot stop later deliveries. `proactive_snapshot.notification_permission` remains `unknown`; the settings surface separately invokes native authorization-status and explicit permission-request commands. Request authorization only after explicit user action. macOS status maps not-determined/denied/authorized/provisional/ephemeral, with timeout/error as unavailable; Windows has no permission prompt: status is authorized/denied/unavailable from notifier settings and install identity, and the explicit button sends one test notification (never enables notifications). Other hosts report unavailable. Click activation restores the existing window and carries stable archive identities; the main window subscribes to `proactive://notification-clicked`, falls back to snapshot pending activation if the event precedes subscription, and unlistens when unmounted.
- **Proactive data boundaries:** Keep all proactive state local; events store archive identity references while notification titles are read from archived revisions. Do not add remote notification services, title/body telemetry, external notification actions, or implicit autostart/collection. Backend-validate and bound settings/task/event inputs. Quiet hours use local wall-clock time; persisted timestamps are UTC.
- Schema 5 adds opt-in lifecycle/scheduler/notification settings, persisted per-source task state, a migration-time revision ceiling, a durable dedupe ledger, and bounded event history. Its event states include pending/claimed/attempted/deferred/delivered/suppressed/failed. Schema 6 adds a bounded durable notification attempt ledger and nondecreasing clock watermark; schema 7 stores hashed, expiring Windows activation tokens. Reserve attempts before OS handoff; history clearing/pruning must not reset rate accounting or dedupe. Preserve the revision ceiling on upgrades. Add migration, default-off, task reconciliation, failure/retry, quiet-hours, sensitivity/negative-feedback, dedupe and action-activation tests for proactive changes.

Focused lifecycle/proactive checks:

```sh
cargo test --locked -p rhythm core::lifecycle
cargo test --locked -p rhythm storage::proactive_tests
cargo test --locked -p rhythm proactive::tests
```

- Native notification, scheduler and login evidence is recorded once in `docs/ROADMAP.md#verification-status` (macOS) and `docs/WINDOWS_VALIDATION.md`. On macOS, notification display/click was observed only in an isolated synthetic bundle, login only as a temporary-HOME plist simulation, and the scheduler only in bounded runs; live-source notifications, real login launch and sleep/wake are unverified. Do not generalize beyond those records.
- Deterministic Rust tests do not verify native tray/login/notification behavior. Do not report an API handoff as display or receipt.

### Personalization invariants

- Schema 4 appends `004_personalization.sql`; never rewrite released migrations. Preserve legacy `settings.interests` on upgrade and clear it only on explicit personalization reset. Interest/provenance/feedback stays in SQLite and never enters network calls or diagnostics.
- Ranking is deterministic and bounded; it must work without installed/loaded AI or network access. AI-generated categories, summaries and extracted dates never create ranking urgency or personalized reasons. Keep signal weights, candidate caps, tie-breaking and diversity behavior aligned with `docs/ARCHITECTURE.md`.
- Current document feedback is one idempotent row per document. `interested` and save are deliberate evidence; read/open/search are not. Learning requires two distinct supporting documents, deduplicates `(topic,document,kind)`, expires evidence after 180 days and obeys the learning switch. Recompute after changed feedback/save state and at the next snapshot at least daily for expiry; do not rescan unchanged evidence on every view. Negative feedback stays document-scoped; it must not unsubscribe, hide categories or create inferred dislike.
- Explicit interests are never replaced by learned ones. Editing a learned memory promotes it to explicit. Canonical explicit aliases suppress duplicate learned rows. Removing a learned memory records its current activity-sequence baseline so unchanged retained evidence cannot recreate it. Reset removes personalization state but preserves archive, saved/read state and AI results.
- Match known Korean/English terms through bounded aliases, not a large ontology. New explicit/learned interests and aliases retain the backend caps. Recommendation explanations must derive from score contributions.
- `source_extensions` links source identity to extension ownership. A mapped source is excluded from new recommendations when its preference is absent or disabled; its archive, feedback and saved state remain accessible. Re-enabling restores history without duplicating evidence.
- `documents.last_revision_at` changes only for meaningful revisions. Initial historical backfill must not gain freshness from collection time. Candidate retrieval uses fixed bounded indexed slices and never transfers the full archive to Svelte.
- Learned topics are derived only from document titles and original categories, never body text or AI output. Keep obvious Korean/English sensitive-term exclusions in place; the denylist is lexical, not semantic.
- `src/lib/analysis-contract.json` is the UI fixture source for current prompt/schema versions; Rust parity is regression-tested. Older contract fixtures must be named explicitly and must not become the default.

### Archive verification

Ordinary tests are network-free. Useful focused commands:

```sh
cargo test --locked -p rhythm storage::archive_tests
cargo test --locked -p rhythm archive::parser
cargo test --locked -p rhythm archive::sync
cargo test --locked -p rhythm archive::tls
cargo test --locked -p rhythm large_archive_operations -- --ignored --nocapture
```

`large_profile_backup_restore_benchmark` (ignored) measures backup/restore on a synthetic profile. Run its phases as separate release processes so `/usr/bin/time -l` reports per-phase peak RSS: `RHYTHM_BACKUP_BENCH_DIR=<fresh scratch dir> RHYTHM_BACKUP_BENCH_PHASE=generate|backup|restore|verify|cancel` with optional `RHYTHM_BACKUP_BENCH_DOCUMENTS`/`RHYTHM_BACKUP_BENCH_RESOURCE_MIB`; `RHYTHM_BACKUP_BENCH_FULL_DIR` adds the disk-full check and must be a small dedicated volume (an attached disk image), never the host disk. A ~1 GiB profile needs about 3.2 GB of scratch space.

The ignored archive benchmark ingests 5,000 generated records through actual Store APIs, verifies pagination/filter/index correctness and reports warm debug samples. It is not a live crawl, native IPC or a timing gate. Storage failure tests use an isolated SQLite page cap/abort trigger, never a full host disk or production DB.

## Data and lifecycle invariants

- Persist through Rust/SQLite, not frontend localStorage. Browser previews must state desktop-only limitations instead of simulating success.
- Database is `app_data_dir()/rhythm.sqlite3` on macOS and `app_local_data_dir()/rhythm.sqlite3` (non-roaming `%LOCALAPPDATA%`) on Windows; resources use generated paths below `resources/`. Managed model files are generated under the default `models/` directory or the model's recorded custom destination; resolve them through `model_storage.rs`. External model references stay at canonical original paths and must never be deleted by unregister. Never hardcode home paths or use remote filenames as filesystem paths.
- Acquire the process-lifetime OS data-directory lock **before** opening/recovering the store. Controller admission additionally allows one archive/retry job. Do not open a second live production store to inspect progress: `Store::open` recovers running source/AI jobs and interrupted model downloads.
- Schemas 3–9 append `003_intelligence.sql` through `009_ai_model_directory.sql` after released migrations (7: Windows activation tokens, 8: AI execution mode, 9: chosen model destination and each model's original destination); never rewrite them. AI, personalization and proactive state remain separate from authoritative archive content except explicit identity references. Require populated-old-schema upgrade, transactional rollback and newer-schema rejection tests; do not change a newer DB even to enable WAL.
- Document identity is `(source_id, external_id)`. Preserve original fetched representations, sanitized/normalized content, meaningful revisions and independent read/saved state. Fetch/parse/resource failures must not replace good content or erase user state.
- Approved Sogang exception: for a new notice whose fetched body consists only of one or more iframes, archive its notice metadata only while preserving the original fetched representation; leave sanitized body/content fields empty and record an explicit unsupported-body state. Never fetch or render the iframe or its content. If an existing notice has last-good readable content, an iframe-only/unsupported-body result must not replace it.
- Catalog has 32 sources; main `sogang-academic`, five `computing-*`, and `eng-general`/`eng-careers`/`eng-academic`/`eng-research` are supported. Engineering uses current `/board/{notice,recruit,academic,research}` SSR routes, not retired CMS routes; `parser.rs` dispatches to its source-specific `engineering.rs` submodule. Working list extraction alone is not support. Require verified full article/resource extraction and fixtures before changing support flags.
- Historical checkpoints advance only after article retrievals on a page succeed; resume pending resources for existing text, including HTTP 304 article checks. Counters describe the current attempt; checkpoint/history state is cumulative. Resource failure outcomes are nonfatal to article archival but must surface as failure for explicit retry. Mark history complete only at the last public page, never at a test/safety limit. Resource completeness is separate.
- Incremental discovery must continue past the three-page edit window while regular records are new; repeated pins cannot establish the known frontier. First incremental seed is historical, not a flood of new notices. It is not a full audit of old edits.
- `sogang_notices` is operational but opt-in and source subscriptions are separate. Restoring/enabling preferences starts no network work. `stop` signals cancellation; the owning async disable/exit path waits without holding the SQLite lock. Hide source controls while disabled, reject new downloads, retain archives/subscriptions and allow local read/search/save.
- Never retain SQLite mutex guards across async network/worker/filesystem operations. Check cancellation/extension enablement at commit boundaries.
- Restore must not relaunch the app itself: a relaunched instance can race the exiting process for the single-instance socket and data-directory lock and exit silently. After the durable journal is written, keep maintenance closed and exit; `recover_pending_restore` finalizes on the next launch (idempotently, before `Store::open`) and returns the outcome shown in the window. A recovery error shows a native dialog and exits without deleting the journal or previous data. Backup reads each file once, verifies resources against their recorded SHA-256 while archiving and writes the manifest last; readers locate it by name.
- Windows restore requires a local fixed NTFS volume, rejects reparse points/junctions and cloud sync roots, moves with `MoveFileExW` (no replace or copy fallback) and stops on ambiguous recovery artifacts; Windows has no directory fsync, so restore survives process interruption, not power loss. The subprocess fault test is `cargo test --locked -p rhythm backup::tests::windows_restore_recovers_after_process_abort_at_each_transition -- --exact --nocapture`. Unix keeps directory fsync after each rename. The restore checks query the real Cloud Files API and fail closed on any result except `0x80070186` (not under a sync root); CI runs `scripts/prepare-windows-restore-ci.ps1` first, which may enable/attach `CldFlt` only on GitHub-hosted runners. Locally use only its read-only `-CheckOnly` mode; never skip or bypass the check in tests.
- For native macOS backup/restore checks, create an isolated profile with `RHYTHM_NATIVE_PROFILE_DIR=<fresh HOME>/Library/Application\ Support/io.github.hiyabye.rhythm cargo test --locked -p rhythm write_populated_native_profile -- --ignored` and launch the bundle executable with that `HOME`. LaunchServices/Finder launches ignore a temporary `HOME` and open the real profile.

## Security and implementation constraints

- Keep user-facing UI, feedback and errors in natural Korean. Internal IDs/docs may use English. Keep `src/lib/types.ts` and Rust payloads synchronized; validate backend inputs.
- Automatic fetches use exact approved HTTPS hosts/routes, public DNS with pinned answers, same-origin redirects authorized by robots before every hop, pacing, cancellation, size/deadline/retry limits. Transport returns redirect targets; only the sync policy layer may follow them. Completed resource response bytes consume the job budget even if format validation or filesystem persistence fails. Preserving HTTP(S) resource metadata is not permission to fetch it. No authentication/access-control bypass, unrestricted remote image fetches or downloaded-code execution.
- `archive/tls.rs` supplements only the exact `www.sogang.ac.kr` intermediate chain. Intermediates are **untrusted candidates**, not roots. Preserve Mozilla roots and normal WebPKI hostname/validity/signature/usage/path checks. Read `src-tauri/src/archive/certificates/README.md` before certificate changes; never repair connectivity by accepting invalid certificates or promoting intermediates to roots.
- Render only sanitized reader content; original responses are archive data. No script/style/iframe/event-handler content or remote-image fallback. Local images require bounded raster bytes and SHA-256 verification. External HTTP(S) links require explicit user action through the OS browser. File reveal must not execute attachments.
- Retain MIME/size/hash/state metadata, generated paths and last-good verified resource references. Retry must repair corrupt bytes rather than assume a hash filename proves integrity. Report failed/oversized/unsupported resources without discarding useful text.
- No localhost AI HTTP, cloud inference/storage, telemetry or separate inference service. Model ownership stays in the worker; stdout is exclusively versioned protocol and diagnostics go to stderr. Preserve CPU startup without weights/GPU tooling. Compiled backend, loaded backend, artifact integrity, actual generation and useful Korean analysis are distinct verification claims.
- Both reference collectors' source licensing is unestablished. Do not copy its implementation under an assumed MIT license. Official notice/fixture content retains its original rights.
- Use Rustfmt; frontend code must pass `npm run check` without warnings. No separate frontend formatter/linter is configured.
