# Rhythm development

## Scope and architecture

Rhythm is a Korean-first, local-first Tauri 2 desktop command center. Current product support and distribution target **macOS Apple Silicon (arm64) and Windows 11 x64** (user decision, added from contributor PR #1); Linux/Intel Mac code and CI/runtime observations are historical, not current support. Both platforms share the bundle identifier `io.github.hiyabye.rhythm`; platform code lives behind `cfg(target_os = "macos")`/`cfg(windows)` and must not remove the other platform's path. Windows evidence in `docs/WINDOWS_VALIDATION.md` was collected by the contributor; apart from the PR #63 AI/installer and #36 in-app update runs (validation identifiers), it predates the merged build. Read `docs/ARCHITECTURE.md` before changing component boundaries and `docs/ROADMAP.md` before adding product scope. Current implementation is v1.10.2 (stable): archive, optional local AI classification (embedding model: categories, similar/duplicate notices, semantic search; AI summaries and the remote engine were retired, #226) and deterministic personalization, opt-in lifecycle/scheduling/notifications, an opt-in local calendar with todos, opt-in manual and app-open automatic Studium seat checks with favorites, seat alerts, a mini window and a relative seat map, versioned single-file backup/restore. Backups exclude model weights and are not encrypted; restore retains managed models only when local weights match expected size/SHA-256. Confirmed restore quits Rhythm; the next manual launch finalizes it and reports the outcome.

**Distribution policy (user decision):** release artifacts are an ad-hoc-signed (hardened runtime) `Rhythm.app` in `Rhythm_<version>_aarch64.dmg` plus a SHA-256 checksum file generated from the final DMG. Developer ID signing and Apple notarization are intentionally excluded; do not treat their absence as a task, request Apple membership, create Developer ID/notary credentials, bypass Gatekeeper, strip quarantine, or describe ad-hoc as trusted/notarized. Gatekeeper rejects these builds; that is expected and documented in README. `scripts/macos-release.mjs` (Developer ID path) is retained for a possible future decision and refuses to run without credentials. **In-app updates (user decision, #30):** the Tauri updater signature (minisign/Ed25519) is separate from OS code signing and needs no Apple or Microsoft account, so releases carry signed updater packages and a `latest.json` while the builds themselves stay ad-hoc (macOS) or unsigned (Windows). The updater signature proves origin to the app; never describe it as OS trust, signing or notarization. The endpoint is `https://github.com/Hiyabye/Rhythm/releases/latest/download/latest.json`, which sees only published releases: an update goes live when the maintainer publishes the draft. The app trusts only the key compiled in through `option_env!("RHYTHM_UPDATER_PUBKEY")`; builds without it (local builds, CI) show manual update steps. v1.1.0 and earlier embed no key, so users install the first keyed release manually. Before installing, `updater_restart` stops and reaps the classifier's embedding `llama-server` (maintenance alone does not, and the Windows plugin exits through `process::exit`, skipping `RunEvent::Exit`). macOS in-place update and the Windows passive NSIS update are verified only under validation identifiers with a loopback manifest (`docs/ROADMAP.md#verification-status`, `docs/WINDOWS_VALIDATION.md#in-app-update`, one PC each). Do not claim either beyond those records. Never test with or overwrite `/Applications/Rhythm.app` or the real profile.

**Windows distribution (current state, unsigned by user decision, #85):** an unsigned per-user NSIS installer (`installMode: currentUser`, custom `scripts/installer-template.nsi` and `installer-hooks.nsh`) that bundles the pinned llama.cpp Vulkan and CPU builds (each with its own copy of the VC runtime DLLs it imports) and the app-local Microsoft VC runtime DLLs; SmartScreen warnings are expected and documented in README. No Authenticode signing exists by that decision; do not treat it as a pending task or describe the installer as signed or trusted. The updater package is the setup executable itself with a `.sig`; `tauri.windows.conf.json` sets `plugins.updater.windows.installMode: passive` (the plugin passes `/P /UPDATE /R`; the custom template then skips the uninstall and desktop-shortcut steps and relaunches the app); observed on one PC under a validation identifier (#36). Uninstall preserves user data and models. Windows config overrides live in `src-tauri/tauri.windows.conf.json` (Tauri JSON-merge-patches it over `tauri.conf.json`; arrays replace).

**Release outputs:** a default `npm run desktop:build` (release, no `--bundles`/`--no-bundle`) deletes `target/release/bundle/` first, then writes a fresh `target/release/distribution/`: on macOS `Rhythm_<version>_<arch>.dmg` and `<dmg>.sha256`; on Windows `Rhythm_<version>_x64-setup.exe` and `<exe>.sha256` (both in `shasum -a 256` format, computed from that file). With both `TAURI_SIGNING_PRIVATE_KEY` and `RHYTHM_UPDATER_PUBKEY` set (`scripts/updater-signing.mjs`; one without the other fails before staging) it also passes `createUpdaterArtifacts` and the public key to Tauri (on macOS also the `app` target: a DMG-only build creates no updater archive, only a bundler warning) and adds the updater files: macOS `Rhythm.app.tar.gz` and its `.sig` (Tauri's name, which the signature binds), Windows `<exe>.sig`. Without the key the output stays exactly two files. Per-file `.sha256` covers the DMG/installer only; updater packages are covered by their signatures (user decision: no `SHA256SUMS`). Publish only distribution files plus the generated `latest.json`; never pick artifacts from `target/release/bundle/`. `.github/workflows/release.yml` automates this on a pushed `v*.*.*` tag: it requires the tag commit to be reachable from `main` and to match every version field, refuses an existing release, runs `npm run desktop:build` on `macos-15` and `windows-latest` with the signing key, verifies each updater signature (`verify-update.mjs artifact`), the macOS archive contents and the embedded key (`bundle`, `binary`), checks that exactly the seven distribution files exist and match their checksums, generates `latest.json` (`scripts/update-manifest.mjs`: `darwin-aarch64[-app]` and `windows-x86_64[-nsis]`), verifies it against the staged files (`verify-update.mjs manifest`), and creates a **draft** release only; the maintainer publishes it. Missing signing secrets fail the release (user decision) rather than dropping updater files. The private key and password are secrets of the reviewer-gated `release` environment, used only in the two build steps; the public key is the repository variable `RHYTHM_UPDATER_PUBKEY`. `contents: write` exists only in its release job. Its `desktop`/`windows` job IDs and Cargo env match `ci.yml` so the tag build can restore main's rust-cache (restore only). The Windows MSVC environment setup lives in `.github/actions/windows-build-tools`, shared by both workflows. To release: set the same version in `package.json`, `package-lock.json`, `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml` (and `Cargo.lock`), merge to `main`, then push tag `vX.Y.Z` on a `main` commit. Pushing tags and publishing releases change remote state: ask first. Release builds pass `--remap-path-prefix` for `$HOME`, `CARGO_HOME` and the checkout via `CARGO_ENCODED_RUSTFLAGS` (appending any existing `RUSTFLAGS`/`CARGO_ENCODED_RUSTFLAGS`) so binaries carry no builder paths; check with `strings <binary> | grep "$HOME"`. Cargo `trim-paths` is unstable on the pinned toolchain. Debug builds keep real paths.

**Dependency advisories (reviewed for v1.0.0):** the app's backup code uses `zip` 9.2.2, the only `zip` in `Cargo.lock`. `deepmerge` (dev-only via `@sveltejs/vite-plugin-svelte`, no fixed release) and Linux-only `glib` 0.18.5 (needs Tauri 3) are accepted by user decision; their Dependabot alerts (numbers 7 and 1) are dismissed as tolerable risk. A new advisory for either package opens a new alert that needs its own review.

The Cargo workspace has one member, `src-tauri`. Do not add a crate or generic extension/plugin infrastructure without a concrete need. Source-specific parsing stays outside generic storage and reader code.

## Setup and commands

Use stable Rust **1.90+**, Node.js **22.12+**, npm and the [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/) for the host. Keep `cargo` and `rustc` on PATH. Use committed root `Cargo.lock` and `package-lock.json`. Desktop app scripts accept macOS and Windows 11 x64 (MSVC host) and reject other hosts; Rust/frontend-only development may still use other hosts but does not imply product support. Windows builds additionally need Visual Studio C++ tools; see `docs/WINDOWS.md`. The app needs no CMake, Vulkan SDK or Metal Toolchain: `scripts/stage-llama.mjs` downloads the pinned upstream llama.cpp archives from GitHub releases (network access), caches them in `target/llama-cache/`, rejects any archive whose size or SHA-256 differs from `scripts/llama-cpp.json`, and replaces `src-tauri/binaries/llama/` with exactly that pin.

```sh
npm ci
npm run desktop                      # stage llama.cpp, then run the app in development
npm run desktop:build                # release app/DMG with the bundled llama.cpp build; distribution files in target/release/distribution/
npm run desktop:build -- --debug      # debug application/bundle
node scripts/stage-llama.mjs         # stage the pinned llama.cpp build only
npm run desktop:build -- --no-bundle  # native build without installer generation
npm run check                        # Svelte/TypeScript diagnostics
npm run build                        # frontend production build only
npm run test:ui                      # compiled frontend + mocked IPC, Chromium/WebKit
npm run screenshots                  # opt-in: regenerate docs/screenshots/*.png from synthetic data (tests/ui/screenshots.spec.ts, playwright.screenshots.config.ts, port 4179); not part of test:ui
npm run test:desktop                 # macOS script stubs (POSIX) and Windows build orchestration (any host)
npm run test:release                 # updater signature/manifest verifier and generator (disposable Tauri-signer keys), release preflight, release/CI workflow rules
cargo fmt --all
cargo clippy --locked --workspace --all-targets -- -D warnings
cargo test --locked --workspace
```

The Rust commands need `dist/` (`npm run build`) and the staged llama.cpp resources (`node scripts/stage-llama.mjs`); the Tauri build only checks that the resources exist.

CI (`ci.yml`) runs each concern once and only when its files changed: a `changes` job runs `scripts/ci-changes.mjs` (merge commit vs first parent on PRs, `before..after` on `main`, everything when unknown, on manual runs or when `.github/` changes) and gates `frontend` (check, build, Node script tests, Playwright), `rust-fmt`, and the macOS/Windows clippy+test jobs (`desktop`/`windows`; keep these IDs and their Cargo env in sync with `release.yml` for cache restore). Release builds in those jobs run only on `main` or manual runs when packaging inputs changed. Markdown files never trigger the Rust or packaging jobs. When Rust code or tests start reading a file outside `src-tauri/`, or a new top-level config appears, update the rules and `tests/ci-changes.test.mjs`; a missing rule silently skips checks. The reverse holds too: `tests/capabilities.test.mjs` reads `build.rs`, `src/main.rs` and `capabilities/` from the frontend job, so those paths run it. Tauri checks need the staged `src-tauri/binaries/llama/` resources (on Windows staged after `binaries/vc-runtime/`, whose DLLs each build needs). The desktop scripts and CI run `scripts/stage-llama.mjs` before Clippy/tests; direct Tauri invocation on a fresh checkout bypasses this step. Staged binaries are ignored; icons are committed. A change to the pin or the staging script runs the Rust jobs. The helper targets the host and assumes Cargo's default workspace `target/` directory. Notifications use the macOS-native UserNotifications APIs and the async `mac-usernotifications` 0.3.1 sender on macOS, and WinRT toasts with the installed AUMID and a verified per-user `rhythm-win:` protocol registration on Windows. Linux has no sender; do not imply a plugin-backed sender or support path. Request authorization only on explicit user action. Do not treat API handoff as evidence of OS authorization/display/receipt; keep to the native evidence and limits recorded in `docs/ROADMAP.md#verification-status`.

UI tests use the dev dependency `@playwright/test` and require its Chromium/WebKit binaries (`npx playwright install chromium webkit`; CI also installs OS prerequisites). `playwright.config.ts` builds/serves the actual frontend at 127.0.0.1:4178; tests mock only the Tauri boundary and must not be reported as native backend verification. Test output/traces stay under ignored `node_modules/.cache/`. Do not rely on a running preview server; the suite owns its server. Maintain meaningful keyboard/focus, failure-state, paging and reader regressions alongside Rust/native checks. The frontend picks platform-specific controls and wording from the WebView user agent (`src/lib/platform.ts`, never for security decisions); `tests/ui/windows.spec.ts` runs with a Windows user agent and the fixture's `windows: true` defaults, and every other spec exercises the macOS path.

`intelligence::tests::real_server_lifecycle_without_model_weights` runs the staged real `llama-server` (or `RHYTHM_LLAMA_TEST_DIR`) and returns early when neither exists; a passing suite alone does not establish process integration. Other process tests use the fake `llama-server` in `src-tauri/src/intelligence/test_worker.rs` (same flags, log lines, socket/loopback listener, API-key check and embedding response shapes): compiled once per test process from fixed source, with first launch completed before any request deadline, then hard-linked per test with its `mode` and control files beside it. macOS holds each newly created executable before its first instruction for an execution-policy check; per-test unique binaries launched in parallel exceeded the 8-second status deadline. Pass per-test behavior through files beside a hard link, never by baking paths into source. Do not raise request deadlines to hide launch latency. Actual-model embedding runs only in the ignored evaluations in `embedding_evaluation.rs`; never claim it verified without real output.

**Inference engine:** Rhythm supervises upstream `llama-server` as an embedding server only, pinned to one llama.cpp build number with per-archive size/SHA-256 in `scripts/llama-cpp.json` (macOS arm64 Metal; Windows Vulkan and CPU). Change the build and all checksums together, then rerun the real-model checks. `server.rs` starts one process for the classifier with `--no-webui --no-slots -np 1 -c 8192 -lv 4 --embedding --pooling <model> --embd-normalize 2 --batch-size 2048 --ubatch-size 2048` (level 4 logs the device and offloaded layers), waits for `/health`, and sends bounded batches to `/v1/embeddings`. It listens on `<app data>/run/embedding/llama.sock` when that path fits the 103-byte Unix socket limit, otherwise on 127.0.0.1 port 0 with a per-launch key file that is deleted once the server is ready (Windows always uses loopback). Responses need an exact `Content-Length`. A failed request, inventory change, execution-mode change or a minute without work kills and reaps the process; a late response is never reused.

**GPU selection:** macOS tries Metal and falls back to CPU (`-ngl 0 --device none`) for the session after a load or request failure. The Windows execution mode (`auto`/`cpu`/`gpu`, schema 8) picks the build for the classifier (`classification::Controller::set_execution_mode` pauses classification, reaps the process and applies to the next batch): the Vulkan build runs only on an NVIDIA device from `--list-devices` and reports a GPU load only after the log shows every layer offloaded; `gpu` reports errors; `auto` falls back to the independent CPU build for the session. On other platforms the mode is ignored. `intelligence::gpu_tests` run only on Windows against the fake server; hosted CI has no NVIDIA GPU. Embedding classification was measured on macOS Metal/CPU only; the Windows classifier is unverified. Do not download weights implicitly. See `docs/AI_EVALUATION.md`.

### Intelligence and personalization verification and invariants

Focused deterministic checks:

```sh
cargo test --locked -p rhythm storage::intelligence_tests
cargo test --locked -p rhythm intelligence::classification
cargo test --locked -p rhythm intelligence::models
cargo test --locked -p rhythm intelligence::model_storage
cargo test --locked -p rhythm intelligence::tests
cargo test --locked -p rhythm intelligence::server
cargo test --locked -p rhythm storage::personalization_tests
cargo test --locked -p rhythm ranking_candidate_retrieval_is_bounded -- --nocapture
```

Normal tests must not download weights. The explicitly ignored `real_curated_model_install` exercises the production downloader with a pinned catalog entry only for validation. With approved weight/disk budget, set `RHYTHM_MODEL_INSTALL_ID` and `RHYTHM_MODEL_INSTALL_DIR` to a dedicated test directory. Never target production app data. The ignored `actual_embedding_classification_evaluation` and `actual_semantic_search_evaluation` take `RHYTHM_EMBEDDING_EVAL_MODEL` (with the staged build or `RHYTHM_LLAMA_TEST_DIR`, e.g. a bundle's `Contents/Resources/llama`); details and bounds are in `docs/AI_EVALUATION.md`.

- Catalog entries are pinned immutable repository revisions/files/size/SHA-256, not arbitrary URLs; the catalog pins only the Qwen3-Embedding 0.6B model (`kind: "embedding"`). Do not promote `experimental` to `verified` without real artifact/backend inference and useful-output evidence; catalog IDs allow only ASCII alphanumerics and `-`. Inventory rows whose catalog ID is absent (the retired generation models and their vision projectors, #226, plus the earlier `qwen35-9b`/`qwen35-0-8b`) must still open, remove and restore, and the UI lists them as no longer offered with only a remove action; never delete their bytes implicitly. A retired model's projector bytes are removed with the model; restore marks a projector `missing` unless its file is still present with the recorded identity under a still-installed model.
- Embedding classification is deterministic local similarity, not generation. `intelligence/classification.rs` embeds an instruction + title + first 1000 body characters, compares the unit vector against authored Korean prototypes, stores the raw score/margin and prototype config hash per revision, and maps a best score below `0.50` to `기타` with a low-confidence marker. The raw score stays in SQLite. A model SHA-256 or config-hash change is a new scope; stored vectors allow reclassification without re-embedding. Stored vectors also back reader similar notices and list cross-post grouping (`Store::ai_similar_notices`): compare only latest-revision vectors under one model hash within the newest `SIMILARITY_WINDOW` (2000) notices, and require an identical normalized title and identical body digit runs for a duplicate; grouping folds copies under an expandable row and never removes a notice. Semantic search (`archive_ranked_query`, #127) embeds the query locally with `SEARCH_INSTRUCTION`, only while classification is on with an installed, unfailed local model, and fuses it by reciprocal rank with the text ranking; no model means text-only relevance ranking. Every text match must still appear exactly once across pages; the 0.20/0.08 cut-off was measured only on synthetic fixtures (`actual_semantic_search_evaluation`). Never feed classification or similarity into ranking urgency, notifications, learned topics or network calls, and never delete archive content when removing the embedding model. The embedding artifact is a separate explicit install (catalog `kind: "embedding"`); classification runs automatically only after that install and can be switched off. macOS Metal/CPU was measured on 18 synthetic fixtures; Windows and broader accuracy are unverified. No notice text leaves the device for AI.
- Model transport is separate from archive transport. Keep HTTPS exact-host/path checks, public DNS/pinned answers, reviewed CDN redirects, disabled proxies and committed digest validation. Safe resume requires strong ETag and exact range validation; use generated `.part` paths and atomic finalization. Disk admission reserves 1 GiB beyond remaining weights.
- The embedding classifier is the only inference user: one transient process with its own `run/embedding` socket/key directory. It yields while a model download or exclusive maintenance is active and stops after a minute without work. Never abandon a request and reuse its server: stop/reap the process, then start a fresh one on demand. Inventory changes and the updater wait until the process is reaped (`stop_confirmed`/`stop_worker`).
- External GGUF registration (`ai_register`) was retired (#226); an existing external reference can still be unregistered. Preflight accepts GGUF v2/v3 `qwen3` (the embedding model) and the retired `qwen35`/`gemma4` metadata; it is not complete tensor/runtime validation. The classifier verifies the complete file once per model identity before first use; the approved `sha2` assembly feature applies only to macOS aarch64 and does not replace hashing with metadata or sampled bytes.

- For native macOS backup/restore checks, create an isolated profile with `RHYTHM_NATIVE_PROFILE_DIR=<fresh HOME>/Library/Application\ Support/io.github.hiyabye.rhythm cargo test --locked -p rhythm write_populated_native_profile -- --ignored` and launch the bundle executable with that `HOME`. ## Security and implementation constraints

- Keep user-facing UI, feedback and errors in natural Korean. Internal IDs/docs may use English. Keep `src/lib/types.ts` and Rust payloads synchronized; validate backend inputs.
- A window may invoke only the app commands its capability grants. The `main` capability lists exactly the commands the main window invokes, and `studium-mini` cannot reach backup, extension or credential commands. Do not add a grant before the code that invokes it.
- Automatic fetches use exact approved HTTPS hosts/routes (`network::Access::Source`), public DNS with pinned answers, same-origin redirects authorized by robots before every hop, pacing, cancellation, size/deadline/retry limits. Transport returns redirect targets; only the sync policy layer may follow them. Completed resource response bytes consume the job budget even if format validation or filesystem persistence fails. Preserving HTTP(S) resource metadata is not permission to fetch it. Exception (user decision, #78): an image embedded in an archived notice (`Access::EmbeddedImage`) may come from any other public HTTPS host name on port 443, never an IP literal, plain HTTP or another route on a `*.sogang.ac.kr` host; that host's robots.txt applies (cached per job; 4xx means no rules, other failures block), redirects stay same-origin and bytes must be a verified raster. Third-party attachments stay blocked. Running out of the job's resource budget leaves files `pending`, never `too_large`. No authentication/access-control bypass or downloaded-code execution.
- Seat checks use the separate `Access::Studium`: only `https://libseat.sogang.ac.kr:444/robots.txt`, `/SEAT/domian5.asp` and `/SEAT/roomview5.asp?room_no=<one fixed catalog ID>` are allowed. For this access mode only, Reqwest selects native TLS (Windows Schannel, macOS Secure Transport), requires TLS 1.2 or newer, verifies hostname/certificate chain and replaces the OS root store with the single pinned Sectigo Root R46 (`archive/certificates/sectigo-r46-root.pem`; macOS trusts only that anchor, Windows also requires normal system validation). Never fall back to the OS store or anchor an intermediate. This is an explicit compatibility decision (user decision) for the seat server's CBC-only TLS 1.2 suites, which Rustls lacks; no invalid-certificate acceptance, other root, proxy or protocol downgrade is allowed. OS trust/cipher policy can still refuse the connection, and compatibility must be checked separately on each platform. Preserve pinned public DNS, robots, pacing and cancellation; page bytes are capped at 1,000,000. Redirects and extra/encoded query parameters are refused. Each seat transport call has one attempt. With automatic mode off a failed manual cycle is not repeated; automatic mode uses the normal completion gap after ordinary failures and stops on 401/403/429. Enabling Reqwest's `native-tls` feature changes its default backend: every other client must explicitly retain its Rustls backend so this exception remains seat-only.
- **Studium favorites/search:** persist unique integer preferred numbers per fixed room, in range 1 through its catalog capacity. Removing a room from lookup targets, disabling the extension and app restart preserve these preferences. Empty input clears only that room. Save transactionally and permit edits during a check or automatic session. Snapshot favorites include all seven room keys with sorted arrays. Saving/editing/search/view changes start no seat request. Search is an exact single-number filter over the same current validated list, separate from the overall remaining count; count-only/failed/unchecked never imply occupied or zero matches. Label stale highlights/search as previous observations with current availability unknown. Preserve edited drafts across status polling and write failure; switching viewed room resets the unsaved favorite draft and search. Favorites are settings, not seat observations or history.
- **Studium alerts:** rules default off per room and additionally require the proactive extension, global notifications and native authorization. Request permission only from existing explicit settings controls. Fresh successful manual and automatic observations qualify; count-only may evaluate a remaining-count rule but never a preferred-number rule. The first match reserves one attempt and consumes a durable rearm latch; only a later fresh successful non-match rearms it. Failed/unknown/stale results do not reset it. Reuse global quiet hours and the combined proactive/seat limit of three attempts per ten minutes. Quiet/rate rejection waits for another fresh observation; a reserved uncertain OS handoff is never automatically replayed. Rule/favorite changes invalidate old versions and tokens but evaluate no old data. Persist only settings, the latch, bounded attempt accounting and hashed 30-minute one-use tokens (at most 64); never persist seat observations, source times or HTML. Startup/restore invalidate tokens. Validate the token, current rule/version, enablement and selected room before changing the display room; click navigation and fallback start no school request or alert. Stop/join handoffs and callbacks for disable/maintenance/exit, with final policy checks sharing Store's boundary. Fake senders, mocked clicks and API acceptance do not verify native display, click or macOS compilation.
- **Studium mini/tray:** `views.rs` owns one explicitly opened `studium-mini` native window; `src/main.ts` selects `StudiumMini.svelte` only for `?studium-mini=1`. Main, mini and tray read the same controller state and saved display room. Reuse manual start/cancel, never add another scheduler or request from open/close/view/on-top/show-main operations. Closing mini preserves an active check. Save only native position/size (schema 30), default 380×480, min 300×260, max 1200×1400; no raw geometry IPC. Open state is not restored and always-on-top is session-only, initially off and reset on close. Validate monitor placement and generation-specific close/destroy ownership. Subscribe/unsubscribe to `studium://state-changed`; defer reads during actions and protect edited drafts/response generations. Mini follows saved/live/system theme and the saved/live 12/24-hour format without core-settings polling; independent generations prevent a late settings read from undoing a newer theme or clock event. Source times remain in Korea in the selected clock format. Tray summaries update only the existing tray and preserve restore/quit/background policy. Disable/exit close and clean up window/display work without implicit reopen. Mocked UI and native compilation alone do not verify native lifecycle or OS interaction. Scope Windows native claims to [recorded validation runs](docs/ROADMAP.md#verification-status); DOM-triggered native IPC does not establish physical input on recreated WebView2 windows, OS tray menus, monitor recovery, installed-app behavior or macOS behavior.
- **Studium map:** optional `SeatData.layout`/`layout_error` must come from the same validated detail response as its numbers/counts/source time. Parse only complete, unique, same-parent absolute marker origins in bounded decimal CSS px; normalize minima and keep both axes as integer thousandths of a pixel. Geometry failure preserves verified numbers; count-only/old/wrong-room detail has no map. Never execute source HTML/CSS/scripts, add map requests or persist observed coordinates. Render numbered position markers, not physical seat outlines/walls/doors. Keep ○/× state, favorite stars and search underlining independent of color with readable contrast and the original number list available. Map open/zoom/pan/filter/reset are local-only, default collapsed, zoom 50–200%; reset by room/job/source/receive identity, preserve same-result refresh state. Avoid hundreds of focus targets; provide a named scroll region and accessible summary. Restore focus before a map is removed or controls collapse, preserving other controls/page navigation and unfocused windows. Stale map/number status is historical, never a current availability claim; display source time in Korea consistently with the tray.
- `archive/tls.rs` supplements only the exact `www.sogang.ac.kr`, `new-cms.sogang.ac.kr` and `eclass.sogang.ac.kr` intermediate chains (the same Sectigo OV R36 intermediate). Intermediates are **untrusted candidates**, not roots. Preserve Mozilla roots and normal WebPKI hostname/validity/signature/usage/path checks. Read `src-tauri/src/archive/certificates/README.md` before certificate changes; never repair connectivity by accepting invalid certificates or promoting intermediates to roots.
- Render only sanitized reader content; original responses are archive data. No script/style/iframe/event-handler content or remote-image fallback. Local images require bounded raster bytes and SHA-256 verification. External HTTP(S) links require explicit user action through the OS browser. File reveal must not execute attachments.
- Retain MIME/size/hash/state metadata, generated paths and last-good verified resource references. Retry must repair corrupt bytes rather than assume a hash filename proves integrity. Report failed/oversized/unsupported resources without discarding useful text.
- No telemetry or cloud storage of user data. Network use is limited to approved archive sources, the opt-in Cybercampus session, explicit or explicitly enabled automatic Studium seat checks, images embedded in archived notices (above), explicit model downloads, and the updater's GitHub release endpoint. No notice text, personalization or personal data leaves the device for AI. Local inference runs only in a child process that Rhythm starts, owns and stops. That process may serve HTTP only on a Unix socket in a `0700` app-data directory, or, where Unix sockets are unavailable, on 127.0.0.1 with a random per-launch API key; it must never listen on another interface or be usable by other processes without that key. The server process owns the loaded model; its stdout is discarded and its stderr is drained as bounded diagnostics. App startup needs no weights or GPU tooling. Compiled backend, loaded backend, artifact integrity, actual embedding and classification accuracy are distinct verification claims.
- Rhythm is GPL-3.0-or-later (user decision; v1.7.1 and earlier were released under MIT). New dependencies, vendored code and bundled files must be GPLv3-compatible; keep upstream notices for vendored/ported code and bundle third-party license texts under `assets/licenses/`.
- Use Rustfmt; frontend code must pass `npm run check` without warnings. No separate frontend formatter/linter is configured.
