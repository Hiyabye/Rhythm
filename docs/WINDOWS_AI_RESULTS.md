## 0.9.3 NVIDIA Vulkan addendum — 2026-11-02

The GPU path was exercised on the development Windows 11 x64 machine with an NVIDIA GeForce GTX 1650, 4 GiB dedicated memory and driver 552.44. The worker uses llama.cpp through pinned `llama-cpp-2`/`llama-cpp-sys-2` 0.1.160. GTX 10/16 and RTX 20/30/40/50 remain hardware targets; only this GTX 1650 was exercised. See [Windows GPU setup and limits](WINDOWS_GPU.md).

**At the user's direction, summary correctness is excluded from the GPU feature/build completion criteria.** The reference observations below do not block packaging. Existing source-grounding and output validation remain enforced; a rejected result is still not a completed analysis or a successful cache check.

Initial load took 9.078 s; structured request took 56.867 s, including 56.794 s generation. |

The direct-worker interruption tests terminate the owned child 500 ms after submitting inference, reap it, then start a new worker, load and infer again. They establish interruption at the pending parent IPC request, not that a GPU kernel was active at that exact instant. These checks launch no HTTP service and read existing local model files; they do not establish OS-enforced offline operation. The app-pipeline run's worker working set was 1,832,340 KiB after load and 1,906,268 KiB at its final sample. These are process-memory samples, not GPU VRAM measurements or measured peaks.

Other builds were running during these measurements. **Do not compare these times to the historical CPU results below or describe them as isolated performance benchmarks.** Neither model-file size nor observed offloaded-layer count establishes a maximum VRAM requirement.

The runtime reports are local at `D:\Codex_Rhythm\.build-tools\validation\gpu-1650-2b-01.json` and `gpu-1650-4b-01.json`; the app-pipeline report is `gpu-app-analysis-2b.json`. The direct-worker reports identify worker SHA-256 `00e285cfd8290a62471a5719ad395fb03819445a8231a4349544d7d2d1f981fc`. Their model byte counts and SHA-256 values match the pinned 2B/4B files recorded below. A later rebuilt installer is a different artifact and requires its own packaging record.

## Historical 0.9.2 CPU observations

These observations were collected on 2026-11-02 on the Windows 11 x64 development machine described in [Windows validation](WINDOWS_VALIDATION.md), using the uncommitted working tree, a release-profile app test host and the CPU release worker unless the installed-app interaction is explicitly identified below. They are not other-PC or broad model-accuracy verification. Each result below covers one case.

The debug test host downloaded and verified the pinned Qwen3.5 2B and 4B files. The 2B file used in the following evaluations was 1,280,835,840 bytes, with SHA-256 `aaf42c8b7c3cab2bf3d69c355048d4a0ee9973d48f16c731c0520ee914699223`. The 4B file was 2,740,937,888 bytes, with SHA-256 `00fe7986ff5f6b463e62455821146049db6f9313603938a70800d1fb69ef11a4`.

The collected notice was read from a local archive opened read-only and imported into an isolated temporary store. A cached result was read after the worker stopped. The tests construct no HTTP client; they do not use an operating-system network block, so this is not proof of OS-enforced offline operation. Manual review remains necessary.

In a separate **installed-app interaction before the latest update**, a 2B file was registered as an external reference, selected and loaded on CPU, and the setup inference completed. Analysis of collected document ID 10 was cancelled after about 17 seconds; a second job completed in 121,481 ms and stored one result covering all 237 source characters. The summary omitted the source's “after December 9” qualification, so the completed job is not a semantic-quality pass. Compilation and Clippy ran concurrently; the elapsed time is not an idle performance benchmark. A read-only database inspection confirmed the cancelled and completed jobs, the external model reference, the stored result, database integrity and zero foreign-key violations (`.build-tools\logs\native-ai-runtime-before-update.json`). Native UI observation also confirmed saving a positive interest, one result for the literal Korean search `유고결석` submitted with Enter, and reading the longer document ID 5. The search used literal Unicode input; Korean IME composition was not tested. The app and worker were observed closed after the session. Network access was not disabled at the OS level. These observations do not establish behavior of the subsequently changed build.

After the catalog guidance was updated, the browser installation, cancellation, retry and selection scenario passed once each in Chromium and WebKit (2/2; `.build-tools\logs\ui-catalog-windows.txt`). Its IPC responses, model metadata and installation progress were mocked; this is a screen-flow check, not a real download, inference or installed-app verification.

The detailed reports contain source-derived notice content and remain local under `D:\Codex_Rhythm\.build-tools\ai-validation`: `2b-synthetic.json`, `2b-synthetic-recovery.json`, `2b-recovery-final-cache.json`, `2b-archived-10.json`, `4b-synthetic-recovery.json` and `4b-archived-10.json`. Do not commit or upload the source-derived reports. Test logs for the initial 2B runs are under `.build-tools\logs`; later test output and sampled memory CSV files are alongside the reports.

Sampled peak per-process working sets were about 4.36 GiB in the earlier 2B recovery run and 8.77 GiB in the 4B recovery run. The catalog's 5 GiB and 10 GiB values are estimates with headroom above these observations, not guaranteed maxima or sufficient total system RAM. A model download, checksum, protocol response or successful structural check alone does not prove usable semantic quality.
