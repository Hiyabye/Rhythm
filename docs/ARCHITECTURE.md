# Architecture

## Boundaries

Rhythm is a Korean-first, local-first modular monolith with one Tauri main window and one isolated AI worker. It is not a web service: no cloud backend, login service, telemetry, or localhost inference server is required.

```text
Svelte 5 / TypeScript
        │ Tauri invoke
Rust application (src-tauri)
  ├─ storage: SQLite settings, archive, revisions, user state and FTS5
  ├─ extensions: built-in registry and lifecycle
  ├─ archive: source catalog, native parsers, HTTPS and manual sync controller
  │     ├─ public Sogang sources → normalized archive records
  │     └─ app_data_dir()/resources/ → verified local files
  └─ intelligence: curated model manager, analysis queue and worker process owner
        ├─ app_data_dir()/models/ → verified managed GGUF files
        ├─ stored document revision → validated result → SQLite cache
        │ versioned JSON lines over stdin/stdout
rhythm-ai-worker (crates/ai-worker)
        └─ mistral.rs v0.9.1 (pinned release commit) → local GGUF
```

There are only two Cargo workspace members: the Tauri app and worker. v0.2 introduced the archive, v0.3 local intelligence, v0.4 deterministic personalization and schema 4, and v0.5 app lifecycle controls, in-process scheduled incremental collection, notifications and schema 5. Collection never waits for inference or writes AI results. Schema 5 adds proactive-operation state without rewriting released migrations. Native and cross-platform lifecycle/notification behavior, permission state and distribution remain unverified; the Linux distribution gate is described below.

## Application ownership and commands

`src/App.svelte` owns navigation, settings, nonblocking first-run AI setup and themes. `src/lib/ArchiveView.svelte` owns archive lists/search, Today recommendations and bounded recent-analysis previews; `DocumentReader.svelte` reads a stored revision and accepts document feedback; `SourceSettings.svelte` manages subscriptions/manual jobs; `PersonalizationSettings.svelte` owns profile, interests, learning controls and memory review. `AiSettings.svelte` manages models/preferences/queue; revision-keyed `AnalysisPanel.svelte` displays real results independently of the original reader. `ProactiveSettings.svelte` exposes lifecycle, scheduled-sync and notification controls/history. `src/lib/types.ts` mirrors Rust command payloads.

Foundation commands remain `get_snapshot`, `save_settings`, `set_extension`, and `worker_status`. `src-tauri/src/archive/mod.rs` adds:

- `archive_sources`, `archive_subscribe`, `archive_summary`: catalog, subscriptions and actual local counts.
- `archive_query`, `archive_document`, `archive_state`: search/list pages, a current or prior revision, and independent read/saved state.
- `archive_start`, `archive_cancel`, `archive_status`: admit, cancel and observe a manual job.
- `archive_retry_resource`, `archive_resource_image`, `archive_reveal_resource`: explicit downloads and integrity-checked local access.
- `archive_open_original`: explicit HTTP(S) navigation through the OS browser; no file, script or custom-protocol URL execution.

The proactive module provides `proactive_snapshot`, `proactive_save`, `proactive_history` and `proactive_clear_history`; lifecycle commands expose status and explicit close-to-background, hidden-start and login-registration updates. A macOS-only `notification_authorization` command queries UserNotifications without prompting; `notification_request_permission` requests alert/sound/badge permission only after explicit user action. Other targets return unavailable/unknown. `ProactiveSnapshot.notification_permission` remains an `"unknown"` placeholder; the settings UI uses the separate authorization command.

Notification delivery is platform-specific: macOS uses the async `mac-usernotifications` 0.3.1 sender and native UserNotifications activation response; Windows and Linux retain the Tauri notification plugin sender/action callback. Both activation paths emit `proactive://notification-clicked`; the main-window capability grants only Tauri event `listen` and `unlisten`, and `App.svelte` removes its listener at teardown. A one-shot snapshot activation covers clicks received before the UI subscribes. A sender handoff is recorded as attempted, not proof of OS display; macOS delivery is recorded as delivered only after the native activation response. Each macOS alert closes itself after 30 minutes, and the scheduler tracks at most 12 pending response waits, processing them independently of the delivery cycle; an ignored alert therefore cannot stall later scheduling or stop delivery. The observed synthetic macOS interaction described below is not live-source delivery evidence.

`AppState` owns an `Arc<Mutex<Store>>`, archive controller/client, extension registry, one shared Tokio-mutex-protected worker, model-install and analysis controllers, a transient command-operation owner and an AI mutation gate. SQLite guards are not held across network, worker or large-file hashing awaits; hashing uses `spawn_blocking`. Health snapshots use `try_lock` rather than waiting behind inference. Search and reader generation guards prevent stale responses from replacing newer views.

`intelligence/commands.rs` exposes `ai_snapshot`, install/cancel/register/remove/select/load/unload/restart controls, `ai_preferences`, `ai_analyze`, `ai_cancel`, revision-local results/jobs and bounded recent results. Additive `ai_cancel_operation` cancels command-owned preparation; `ai_diagnostics` reads transient per-job timing/count reports. Snapshots include operation/progress state and the current prompt/schema/configuration contract. Worker operations are serialized; model removal requires confirmation, no conflicting work, unloading and selection clearing. Analysis/results do not require the notice extension to remain enabled.

`intelligence/operations.rs` owns in-memory load/setup/register phases and cancellation independently of Settings component lifetime. Leaving and remounting Settings observes the same operation. Cancellation joins cooperative blocking verification or stops/reaps interrupted worker IPC before admission is released. Setup persists completion only after its real inference succeeds. This adds no database job kind or migration. Snapshot disk capacity is refreshed; physical RAM is labeled as physical capacity, not available loader memory.

Before `Store::open` can recover interrupted work, `core::lock_data_dir` obtains a process-lifetime OS file lock on `app_data_dir()/rhythm.lock`. A second owner of that data directory is rejected with a Korean diagnostic and normal exit before opening the store/worker; Tauri's setup-error panic is avoided. The OS releases the lock after process termination; startup does not infer ownership from an old file's mere existence. This complements the controller's in-process single-job admission and prevents concurrent instances from racing checkpoints or temporary resource files.

Rust owns persistence; browser previews do not substitute localStorage or simulate success. A startup or migration failure prevents launch rather than replacing user data. Theme changes are optimistic and revert on save failure; system mode follows OS preference. Energy profile controls app-open inference admission/residency and scheduled sync cadence only when the scheduler interval is set to automatic (`0`). Schema-4 profile, interests, feedback and learned evidence remain local; deterministic ranking does not depend on an AI model or inference result.

## SQLite schema 5 and upgrade compatibility

`storage/mod.rs` opens `app_data_dir()/rhythm.sqlite3` for `io.github.hiyabye.rhythm`, enables foreign keys, WAL and a five-second busy timeout, and applies ordered transactional migrations using `PRAGMA user_version`. A newer schema is rejected before changing journal mode. Migrations `001`–`004` remain unchanged; `005_proactive.sql` adds lifecycle/scheduler settings, per-source scheduler tasks and outcomes, notification baseline/dedupe/events and `sources.seed_complete`.

Schema 5 is opt-in by default: login launch, hidden start, close-to-background, scheduler and notifications are disabled. Baseline is initialized to the largest existing `document_revisions.id`, preventing pre-upgrade material from replaying as a new event. The candidate query excludes a document's initial revision when it is historical, but allows a later meaningful post-baseline revision even for a historically collected document. It skips meta-only revisions with unchanged title/body. Seed completion is initialized for complete historical imports or sources already containing a non-historical document; a partial old historical seed alone does not establish the incremental frontier. Event records reference document/revision identities rather than copying notice bodies. A durable dedupe ledger outlives bounded event history and history clearing, so clearing visible records does not enable repeat notifications.

Settings include scheduler enable/pause, scheduler interval automatic (`0`, default) or explicit 15–720 minutes, retry interval 5–120 minutes (default 15), notifications enabled (default off), sensitivity (`important`, `interested`, `all`), and optional local-wall-clock quiet hours (default disabled, 22:00–07:00). Automatic cadence follows Eco/Balanced/Performance at 60/30/15 minutes. Explicit intervals, including 60 minutes, use the exact selected value. Notification thresholds: `important` requires preferences and personalized score ≥18; `interested` requires an explicit-interest match; `all` accepts otherwise eligible items. Negative feedback and negative-interest matches reject every mode. The per-source tasks exist only for supported, subscribed sources while the archive extension is on. Scheduled runs use incremental sync only.

The event state machine is `pending → claimed → attempted | deferred | failed`, with `delivered` after notification action confirmation and `suppressed` for policy/source rejection. Claims have a five-minute recovery lease, delivery attempts cap at three, and failed delivery retries use configured delay with capped exponential backoff (maximum four hours). At most three distinct notification attempts are allowed per ten minutes; candidate discovery and delivery are bounded. `attempted` means the sender accepted a handoff, not that the OS displayed it. macOS uses the async `mac-usernotifications` 0.3.1 sender and native activation response; Windows/Linux use the Tauri notification plugin and action callback. The macOS authorization query/request is separate from delivery and is used only after explicit user action. Quiet-hour deferral uses local wall time and does not consume an attempt; native isolated testing observed three deferred synthetic events at zero attempts. This does not establish live-source delivery.

`002_archive.sql` adds only implemented archive structures:

| Structure | Ownership and purpose |
| --- | --- |
| `sources` | Stable catalog identity, persisted subscription, support flag, last attempt/success/error, progress counters, resumable page and history completion. |
| `documents` | Current canonical identity/metadata and sanitized HTML/normalized text, keyed uniquely by `(source_id, external_id)`. |
| `document_revisions` | Append-only meaningful content snapshots, including original fetched JSON/HTML representation, reader content and hash. |
| `document_state` | Read/saved flags and timestamps, independent of fetched content. |
| `resources` | Revision-associated image/attachment metadata, download state, local path, size, MIME and SHA-256. |
| `documents_fts` and triggers | FTS5 trigram index over current title and normalized body text. |

The schema-1 upgrade keeps theme, energy, interests and extension preferences. Catalog refresh updates definitions without replacing subscriptions or checkpoints. Previously running source jobs become `interrupted` on reopen and retain their page. Running AI jobs become retryable failures; interrupted downloads become cancelled/recoverable while retaining partial bytes and validators. Pending AI jobs remain persisted and are drained on later analysis admission, not by loading a model at startup.

`003_intelligence.sql` adds four tables without modifying archive content:

| Structure | Ownership and purpose |
| --- | --- |
| `ai_models` | Managed/external ownership, file identity, pinned provenance, download state/progress, resume ETag and errors. |
| `ai_preferences` | Separate singleton: selected model, setup completion, explicit/recent policy, automatic session limit and output token limit. |
| `ai_jobs` | Persistent attempts, priority/status/error/duration and full semantic identity; a partial unique index prevents duplicate active work. |
| `ai_results` | Validated JSON, provenance, revision/cache identity, duration and partial-processing counts. Completion and result insertion are transactional. |

Jobs/results use the composite `(revision_id, document_id)` foreign key. Results retain artifact provenance without depending on installed inventory, so model deletion does not delete analyses. A failed or cancelled regeneration leaves previous successful output intact. Current/history lookups are separate from authoritative active-job queries; bounded terminal history is not used to establish deletion safety. Revision-local job queries independently include all active attempts plus the requested terminal-history limit (20 for the reader), so newer completed attempts cannot hide older pending/running work.

### Schema 4 personalization and ranking

`004_personalization.sql` preserves the legacy `settings.interests` text and imports its initial terms into structured rows; equivalent known Korean/English labels share a normalized identity and aliases. The legacy value is cleared only by an explicit personalization reset. `documents.last_revision_at` is populated for documents with multiple revisions and updated only when a new meaningful revision is committed.

| Structure | Ownership and purpose |
| --- | --- |
| `personalization_profile` | Optional university, department and study level; behavioral-learning switch. |
| `personalization_interests` | Explicit or learned topic, normalized identity, aliases, priority (1–5), positive/negative polarity and evidence summary. |
| `personalization_feedback` | Idempotent current document-level feedback (`interested` / `not_interested`), reversible without creating duplicate rows. |
| `personalization_evidence` | Bounded, deduplicated save/positive-feedback events per topic, document and event kind. |
| `personalization_activity` | Monotonic interaction sequence; refreshes learned-memory summaries after changed feedback/save state and at most daily for evidence expiry. |
| `personalization_suppressed` | Activity-sequence baseline preventing deleted/removed inferred interests from reappearing from unchanged prior events. |
| `source_extensions` | Maps source identities to built-in extensions; missing or disabled extension preferences remove those sources from recommendation candidates, not from the archive. |

Saving and explicit positive feedback are the only behavioral evidence; opening, reading, searching, and negative document feedback do not create topic memory. Learning requires evidence on at least two different documents. Evidence older than 180 days is pruned; learned memory is recomputed after changed feedback/save state or at the next snapshot after a day for expiry, rather than rescanning on every view. A save and positive feedback are separate deliberate signals, but each is unique per topic/document/kind; repeated toggles update or remove existing evidence. Negative feedback adjusts only that document. It becomes a bounded per-item penalty and never suppresses the source or topic. Explicit interests are not overwritten by learned evidence. Canonical explicit aliases also prevent creation of duplicate learned topic rows. The user can edit, promote, or delete memories, disable learning, or reset all personalization; removal records a sequence baseline, so old retained activity alone cannot recreate the same memory.

Evidence topics are derived from title and original source category only, limited to 32 terms per action and excluded against a small Korean/English sensitive-term list before persistence. This is a lexical safeguard, not semantic classification; explicit user-entered interests remain under the user's control. It does not read body text, personal correspondence or AI summaries.

`Store::personalization_recommendations` is deterministic and does not read AI results or call the worker. Each matching explicit topic contributes `12 + 3×priority` points (15–27); a learned topic contributes at most 6. Explicit negative topics subtract their matching amount. Current positive document feedback contributes +24 for 30 days, +12 through day 180, +6 through day 365. Negative document feedback caps the final item score at −40 through day 180 and −20 through day 365; it does not hide the item. Saved items add +8, subscribed sources +2, and exact university/department/study-level text matches +4/+8/+2. A non-historical publication gains 0–6 points over the first 30 days; a recently collected older or undated non-historical record adds +2. A meaningful revision to an older/historical item in the last three days adds +4. Historical initial backfill gets no freshness boost. AI dates, categories and summaries are excluded from scoring: source-supported deadline validation is not yet available, so analysis cannot create false urgency.

Candidates come from bounded indexed slices: up to 500 latest published, 250 recent non-historical collections, 250 meaningful updates, 100 saved, 100 feedback, 250 source matches, 250 category matches and 250 FTS matches (at most 1,950 before deduplication). At most 32 terms are matched against the full FTS5 index for scoring, without copying full bodies; the result exposes only a 320-character body prefix per candidate. The query joins only enabled/mapped extensions. Today requests eight rows; scores are not persisted. Matched signals emit their explanation from the same scoring branch. Cold-start items receive no personalized-score claim. Ordering is score descending, then publication timestamp and stable document ID descending. The first pass limits one source to at most half the requested list; a second pass fills remaining slots while preserving score order. Existing archive FTS5/indexes and bounded SQL queries avoid loading the archive into Svelte or running inference per record.

One measured macOS debug-profile recommendation call took 335.96 ms on a synthetic 2,003-document database with 32 explicit interests; fixture creation was outside the timer. This is a single local observation, not a release-build or user-archive performance guarantee.

The Store API is exposed through `personalization_get`, `personalization_save_profile`, `personalization_save_interest`, `personalization_remove_interest`, `personalization_set_learning`, `personalization_reset`, `personalization_get_feedback`, `personalization_set_feedback` and `personalization_recommendations`. Recommendation results and personal evidence are never sent over the network or copied into diagnostics.

`Store::upsert_article` commits the current document, revision, user-state initialization and resource references transactionally. Identity includes the source, so equal article IDs on different boards do not collide. Hash input includes canonical URL, title, author, category, publication date, sanitized body/text and resource identities—not volatile view counts, collection time or raw response churn. An unchanged check updates validators/check time without another revision. Revisions never replace read/saved state. Old snapshots and their resource references remain selectable. Downloaded resources are reused only for the same document, URL and role. This does not detect a remote binary overwritten at an unchanged URL; explicit retry can replace that revision's resource reference. Immutable binary revisioning is not claimed.

Original responses are stored as revision data, not injected into the webview. A parse, network or write failure does not replace the last good article with an error page. There are no deletion/tombstone semantics or automatic retention cleanup in v0.2.0.

Database size in Settings counts the database plus WAL only. Archive summaries separately total referenced downloaded resource bytes, deduplicated by local path. Neither is a complete filesystem usage or backup report. Copying only an active WAL database is not a safe backup design; backup/restore remains unimplemented.

## Korean local search

`storage/archive.rs::archive_query` searches the title and normalized article body, never page navigation/footer text. Whitespace-separated terms are combined with AND; each term may match either title or body. Terms of three or more Unicode characters provide quoted trigram MATCH candidates. Parameterized, escaped literal LIKE checks enforce substring semantics for every term and provide the one/two-character Korean fallback. User punctuation is data, not an FTS query language. Embedded NUL is rejected before constructing SQLite LIKE/FTS input; tabs/newlines remain term separators. Limits are 512 query characters, 32 terms and at most 100 rows per backend page; the UI uses 30.

Results have deterministic publication-date/ID order, source/category filters, saved/unread filters and a nearby plain-text excerpt. `Highlighted.svelte` escapes regex syntax and renders text/`mark` nodes, not HTML snippets returned by SQLite. Search and user-state operations remain available when offline or when the notice extension is disabled. Short-query LIKE scans are an intentional correctness tradeoff. The reproducible ignored 5,000-record benchmark measures correctness and warm debug timings rather than enforcing fragile speed thresholds; observed medians were about 11 ms for inbox, 17 ms for short Korean and 52 ms for broad mixed queries. These do not establish release/native-IPC/cold-cache performance; see the roadmap for the workload and measurements.

## Manual and scheduled synchronization; app lifecycle

`archive/sync.rs::Controller` admits one archive or resource-retry job at a time. Admission checks the enabled extension and supported subscribed sources under the same store lock used by disabling. Sources run sequentially. One source's failure is recorded independently and does not discard completed documents or prevent the next selected source from running.

- **Historical:** begin at persisted `next_page`, follow public pagination, deduplicate pins/article identities, and checkpoint only after article retrievals on that page succeed. Existing text is not fetched again unnecessarily, but pending resources are resumed. Cancellation retains committed text/files and the last safe page. `history_complete` becomes true only after the last public page is reached; repeated/empty unexpected pages and safety/test limits do not claim completion.
- **Incremental:** start at page one, recheck recent pages and pins with saved ETag/Last-Modified validators where available, and create revisions only for meaningful changes. The minimum recheck window is three pages. New-record discovery continues beyond that window until a page of known regular records establishes the archive frontier; repeated pins do not establish it. This prevents a burst larger than three pages from being silently lost.
- **Initial incremental seed:** if the source has no local documents, fetch at most the first three pages as historical records. Do not inflate the new-notice count or mark full history complete. Historical import can later fill the remainder.
- **Scope limit:** incremental sync is not a complete audit of all old edits, and completed historical import is not a recurring whole-history rescan.

Per-source state records attempt/success timestamps, errors, per-attempt discovered/archived/failed counts, cumulative page and completion. Counters reset for each historical or incremental attempt, so retried failed IDs are not double-counted as lifetime discoveries. HTTP 304 updates article check time and still resumes its pending resources. A resource outcome distinguishes recorded nonfatal download failure from success; normal article ingestion can retain text while explicit retry reports the actual failure. Global status reports current source/page/message for UI polling. Failed or unsupported resources are distinct from failed article retrievals: useful text remains readable with `missing_resources`. Completing source pagination does not promise that every referenced resource was downloaded.

The scheduler is an in-process Tokio task awakened every 15 seconds, not an OS timer or service. When enabled and unpaused, it reconciles tasks for supported subscribed sources under the enabled extension and runs due source jobs sequentially using incremental sync. Interval `0` means automatic cadence from the energy profile (Eco/Balanced/Performance: 60/30/15 minutes); nonzero intervals, including 60, are exact. Retry/task/scheduler outcomes, next-run state and errors persist in SQLite. Work is cancelled if scheduling is disabled/paused, extension/source subscription changes, or app shutdown begins. The process does not wake a sleeping computer; timers and jobs run only while the app process and OS are running. On wake/restart, due work can be resumed by subsequent scheduler cycles, but sleep/wake timing and native behavior are not verified. Autostart is explicit and reconciled with OS state on user action; startup does not silently register it. Hidden launch applies only to OS login launch. Close-to-background hides the window only when tray installation succeeded; otherwise closing quits.

Notification discovery is post-archive event processing. New records created by a historical initial seed are historical and excluded; migration establishes a revision ceiling so archived rows are not replayed after upgrade. New meaningful later revisions are candidates, including revisions to an older/historical notice. Candidate score/source/negative-interest policy is rechecked before delivery, and disabled/unsubscribed source or policy rejections are persisted as suppressed with a reason. Denied or not-yet-determined macOS permission prevents delivery attempts; status-query/request code is implemented for macOS only. In an ad-hoc-signed isolated debug app, the user granted the native permission prompt and a later authorization-status read returned authorized. macOS sends digests asynchronously through `mac-usernotifications` 0.3.1; Windows/Linux retain the Tauri notification plugin. The sender handoff is not proof of display; a native activation response is required to record delivered events. Other platforms report authorization unavailable/unknown and remain unverified. Notification payload text includes the source name and title. No AI request is triggered.

Observed synthetic macOS behavior: the user saw and clicked a test notification, Accessibility Inspector showed a matching archived notice title/body, and SQLite recorded one event delivered with attempt 1. After app restart, the single dedupe row remained and no duplicate was observed. A separate quiet-hours check deferred three synthetic events with zero attempts; after simulated quiet-hour end, the user saw and clicked the grouped alert, Accessibility Inspector showed its history, and SQLite recorded two included events delivered while the third remained deferred by the rate limit. These isolated synthetic results do not verify notifications generated from live-source data or repeatable production delivery. An isolated native scheduler test ran with the window hidden: two supported subscribed sources each archived one article, but a temporary debug-only test cap (one page and one detail per source) caused both source tasks to record failure and left history incomplete. The sources ran seconds apart while a synthetic alert awaited response. This demonstrates bounded execution and partial-archive/failure semantics only, not successful full scheduled sync; the temporary override has been removed and production has no debug testing override. A separate offline scheduler attempt persisted a 15-minute source retry backoff and left SQLite integrity `ok`; this is failure-state evidence, not successful scheduled collection. Extension disable/re-enable testing with the app stopped between retained both subscriptions and all 13 stored documents; SQLite integrity was `ok`. An isolated macOS lifecycle check observed close-to-background hiding, reopening the hidden window and normal app-menu quit (exit 0); the bounded scheduler run above also executed while the main window was hidden, so scheduled collection does not require a visible window. Login registration was simulated under a separate temporary HOME: the native login item plist was created and removed, and `--autostart` with hidden-start enabled produced zero windows. This is isolated registration/startup-path evidence, not a real user login test. The bounded live/offline archive test imported 10 documents, downloaded 12 resources, recorded 2 missing resources and 8,149,764 local bytes; all sources were deliberately partial. It verified local state after offline database reopen and does not establish full-history coverage or general source reliability.

`sogang_notices` remains opt-in and separate from subscriptions. Disabling hides source controls and rejects new manual work; scheduled tasks reconcile disabled when the extension is off. Existing archive/search/read/saved functionality remains available. Exit signals scheduler and archive cancellation, waits for work to settle, and then stops the AI worker.

## Transport, resources and safe rendering

`archive/network.rs` uses native Reqwest/Rustls. Automatic requests require exact approved HTTPS hosts/routes on port 443. URLs with credentials, fragments or unsafe encoded path separators are rejected. DNS answers must be public and are pinned for the connection; proxies and automatic redirects are disabled. At most three same-origin redirects are followed by the sync policy layer, with static URL/DNS/TLS checks and robots authorization before each hop. Transport returns redirect targets rather than following them implicitly. Only the exact approved main, Computing and Engineering HTTPS routes are eligible. This narrow download policy is separate from resource/link metadata and from explicit browser navigation. Safe HTTP(S) resource references are retained as metadata, so an old HTTP image does not discard otherwise useful article text. Automatic HTTP or unverified-host downloads remain unsupported; a storage regression covers mixed-content metadata and rejects credential-bearing URLs.

Requests are paced at least 650 ms apart. Source `robots.txt` is checked before collection; the most applicable allow/disallow rules and supported crawl delays are applied, with delays above 60 seconds rejected for manual handling. Robots requests use a plain-text Accept header; Computing otherwise returns HTTP 406. HTML error pages and malformed/nonfinite/negative/over-60-second crawl delays fail closed. Wildcard/end-anchor matching considers later possible matches instead of permitting a disallowed path after a greedy first occurrence. There are at most three attempts for transient errors, short bounded backoffs, connect/request/attempt deadlines and cancellable waits/reads. HTTP 429 stops with an actionable message rather than hammering the site. No login, access restriction or anti-bot bypass is used.

### TLS chain completion

The main university host omits its intermediate chain. `archive/tls.rs` supplies two bundled public **untrusted intermediate candidates only for exact `www.sogang.ac.kr`**, then delegates certificate and handshake-signature checks to WebPKI. The trusted root store remains exactly Mozilla's `webpki_roots`; hostname, validity, signature, usage and trusted-root path checks remain mandatory. Computing receives no completion candidates. There is no invalid-certificate acceptance, new root, system-trust change or automatic CA download. Certificate provenance/fingerprints and fixed-time negative tests are documented in `archive/certificates/README.md`.

### Resource ownership

Limits are 4 MiB per list/article response, 10 MiB per inline image, 20 MiB per attachment and 256 MiB of completed resource response bytes per job. Received response bytes are charged before validation/disk persistence and the next response is capped to remaining budget. Bytes from incomplete transport failures/retries are not exposed by the transport contract and are not included in that counter. Robots responses are capped at 64 KiB; production pagination has an explicit 100,000-page safety ceiling. Developer test budgets are reported as `limited`, never complete history.

Resource URLs, original filenames, kind, MIME, bytes, state and SHA-256 are retained. Files use generated `resources/<sha256>.<validated-extension>` paths, not remote filenames. Writes go through a temporary `.part` file before the completed path is referenced in SQLite. Raster images require PNG/JPEG/GIF/WebP signatures; attachment extensions are restricted, active web types are rejected, and PDFs require a PDF signature. This is format/transport validation, not antivirus scanning. Files are never automatically opened or executed.

Local access canonicalizes containment, bounds size and verifies the stored SHA-256. A retry repairs corrupt existing bytes; a failed refresh preserves a verified last-known-good copy. Failed, oversized or unsupported resources retain explicit states and can be retried by user action. There is no remote-image fallback and no guarantee that external, deleted, restricted or oversized resources can be archived. Cleanup of unreferenced/partial files and total-storage quotas are deferred.

The Rust sanitizer keeps a limited structural HTML subset, strips scripts/iframes/forms/styles/event attributes and emits image resource references without `src`. `DocumentReader.svelte` reconstructs a second restricted DOM, requests only integrity-checked local raster data URIs, and intercepts HTTP(S) links for explicit OS-browser navigation. Missing/corrupt images become placeholders; known local-integrity failures override persisted download labels and expose repair actions. A render-local promise cache validates repeated images only once; disposed/stale renders stop admitting subsequent image reads. Legacy attachment-role inline images are accepted only after the same backend local-integrity/raster/10 MiB checks. A failed automatic read-state write cannot suppress retrieved content. The original fetched representation is never rendered directly. CSP remains a further layer, not the sanitizer's replacement.

## Managed models and download boundary

`intelligence/models.rs` owns curated downloads independently of university transport. `catalog.json` pins Unsloth Qwen3.5 2B/4B/9B Q4_K_M repository revisions, filenames, byte sizes and SHA-256 values. Catalog presence and downloaded integrity are not runtime support. The exact 2B/4B artifacts are marked `verified` with an explicit macOS Apple Silicon/Metal qualification after one useful synthetic scholarship analysis each; 9B remains experimental, not downloaded or tested. Ordinary one-click installation rejects entries not marked `verified`. This status does not verify CPU/CUDA or other platforms. See [AI evaluation](AI_EVALUATION.md) for exact artifacts, measurements and limits before changing support claims.

Downloads use HTTPS on exact approved Hugging Face/CDN hosts, public DNS answers pinned per hop, normal TLS validation, no proxy, no automatic redirect following and at most five reviewed redirects. This hosting allowlist is not permission to relax the separate notice transport. Transfers have connection/read/total limits, bounded expected bytes and a disk check reserving 1 GiB beyond the remaining artifact. Retry is explicit, not an unbounded loop.

Managed paths are generated as `models/<sha256>.part` and `models/<sha256>.gguf`. Safe resumption requires a strong ETag, `Range`/`If-Range`, exact `Content-Range`, matching validator and expected remaining size. A full `200` response restarts rather than appends. Actual partial-file length overrides stale progress; invalid ranges or full-file hashes discard unusable bytes. Complete partial files can be verified offline. Files flush/sync and pass bounded GGUF preflight, exact size and committed SHA-256 checks before atomic rename and installed-state persistence. Interrupted installation preserves other models.

External registration references a canonical absolute `.gguf` path without copying. Preflight currently allows GGUF v2/v3 `qwen3` and `qwen35` metadata; this is not exhaustive tensor/tokenizer/runtime validation. Registration computes full SHA-256, while loading/inference must still succeed. Unregister never deletes external bytes. Managed deletion checks containment/symlink escapes and leaves documents/results intact. It removes ancillary partial files before weights, records conservative `missing` inventory before irreversible unlink and reconciles failures. A failed removal restores selection only if the previous artifact remains installed; no filesystem/SQLite atomic transaction is claimed.

Loading and uncached analysis still verify the complete model file. The approved macOS aarch64-only `sha2` assembly feature accelerates hashing without replacing it with metadata, sampled bytes or cached trust.

## Worker ownership and IPC

The parent locates the bundled worker beside its executable, launches it inside Tokio, pipes stdin/stdout, drains stderr in fixed 4 KiB chunks and suppresses a separate Windows console. The child is kill-on-drop. Malformed typed health/version/ID/framing responses terminate and reap it rather than reporting healthy. A crash does not remove archive/settings access; explicit restart and subsequent load/inference can start a replacement.

Protocol v1 remains serial, ID/version-matched UTF-8 JSON Lines, maximum frame 1 MiB. Analysis negotiates the optional `analysis_json_v1` capability before sending that infer output mode; absent mode preserves generic text/setup behavior. A static closed worker schema constrains types, enums and at most six compact facts, with explicit grammar-EOS termination. Unsupported legacy workers receive no unknown parameter, and their ordinary pipe remains usable. All parent source validators and one bounded repair remain; grammar does not guarantee semantic correctness. Additive `load` and `unload` methods join `ping`, `status`, `infer` and `shutdown`:

```json
{"version":1,"id":1,"method":"load","params":{"model_path":"/absolute/model.gguf"}}
{"version":1,"id":2,"method":"infer","params":{"model_path":"/absolute/model.gguf","prompt":"분석 요청과 인용된 데이터","max_tokens":1024}}
{"version":1,"id":3,"method":"unload"}
```

At most one model and sequence are retained. Switching drops the old model first; parent unload reaps/restarts an empty worker to reclaim process memory. Cancellation persists job state before dropping the pending request and reaping its process; a late serial response is never reused for another request. Ordinary lifecycle, load and inference deadlines are 8, 180 and 600 seconds respectively. Exit signals maintenance/download/analysis cancellation, waits without a SQLite guard, and shuts down the worker. Long command-owned loading/setup inference also observes explicit operation cancellation and exit cancellation. Their transient phases include verification, worker waiting/loading, setup and cleanup; these are application progress, not GPU-kernel utilization.

mistral.rs stays only in the worker, pinned to v0.9.1 release commit `11f255058573e085afe0a149f8a19cbd39aa1200`: the inspected 0.8.1/0.9.0 GGUF routes lacked `qwen35`, while this release adds text-only Qwen3.5 loading without a projector. Local loading uses embedded metadata, no remote tokenizer ID or authentication token. Stdout remains protocol-only, upstream diagnostics go to stderr. Direct Cargo builds default to CPU; Metal/CUDA builds attempt a clean CPU fallback on returned accelerated-load errors and report loaded versus compiled backend separately. These paths require per-artifact/backend verification, not merely compilation. See the [worker README](../crates/ai-worker/README.md).

## Analysis, validation and cache

`intelligence/analysis.rs` reads a selected local revision through `Store::document`, never refetches the university page and never opens binary attachments. One persistent queue serializes inference. The default is explicit requests; opening an article only retrieves existing results. Cached lookup occurs before model-file inspection or worker launch. Pending/running semantic duplicates share an attempt; failed output is not a trusted result.

Cache identity is document/revision + task + exact artifact SHA-256 + prompt version + output-schema version + hash of output-affecting configuration. Configuration includes output token limit, source bound, selector/evidence encoding versions, output-affecting prompt rules, clock-validation rules, constrained-decoding mode, thinking, deterministic sampling and the one-repair-attempt policy. Current prompt version is **3**, selector identity is **head-tail-keywords-v4**, and stored output schema remains **1**. New revisions/model/prompt/configuration produce distinct keys; older results remain readable with provenance but cannot satisfy a newer semantic key. Recovered pending attempts are checked against the current prompt/schema/configuration before inference; obsolete attempts fail with retry guidance instead of mislabeling output. No source metadata or user state is overwritten. History has no automatic retention/garbage collection yet.

Stored schema 1 output is strict JSON: `short_summary`, `summary`, central eight-category `category`, qualitative `uncertainty` and `facts`. Facts contain `kind`, `label`, `value`, exact `evidence`, nullable ISO `date` and qualitative uncertainty. Allowed fact kinds are deadline, event date, eligibility, documents, application method, link and action. Prompt-v3 supplies selected source-owned passages as explicit `{id,text}` objects. Generation ingress accepts exactly `kind`, `label`, `value` and integer `evidence_id` per fact, rather than legacy generated quotations or model-supplied dates/uncertainty. The backend resolves the reference to exact archived text and supplies derived fields before strict stored-schema validation. Historical schema-1 output remains readable. Invalid references, duplicate evidence forms, unknown/missing fields, invalid categories, malformed/empty/oversized/repetitive output, reasoning/control tokens, unsupported evidence and unsafe/ungrounded links are rejected.

For date facts, normalization is derived deterministically from a uniquely identifiable explicit date in the extracted value that also appears in its source passage, not from an LLM-proposed ISO field. Date matching preserves digit boundaries and checks claimed clock times against the corresponding source date/time, rather than borrowing an unrelated clock elsewhere in a multi-date passage. Missing years, multiple explicit dates, abbreviated calendar ranges and ambiguous/missing dates stay null; non-date facts cannot acquire dates from incidental passage content. Missing per-fact uncertainty defaults to unknown except for a mechanically verified literal date. Source occurrence and qualitative uncertainty are not proof of semantic entailment or calibrated factual confidence.

One schema/grounding failure permits one bounded repair attempt with validation feedback, the same bounded source and the same output limit. A second invalid output fails the attempt without replacing prior good results; runtime errors do not cause an unbounded retry loop. Cancellation covers both generations and reaps the worker before pipe reuse.

The worker receives a fixed system instruction and JSON-quoted untrusted source data, no tools or application capabilities. Generated fields render as escaped Svelte text, never reader HTML. There are no model-driven commands, preference changes, downloads or external actions.

Input is intentionally bounded: exact title/body ranges are selected from the head, tail and important passages within 18 KiB including explicit-ID objects and JSON escaping, inside a 24 KiB full prompt. Selector v4 admits exact repeated passage text only once when the complete input exceeds that budget; full-fit input retains every occurrence. Structural pipe-delimited table rows receive separate evidence units, while ordinary passages prefer sentence/line boundaries with a 500-character hard bound and numeric-date protection. Selected ranges remain in source order; omitted ranges are not joined into rewritten source text.

Output is bounded to 1–4096 tokens; application preferences allow 128–4096, default 1024. Long documents record `partial`, actual selected `processed_chars` and `total_chars`; the reader warns that omitted intervals may contain dates/requirements. This is not chunk-and-merge or complete long-document understanding. No PDF/HWP/DOCX extraction or vision is performed.

Analysis diagnostics are local, transient stage timings and typed worker metrics, with at most 20 terminal reports retained in memory and no source/generated text. They separate retrieval, integrity, preparation, worker wait, inference, validation and persistence where observed. Per-request loading/reuse is distinct from historical `load_ms`; upstream token/engine timing is not end-to-end latency. Missing legacy metrics remain unknown. The UI recovers from transient read errors and warns when a stored result differs from the current prompt/schema/configuration contract.

## Energy policy and process lifetime

`intelligence/maintenance.rs` checks every five seconds while the app is alive; this app-open AI admission is separate from the proactive scheduler. Optional `recent` processing requires completed setup, an installed selected model and a focused main window. After acquiring the AI admission gate, it reads current preferences and considers at most 20 eligible latest revisions ordered by revision collection time after session startup. Initial historical backfill, startup history and revisions with any prior attempt are excluded. Historical archives are never scanned wholesale. Attempts are bounded per session, including failures/cancellations.

| Profile | Automatic analysis | Idle loaded-model residency | Scheduled sync cadence when interval is automatic |
| --- | --- | --- | --- |
| Eco | None; explicit requests only | 30 seconds | 60 minutes |
| Balanced | Up to `min(automatic_limit, 3)` | 120 seconds | 30 minutes |
| Performance | Up to `min(automatic_limit, 20)` | 600 seconds | 15 minutes |

Observed active work, a busy operation gate and model/job changes reset residency. A transient operation generation counter records brief AI operations between maintenance polls. Battery status is not separately detected; Eco conservatively disables automatic AI processing on AC and battery. Scheduled collection is separate and does not detect battery state. Neither path is an OS wake timer; no work runs while the computer is asleep or after the application process exits.
