# Architecture

## Boundaries

Rhythm is a Korean-first, local-first modular monolith: one Tauri main window and, while a model is loaded, one supervised `llama-server` child process. It is not a web service. There is no cloud backend, login service or telemetry, and the local inference server is reachable only by Rhythm (a private Unix socket, or loopback with a per-launch key). Remote inference is an opt-in client of a user-configured OpenAI-compatible HTTPS endpoint: the local engine is the default, the user supplies the endpoint and key, and only public notice analysis text is sent.

Supported platforms are macOS Apple Silicon and Windows 11 x64. Platform code sits behind `cfg(target_os = "macos")`/`cfg(windows)`; both platforms share the bundle identifier `io.github.hiyabye.rhythm`, the schema and the backup format. The app data root (`<data>` below) is `app_data_dir()` on macOS and `app_local_data_dir()` (non-roaming `%LOCALAPPDATA%`) on Windows.

```text
Svelte 5 / TypeScript
        │ Tauri invoke
Rust application (src-tauri)
  ├─ storage: SQLite settings, archive, revisions, user state, FTS5, AI, personalization, proactive state
  ├─ extensions: built-in extension list and on/off registry
  ├─ archive: source catalog, native parsers, constrained HTTPS, sync controller
  │     ├─ public Sogang sources → normalized archive records
  │     └─ <data>/resources/ → verified local files
  ├─ studium: fixed reading-room catalog, pure parsers, manual controller, memory-only seat results
  ├─ proactive: in-process scheduler and notifications
  └─ intelligence: curated model manager, analysis queue, local supervisor, optional remote engine
        ├─ <data>/models/ or a chosen folder → verified managed GGUF files
        ├─ stored document revision → validated result → SQLite cache
        │ local: HTTP/1.1 over <data>/run/llama.sock, or 127.0.0.1 + per-launch key
        └─ remote (opt-in): user-configured HTTPS /v1/chat/completions or /v1/embeddings
one llama-server process per loaded model (bundled resources, pinned upstream build)
  ├─ macOS: llama/metal/ → Metal, or CPU after a failure
  └─ Windows: llama/vulkan/ (NVIDIA only) or llama/cpu/
```

The Cargo workspace has one member, the Tauri app (`src-tauri`). Collection never waits for inference or writes AI results. Release builds are ad-hoc signed (macOS) or unsigned (Windows) by policy; updates are authenticated separately by the Tauri updater signature, and the updater stays disabled in builds without a compiled-in public key.

## Application ownership and commands

`src/App.svelte` owns navigation, the settings panes (one rendered at a time; the last pane is kept while the app runs), nonblocking first-run AI setup and themes. `src/lib/extensions.ts` maps each extension to the nav items and settings panes it adds; the shell shows only the core entries (오늘; 확장 기능, 일반, 데이터 및 정보) plus those of enabled extensions, and falls back to Today or 확장 기능 when the current one goes away. In `src/lib/`: `ExtensionSettings.svelte` is the extension on/off list; `ArchiveView.svelte` owns lists, search, Today (its recommendations and week pane each follow their extension, with an empty state when neither is on) and recent-analysis previews, hiding stored AI output while `ai` is off; `DocumentReader.svelte` reads a stored revision and takes document feedback; `SourceSettings.svelte` manages the subscriptions and jobs of one source extension's sources (with `CybercampusSettings.svelte` for the eClass login); `CybercampusTasks.svelte` is the 과제·마감 page, shown while the `cybercampus` extension is on; `CalendarView.svelte` is the 캘린더 month page (open eClass deadlines, current AI reference dates and the user's todos, with todo editing for the selected day), rendered by `ArchiveView.svelte` so it shares the week pane's deadline and AI-date rules and the reader; `PersonalizationSettings.svelte` owns profile, interests, learning and memory; `AiSettings.svelte` manages models, preferences and queue; revision-keyed `AnalysisPanel.svelte` shows results independently of the reader; `ProactiveSettings.svelte` exposes lifecycle and scheduler controls (`part="background"`) or notification controls and history (`part="notifications"`); `Popover.svelte` anchors a native light-dismiss popover to its `popovertarget` button and `Hint.svelte` uses it for row explanations. `types.ts` mirrors Rust command payloads. `platform.ts` picks platform wording from the WebView user agent (never for security decisions).

Commands:

- Foundation: `get_snapshot`, `save_settings`, `set_extension`, `worker_status`.
- Archive (`archive/mod.rs`): `archive_sources`, `archive_subscribe`, `archive_source_groups`, `archive_set_group`, `archive_summary`; `archive_query`, `archive_ranked_query`, `archive_document`, `archive_state`; `archive_start`, `archive_cancel`, `archive_status`; `archive_retry_resource`, `archive_resource_image`, `archive_reveal_resource`; `archive_open_original` (explicit HTTP(S) navigation in the OS browser only).
- Cybercampus (`archive/cybercampus/mod.rs`): `cybercampus_status` (saved login ID, rejection flag, current courses; never the password), `cybercampus_save_login` (logs in first and stores the login only when eClass accepts it; refused while a sync runs), `cybercampus_forget_login`, `cybercampus_tasks`.
- Calendar (`commands.rs`): `calendar_todos` (an inclusive local-day range of at most 62 days), `calendar_create_todo`, `calendar_update_todo`, `calendar_set_todo_done`, `calendar_delete_todo`; writes are refused while the `calendar` extension is off.
- Studium (`studium/commands.rs`): `studium_snapshot`, `studium_save_preferences`, `studium_set_view_room`, `studium_start`, `studium_status`, `studium_cancel`. Only `studium_start` starts school requests; snapshots/status are local reads, and saving or changing the displayed room never starts a job.
- Proactive: `proactive_snapshot`, `proactive_save`, `proactive_history`, `proactive_clear_history`, lifecycle status and explicit close-to-background/hidden-start/login updates, `notification_authorization` (status, no prompt) and `notification_request_permission` (explicit user action only).
- AI (`intelligence/commands.rs`): `ai_snapshot`; install, cancel, register, remove, select, load, unload and restart; `ai_preferences`; `ai_analyze`, `ai_cancel`; revision-local results and jobs; bounded recent results; `ai_cancel_operation` for command-owned preparation; `ai_diagnostics` for transient timing reports; classification preferences and results (`ai_classification_preferences`, `ai_classifications`, `ai_classification`); `ai_choose_model_directory` and `ai_reset_model_directory`; remote engine configuration (`ai_remote_status`, `ai_remote_key`, `ai_remote_key_clear`, `ai_remote_test`).
- Personalization: `personalization_get`, `_save_profile`, `_save_interest`, `_remove_interest`, `_set_learning`, `_reset`, `_get_feedback`, `_set_feedback`, `_recommendations`.

`AppState` owns an `Arc<Mutex<Store>>`, the archive controller and client, the Studium controller, the extension registry, one shared Tokio-mutex worker, model-install and analysis controllers, the remote credential/transport owner, a transient operation owner and an AI mutation gate. SQLite guards are never held across network, worker or large-file hashing awaits; hashing uses `spawn_blocking`. Health snapshots use `try_lock` instead of waiting behind inference. Search and reader generation guards keep stale responses from replacing newer views.

`intelligence/operations.rs` owns in-memory load/setup/register phases and cancellation independently of Settings' lifetime, so leaving and returning to Settings shows the same operation. Cancellation joins cooperative blocking verification or stops and reaps an interrupted server before admission is released. Setup persists completion only after its real inference succeeds. No database job kind is added for these operations.

Before `Store::open` can recover interrupted work, `core::lock_data_dir` takes a process-lifetime OS file lock on `<data>/rhythm.lock`. A second owner gets a Korean diagnostic and exits normally before opening the store or worker. Single-instance handling runs before that lock. The OS releases the lock when the process ends; an old lock file alone means nothing.

Rust owns persistence; browser previews never substitute localStorage or simulate success. A startup or migration failure stops launch instead of replacing user data. Theme changes are optimistic and revert on save failure.

### Archive tables

| Table | Purpose |
| --- | --- |
| `sources` | Catalog identity, group, pick (`selected`) and effective subscription, support flag, last attempt/success/error, per-attempt counters, resumable page, history and seed completion |
| `documents` | Current identity and metadata, sanitized HTML and normalized text, unique on `(source_id, external_id)` |
| `document_revisions` | Append-only meaningful snapshots, including the original fetched JSON/HTML, reader content and hash |
| `document_state` | Read/saved flags and timestamps, independent of content |
| `resources` | Per-revision image/attachment metadata, download state, local path, size, MIME, SHA-256 |

`Store::upsert_article` commits document, revision, user-state initialization and resource references in one transaction. The revision hash covers canonical URL, title, author, category, publication date, sanitized body/text and resource identities, not view counts, collection time or raw response churn. An unchanged check only updates validators and check time. Revisions never replace read/saved state, and old snapshots stay selectable. A downloaded resource is reused only for the same document, URL and role, so a remote file overwritten at the same URL is not detected; explicit retry can replace that revision's reference. There are no deletion/tombstone semantics or automatic retention cleanup.

Original responses are stored as revision data and never injected into the webview. A parse, network or write failure never replaces the last good article.

On reopen, running source jobs become `interrupted` and keep their page; running AI jobs become retryable failures; interrupted downloads become cancelled but keep partial bytes and validators. Pending AI jobs stay persisted and drain on later analysis admission, not at startup.

Settings shows database plus WAL size; archive summaries separately total referenced resource bytes, deduplicated by path. Neither is a full disk-usage report.

### AI tables

| Table | Purpose |
| --- | --- |
| `ai_models` | Managed/external ownership, `generation`/`embedding` role, file identity, pinned provenance, download state, resume ETag, errors, storage directory |
| `ai_preferences` | Selected generation model, setup completion, explicit/recent policy, automatic session limit, output token limit, execution mode, model directory, selected embedding model, automatic classification switch |
| `ai_jobs` | Attempts with priority, status, error, duration and full semantic identity; a partial unique index prevents duplicate active work |
| `notice_embeddings` | One unit-length vector per document revision and embedding model SHA-256; retained so a prototype change reclassifies without re-embedding |
| `notice_classifications` | Revision-scoped category, local score/margin, low-confidence marker and prototype config hash; a model or config change adds history instead of overwriting it |
| `ai_results` | Validated JSON, provenance, revision and cache identity, duration, partial-processing counts; inserted in the same transaction as job completion |

Jobs and results use the composite `(revision_id, document_id)` foreign key. Results keep artifact provenance without depending on inventory, so deleting a model keeps its analyses. A failed or cancelled regeneration keeps earlier good output. Revision-local job queries return all active attempts plus a bounded terminal history (20 in the reader); bounded history is never used to decide deletion safety.

## Personalization and ranking

`004_personalization.sql` keeps the legacy `settings.interests` text and imports its terms into structured rows; equivalent Korean/English labels share one normalized identity with aliases. The legacy value is cleared only by an explicit personalization reset. `documents.last_revision_at` changes only when a meaningful revision is committed.

| Table | Purpose |
| --- | --- |
| `personalization_profile` | Optional university, department, study level; learning switch |
| `personalization_interests` | Explicit or learned topic, normalized identity, aliases, priority 1–5, polarity, evidence summary |
| `personalization_feedback` | One idempotent row per document (`interested` / `not_interested`) |
| `personalization_evidence` | Deduplicated save/positive-feedback events per topic, document and kind |
| `personalization_activity` | Monotonic interaction sequence for refreshing learned memory |
| `personalization_suppressed` | Sequence baseline so removed inferred interests do not return from unchanged evidence |
| `source_extensions` | Source → built-in extension; a missing or disabled extension removes the source from recommendations, not from the archive |

Only saves and explicit positive feedback are behavioral evidence; opening, reading, searching and negative feedback create no topic memory. Learning needs evidence on at least two different documents, expires evidence after 180 days and recomputes after changed feedback/save state or at the next snapshot after a day. Negative feedback adjusts only its document and never hides a source or topic. Explicit interests are never overwritten by learned ones, and canonical explicit aliases prevent duplicate learned rows. Editing a learned memory promotes it to explicit; removing one records a sequence baseline.

Evidence topics come only from titles and original source categories, at most 32 terms per action, filtered by a small Korean/English sensitive-term list (lexical, not semantic). Body text and AI output are never used.

`Store::personalization_recommendations` is deterministic and never reads AI results or calls the worker:

- Each matching explicit topic: `12 + 3×priority` (15–27). Learned topic: at most 6. Explicit negative topics subtract their amount.
- Positive feedback: +24 for 30 days, +12 to day 180, +6 to day 365. Negative feedback caps the item score at −40 to day 180, −20 to day 365 (the item is not hidden).
- Saved +8; subscribed source +2; exact university/department/study-level match +4/+8/+2.
- Freshness: non-historical publication 0–6 over 30 days; recently collected older or undated non-historical +2; meaningful revision of an older item in the last three days +4. Historical backfill gets no freshness.
- AI dates, categories and summaries are never scored.

Candidates come from bounded indexed slices: 500 latest published, 250 recent non-historical, 250 meaningful updates, 100 saved, 100 feedback, 250 source, 250 category and 250 FTS matches (at most 1,950 before deduplication). At most 32 terms are matched against FTS5; each candidate exposes only a 320-character body prefix. Today requests eight rows; scores are not persisted. Explanations come from the same scoring branches. Order is score, then publication time, then document ID, descending. A first pass limits one source to half the list; a second pass fills the rest in score order. Personal evidence and results never leave the device or enter diagnostics.

## Korean local search

`storage/archive.rs::archive_query` searches title and normalized body, never navigation or footer text. Whitespace-separated terms are ANDed; each may match title or body. Terms of three or more characters provide quoted trigram MATCH candidates; parameterized, escaped LIKE checks enforce substring semantics for every term and handle one- and two-character Korean terms. Punctuation is data, not query syntax. Embedded NUL is rejected. Limits: 512 query characters, 32 terms, 100 rows per page (the UI uses 30).

Results have deterministic publication-date/ID order, source/category and saved/unread filters, and a plain-text excerpt. `Highlighted.svelte` renders text and `mark` nodes, not HTML from SQLite. Search and user state work offline and with the notice extension disabled. The ignored 5,000-record benchmark checks correctness and reports warm debug timings (about 11 ms inbox, 17 ms short Korean, 52 ms broad mixed queries on the development Mac); it is not a speed gate.

`archive_ranked_query` is the search page's default **관련도순** order (the date orders still use `archive_query`). Text matches use the same conditions, ranked by the number of terms in the title, then FTS5 `bm25` when a term has three or more characters, then newest. When `classification::Controller::query_vector` can embed the query, reciprocal rank fusion (k = 60) merges the first 200 text matches with semantic hits; later text matches follow in text order and are excluded from the fused head, so every text match appears exactly once and `total` counts the fused head plus the remaining text matches. Semantic hits compare the query vector with latest-revision vectors under the selected local embedding model's SHA-256, within the newest `SIMILARITY_WINDOW` (2000) notices that pass the source/category/saved/unread filters, and keep at most 20 hits scoring at least 0.20 and within 0.08 of the best (measured on synthetic fixtures; see `docs/AI_EVALUATION.md`). A damaged vector or another dimension only drops that notice from the semantic side. `meaning_only` lists hits that match no term; the list marks them **검색어는 없지만 뜻이 비슷한 공지**. The query is embedded with Qwen3's web-search instruction (`SEARCH_INSTRUCTION`), not the classifier instruction the stored vectors carry. It runs only when classification is on and the selected local model is installed and not failed; with remote embeddings selected, no model, a paused classifier (maintenance) or a busy inventory/backend operation, search is text-only. The query is never sent to the remote endpoint. Embedding holds the classifier batch guard, starts the embedding process on demand (it unloads after a minute idle like classification), and caches the last query vector so paging does not re-embed it. Semantic search never feeds personalization, notifications or learned topics.

`parser.rs` validates board/article identity, metadata, dates, pagination and response structure. The main board uses public paginated JSON list/detail endpoints; HTML error pages are not accepted as JSON, and listings must agree on size, total, page, pins and duplicates. Computing uses desktop `.board-list table` rows (so mobile pin copies don't distort pagination), extracts `article.board-detail`, and reads attachment metadata from a restricted subset of serialized Nuxt data without running JavaScript; its public route ID, internal `DETAIL.SN` and file path must all agree, and inline image roles win when an attachment shares the URL. `engineering.rs` validates the current SSR canonical/form/board/pagination identity, ordinals, full title and body, attachment names and visible Korean time against machine UTC. Unexpected structure is an explicit source failure, never an empty success. Fixture provenance is in `archive/fixtures/README.md`.

The dormitory calendar menu (`/sgdormitory/6558/subview.do`) is deliberately not a
source: it is a month grid of schedule entries (title and time only, fetched per month)
with no article body or publication date. Rendering it requires a separate event model,
not a notice document; the parser and catalog must not turn schedule entries into
articles with fabricated fields.

`dormitory.rs` covers the three dormitory CMS menus. It validates the page title, the search form's board id and the hidden site@@menu@@fnct token, the declared total, the ten-page pager block and its first/previous/next/last targets, and seven descending regular rows per page. Pins repeat on every page and may also appear in the regular rows; they stay one entry. Details are bound by `og:url`, the hidden article title and the list form's board id; attachments must be `/bbs/sgdormitory/<board>/<file>/download.do`, and inline images are kept as references. Beyond the last public page the site still serves a pins-only page, so the declared total is authoritative.

`community.rs` covers the two department sites that share the aseoul board engine but render different skins. It validates the board title, the declared total, the 5-page pager block (`FIRST`/`PREV`/`NEXT`/`LAST` links and the active page), page-local row budgets, descending regular ordinals and unique `idx` identities. Pins are sorted before regular rows and can therefore continue onto page two; the page size is 10 for tables and 12/9 for the ee/sse galleries. Details carry no canonical or self-identity link, so the parser binds the requested `?m=v&idx=` URL, the back-to-list link (`pNo` and `code`), the board title and the metadata; attachments must belong to the same article `idx`. The ee host serves attachments from `/aseoul_bbs/down.php`, but both sites' robots.txt disallows the `/se2/` editor-image and `/data/` directories, and sse also `/bbs/`, so the network policy never requests those. The parser still emits those references so the reader lists them as unsupported rather than losing the fact that they exist.

`mechanical.rs` covers the seven department boards. The site paginates only as
`?page=N`, and its robots.txt forbids every query string (`Disallow: /*?`), while the
legacy `/bbs/board.php` routes answer a Vercel challenge (HTTP 429). Discovery therefore
uses the public `/sitemap.xml` that robots allows: the parser filters the exact
`/ko/board/<board>/<id>` URLs, rejects duplicate identities, foreign hosts and query or
fragment forms, and sorts newest recorded change first. The listing is a single complete
document (`has_next=false`), so the sync's three-page window does not apply. Each entry
keeps the sitemap `lastmod`; the sync skips an existing notice while the archived
`modified_at` still equals it, and otherwise refetches with conditional validators. A
missing or non-UTC timestamp is never trusted and forces a refetch. Details are bound by
`link[rel=canonical]`, the board label, author/date metadata and a `div.prose-sg` body;
optional hero images in direct child blocks are kept and embedded iframes are dropped.
Attachment links are recorded from the page's `첨부파일` section (Supabase or a legacy R2
bucket) but are never downloaded from a third-party host, so they surface as unsupported.

Two reference collectors by the owner, [SogangFriends](https://github.com/Hiyabye/SogangFriends) and [sogang-notices](https://github.com/Hiyabye/sogang-notices), informed the catalog and parser contracts. Neither has an explicit code license, so Rhythm's Rust is written independently; observed public contracts are not permission to copy their code. Official notice and fixture content keeps its original rights.

A new notice whose body is only iframes (blank text and textless `p`/`div`/`span`/`br` wrappers allowed, as in the school's `div.iframe-wrapper` PDF viewers) is archived as metadata plus the original representation, with empty sanitized fields and an explicit unsupported-body state. The iframe is never fetched or rendered, and existing readable content is never replaced by such a result: that notice is recorded as checked and is neither a failure nor a skip. Readable content means non-empty sanitized HTML or text, or an image reference of the current revision whatever its download state; a stored image reference is kept because a later retry or route change can still fetch it.

PDF-viewer bodies (user decision): when such an iframe-only body shows `https://scc.sogang.ac.kr/pdfviewer/web/viewer.html?file=<URL>` and the file URL is the approved `/Download3` route (`pathStr`, a `.pdf` `fileName`, `gubun=cmsfile`), the parser adds that file as an attachment named by `fileName`. Once the PDF is downloaded, `archive/pdf.rs` (the `pdf-extract` crate in a blocking task, panics contained, at most 512 KiB of text) extracts its text layer, and `parser::with_pdf_text` makes it the body: a fixed note paragraph, then one escaped paragraph per line (a heading per file when there are several); `body_text` is the normalized text, so search, ranking and AI read it. The viewer page itself is never fetched or rendered. `archive/sync/pdf.rs::fill_pdf_body` re-parses the latest stored response, adds missing viewer-PDF references to the latest revision, downloads them if allowed, and `Store::fill_body` writes the text into that revision in place: the response did not change, so no revision, freshness change or change notice results, and the stored hash equals what a later fetch of the same response yields (a refetch derives the body from the local PDF first). Title-only embeddings/classifications of that revision are deleted for recomputation; if an analysis job or result already used the empty revision, the text is archived as a new revision instead. It runs after the article step and resource retry, and after every non-Cybercampus board run as a backfill of stored responses (`pdf_viewer_candidates`, no notice refetch, at most 10 PDF downloads per job; failed downloads wait for an explicit retry). A PDF without a text layer leaves the notice metadata-only with the PDF attached. A refetch keeps last-good content unless the viewer shows a PDF the notice never referenced.

## Cybercampus connector

`archive/cybercampus/` (#86) reads the logged-in user's own eClass (ilos LMS) data. Its request flow follows [rycont/eclass-cli](https://github.com/rycont/eclass-cli) (used with its author's permission under MIT terms); the Rust parsers are a port onto `scraper`, checked against pages captured from one account on 2026-11-06 and covered by synthetic fixtures (`archive/cybercampus/fixtures/README.md`).

- **Source and data model.** One catalog source, `cybercampus` (family `cybercampus`, owned by the `cybercampus` extension), so subscription, `archive_start`, the scheduler, cancellation and status are the archive controller's: `Controller::execute` dispatches the family to `cybercampus::sync` instead of the list/detail pipeline. Course notices are ordinary documents with `external_id` `<course key>-<notice seq>` and `category` = course name; their attachments (`/ilos/co/efile_download.acl`, which redirects to `/ilos/co/file_download_v2.acl`) and editor images (`/ilosfiles/editor-file/`) download with the session through the shared `install_resource` step (same size caps, format checks and hash paths); images on other hosts are recorded as unsupported. Courses and deadlines are not notices: `cybercampus_courses` holds the synced term's courses and `cybercampus_tasks` holds assignments (list + detail page: open date, deadline, late deadline, submission status/time) and the site's TODO items of other kinds (quizzes, lectures), keyed `(course, category, item)`, `pending` when the TODO list shows them.
- **Sync.** Terms come from `YearInfo` on the course-registration page; the newest of the first three terms that lists courses is synced (TA rooms and past terms are not). Per course: enter the room (`eclass_room2.acl`, which sets the session's current course), read every notice-list page (`start` is a 1-based row offset, 20 per page, at most 25 pages), fetch a notice only when it is new or its list title/preview fingerprint (stored in `documents.modified_at`) changed, then its `efile_list.acl` fragment; read the assignment list and fetch a detail page only for open or not-yet-stored assignments. One TODO request covers all courses. A failed course keeps its stored rows and the job reports it. The first successful sync archives notices as historical and sets `seed_complete`, so it never announces existing notices. eClass dates without a year (`10월 23일 (금)`) take the course year or the next one, whichever matches the shown weekday.
- **Session and credentials.** `client.rs` sends requests only to `https://eclass.sogang.ac.kr` on fixed read-only routes (plus `/ilosfiles/editor-file/`), with pinned public DNS, no proxy, the archive TLS chain completion, manual same-origin redirects (cookies kept per hop), a 700 ms gap, 30 s per request and 4 MiB page / 20 MiB file caps. Cookies stay in process memory. The login (학번 + SAINT password) is stored only in the OS credential store (`credentials.rs`, service `io.github.hiyabye.rhythm.cybercampus`), never in SQLite, backups or logs, and is sent only to `/ilos/lo/login.acl`. A redirect to the login page or a login form body means the session expired; the request logs in once more and repeats. When eClass rejects the login, `rejected` stops every further automatic attempt until the user saves a login again, so a changed password cannot lock the account through scheduled syncs.
- **Read-only boundary.** No submit, post, delete or confirmation route is allowed. Fetching a notice counts as a view on eClass, as opening it in a browser does; unchanged notices are not fetched again.
- **Privacy.** Cybercampus documents are personal data: `storage::intelligence::PRIVATE_SOURCE` excludes them from remote automatic analysis and remote classification candidates, and analysis admission and execution refuse them for the remote engine (`PRIVATE_REMOTE`). The local engine, local classification and search treat them like other documents.

## Studium manual seat checks

`studium/rooms.rs` defines seven fixed room identities and capacities. `studium/parser.rs` is independent of transport, SQLite and the UI; it decodes bounded UTF-8/CP949 bytes and validates room identity, counts, every seat number and the school's own timestamp. `StudiumView.svelte` owns the selected-room editor, per-room progress, displayed room and count/number results. This is separate from the notice archive, AI and notification pipeline.

`storage/studium.rs` persists one to seven unique selected room IDs and a display room belonging to that set. Saving the set adds targets, chooses a valid display room, then removes excluded targets in one transaction. Removing the current display room falls back to the first selected room in catalog order. Input or write failure preserves the previous preferences. The display room may change during a check; the selected set may not. Disabled-extension writes are refused.

`studium/controller.rs` owns one manual job and its bounded, per-room memory results. A start clears the selected rooms' old values and marks them `loading`; one common-status request is followed by one detail request per selected room, in sequence. A validated detail response supplies its own counts, numbers and timestamp together, even when its counts differ from the common page. An invalid or older detail response leaves only validated common counts (`count_only`, numbers absent); access denial is an error. Common-page failure clears the selected rooms, and a room failure clears that room while preserving other rooms' successes from this job. Validated zero remaining seats has an empty number list; unknown or failed results have no counts. Cancellation preserves completed rooms and clears unfinished rooms. Job identity prevents old cancellation or completion from changing a later job.

The states are `not_checked`, `loading`, `ready`, `count_only`, `failed` and `cancelled`. Source time is interpreted as KST and stored in memory as UTC; responses more than 300 seconds old or 60 seconds in the future fail validation. The UI reevaluates age while displaying a result. Receive time never replaces a missing source timestamp. The fetched HTML never enters the WebView or persistent storage.

Enabling the extension, opening its page, changing preferences and app startup cause no seat requests. UI polling reads local job status only while the page is open and a job is active. Disabling signals cancellation under the store lock, then waits without it and clears results; room preferences stay. The controller holds the shared admission lease through completion. Maintenance and exit cancel and join this worker before proceeding. Reopen/restore starts with no seat results; backups contain only the two preference tables and extension flag. No automatic school polling, seat alerts, predictions, seat-map rendering or reservations are implemented.

## Synchronization, scheduler and lifecycle

`archive/sync.rs::Controller` (listing, article, resource and robots code in `archive/sync/`) admits one archive or resource-retry job at a time. Admission keeps only supported subscribed sources whose owning extension (`source_extensions`) is on, under the same store lock that disabling uses. Disabling a source extension sets the controller's cancel flag under that lock and admission resets it only for enabled sources, so commit boundaries check the flag alone. Inside a job, three workers (`network::MAX_HOSTS`) take boards from one queue, never two boards of the same host at once, so boards on different hosts collect concurrently and each host keeps its own pacing; one source's failure is recorded and does not stop the others. Each running board has its own cancel flag: unsubscribing (`archive_subscribe`) stops only that board (recorded `cancelled`, not a job failure) or drops it from the queue, while job cancellation and extension disabling set every board's flag. Settings groups (`archive/catalog.rs::groups`, stored in `source_groups`) nest public boards; Cybercampus has none. A grouped board is subscribed only when its pick (`selected`) is on and every enclosing group is on; `Store` recomputes that in `sources.subscribed` whenever a pick, a group or the catalog changes, so collection, the scheduler, ranking and notifications read only `subscribed`. A pick under a group that is off is refused, and `archive_set_group` stops (or joins) exactly the boards whose effective subscription changed, as unsubscribing does. A command-started job that covers every subscribed board of an extension also takes that extension's boards subscribed while it runs, until its last board ends (`SubscribeResult.joined`); scheduled per-source jobs never take joins. The job's resource budget is one shared atomic counter, so bytes that push it past the cap are not installed. `SyncStatus.active` lists the boards collecting now.

- **Historical:** start at the persisted `next_page`, follow public pagination, deduplicate pins and IDs, and checkpoint only after no article on the page failed transiently (see below). Existing text is not refetched, but pending resources resume. `history_complete` becomes true only at the last public page, never at a safety or test limit.
- **Incremental:** start at page one and recheck recent pages and pins with ETag/Last-Modified validators. The minimum recheck window is three pages; discovery continues past it until a page of known regular records marks the frontier. Repeated pins never establish the frontier.
- **Refresh:** the manual action (새로고침) runs one job per board: an incremental pass first so new notices appear quickly, then a historical pass only while `history_complete` is false. Either step's failure or cancellation stops that board and keeps what the earlier step saved. The scheduler never uses it, so automatic work cannot start a backlog download.
- **First incremental seed:** with no local documents, fetch at most three pages as historical records, without counting them as new or marking history complete.
- **Scope:** incremental sync is not an audit of every old edit.

**Article failures.** A *transient* failure (network, deadline, server error, cancellation, redirect, or a response of the wrong content type, which is more likely a block page than the notice) holds the page checkpoint, fails the board and is retried on the next run. A *permanent* failure belongs to the fetched response: the body does not parse or its encoding is unsupported. It is recorded in `skipped_articles` (reason and response SHA-256), any last-good content stays, and the checkpoint advances, so one bad notice cannot stop a board. A later fetch that archives or confirms the notice (including HTTP 304) removes the row. Skipped notices are listed per board (count plus the 20 most recent) and are never dropped silently. Notices on recent pages are refetched by every incremental run; others only by the explicit `skipped` mode, which requests just those detail pages, archives them with their recorded historical marking, and leaves the board's status, counters, checkpoint and last success unchanged.

Counters describe the current attempt; checkpoints are cumulative. HTTP 304 updates the check time and still resumes pending resources. A resource failure is nonfatal to article archival but surfaces as a failure on explicit retry. Completing pagination does not promise every resource was downloaded.

The scheduler (`proactive/scheduler.rs`) is an in-process Tokio task that wakes every 15 seconds, not an OS service. When enabled and unpaused it reconciles tasks for supported, subscribed sources whose owning extension is on, while the `proactive` extension is on, and runs due sources sequentially with incremental sync. Interval `0` follows the energy profile (Eco/Balanced/Performance: 60/30/15 minutes); explicit intervals are exact values from 15 to 720 minutes. Retry interval is 5–120 minutes (default 15). Outcomes, next-run times and errors persist. Disabling, pausing, changing subscriptions or the extension, and shutdown all cancel work. Nothing runs while the computer sleeps or the app is closed. Scheduled results are tied to the admitted controller task, and the scheduler keeps servicing notification discovery while an import runs, without starting a second archive job.

`core/lifecycle.rs` owns tray, window and login behavior. Every lifecycle feature defaults off. Login registration changes only on explicit user action, is checked against actual OS state and rolls back if persistence fails. The registration is named after the bundle identifier: the production identifier keeps the entry released builds already created (macOS `Rhythm.plist`, Windows Run value `Rhythm.io.github.hiyabye.rhythm`), and every other identifier gets its own entry, so a validation or test build cannot read, replace or delete the installed app's login registration. A login launch honors hidden start; a manual launch stays visible unless `--hidden` is passed. Close-to-background works only if the tray installed; otherwise closing quits. Exit signals scheduler and archive cancellation, waits without holding SQLite, then stops the worker.

Every feature beyond the core shell (Today, 일반, 데이터 및 정보, 확장 기능) is a built-in extension in `extensions/mod.rs`; nothing is loaded from outside the app. Each is opt-in, and its flag lives in `extension_preferences`. Turning one off keeps its durable data and preferences:

| Extension | Off means |
| --- | --- |
| `sogang_notices`, `cybercampus` | Their sources' archive work is cancelled and refused (subscriptions stay separate and kept); `cybercampus_save_login` is refused |
| `search`, `saved`, `recommendations`, `week` | UI only |
| `calendar` | Its page and the week pane's todos are hidden; `Store` refuses todo writes and keeps the rows |
| `studium` | New checks and preference writes are refused; its worker is cancelled and joined, then in-memory results are cleared; selected rooms and display room stay |
| `ai` | `set_extension` cancels the running analysis of any priority and reaps `llama-server`; admission refuses, pending jobs stay queued, and `Store::ai_effective_preferences` masks automatic analysis, classification and semantic search (the classifier stops its process on its next pass) |
| `proactive` | `set_extension` first removes the OS login item (with rollback; on failure the extension stays on); `Store::proactive_effective_settings` masks the scheduler, notifications, close-to-background and hidden start |

Reading, search and saving of archived notices work with every source extension off.

## Notifications

Notifications are opt-in and independent of the scheduler. Discovery runs after archive commits. Candidate identity is document + revision + kind. Migration 005 set a revision ceiling so upgrades never announce old notices; a historical first seed is excluded, but a later meaningful revision of an old notice can qualify. Policy, source and negative-interest checks repeat before delivery; rejections are stored as `suppressed` with a reason. Events reference archive identities and read titles from archived revisions; no notice body is copied.

| Setting | Values |
| --- | --- |
| Sensitivity | `important` (preferences and score ≥18), `interested` (explicit-interest match), `all` (any eligible item). Negative feedback or negative-interest matches always suppress |
| Quiet hours | Local wall-clock range (default off, 22:00–07:00); eligible events are deferred, not consumed |
| Rate | At most three attempts per ten minutes, bounded candidate batches |

Event states: `pending → claimed → attempted | deferred | failed`, then `delivered` after activation confirmation, or `suppressed`. Claims have a five-minute lease; delivery attempts cap at three with capped exponential backoff (maximum four hours). Schema 6 reserves rate slots in a durable ledger before handoff, so clearing or pruning history never resets rate accounting or dedupe. A crash between reservation and handoff can use a slot without a visible notification. A backward clock change pauses the watermark until wall time catches up.

- **macOS:** native UserNotifications through the async `mac-usernotifications` 0.3.1 sender. A handoff is only `attempted`; an event is `delivered` only after the activation response. Responses are processed independently of the scheduler's delivery cycle: each alert closes itself after 30 minutes and at most 12 responses are tracked, so an ignored alert cannot stall later work. Authorization status maps not-determined/denied/authorized/provisional/ephemeral (timeout or error = unavailable). Denied or undetermined permission blocks attempts, but quiet-hours deferral still applies.
- **Windows:** WinRT toasts with the installed AUMID and `rhythm-win://notification/<token>` protocol activation; the protocol registration must resolve to the expected executable first. Status is authorized/denied/unavailable from notifier settings and install identity; there is no prompt, and the explicit button sends one test notification. The final policy check, token creation, attempt reservation and synchronous handoff share one store lock. Schema 7 stores only a hash of the random, expiring, one-use token bound to the event attempts; a validated click for the current attempt marks delivery. Discovery claims nothing unless authorization is `authorized`. Clicks during shutdown are refused, and restore clears tokens in staging.
- **Other hosts:** no sender; status is unavailable.

A click restores the existing window and emits `proactive://notification-clicked` with stable archive identities. The main-window capability grants only event `listen`/`unlisten`; `App.svelte` unlistens on teardown and falls back to a one-shot snapshot activation if the click arrived before it subscribed. `ProactiveSnapshot.notification_permission` stays `"unknown"`; Settings uses the separate authorization commands. Notification text includes the source name and title. No AI request is involved.

## Transport, resources and safe rendering

`archive/network.rs` uses native Reqwest/Rustls. Automatic requests need exact approved HTTPS hosts and routes on port 443 (main, Computing, Engineering, the Electronic/System Semiconductor community boards, the dormitory CMS, the Mechanical sitemap/article routes and the Semiconductor board list/detail, filedown and editor-image routes). URLs with credentials, fragments or unsafe encoded separators are rejected. DNS answers must be public and are pinned per connection; proxies and automatic redirects are off. The sync policy layer follows at most three same-origin redirects, re-running URL/DNS/TLS checks and robots authorization before each hop; transport only returns redirect targets. HTTP(S) resource references are kept as metadata so an old HTTP image doesn't discard the article, but only approved HTTPS routes are downloaded. Main images under `/dataview/board/<id>/<file>.(png|jpg|jpeg|gif|webp)` are an approved route, as is `scc.sogang.ac.kr/Download3` with exactly the PDF-viewer query above (other `scc` routes, including its HTTP article images, are not). The community hosts approve only their `/kor/community` (and ee `/kor/recruit`) article pages plus ee `/aseoul_bbs/down.php`; their robots-disallowed `/se2/`, `/data/` and sse `/bbs/` routes are never requested, so those resources are recorded as unsupported. The Cybercampus connector does not use this transport; its session client applies the same DNS, proxy, redirect and TLS rules to its own fixed eClass routes (see above). Requests carry an access mode: `Source` allows only those routes; `EmbeddedImage`, used for image resources only, also allows any other public HTTPS host name on port 443 (no IP literals, no other `*.sogang.ac.kr` route). Each such origin's robots.txt is loaded once per job and cached (including a failure); a 4xx robots.txt from such a host means no rules (RFC 9309), while a school host's error stays fatal. Third-party attachments are not downloaded.

Requests to the same host are paced at least 650 ms apart; different hosts do not wait for each other, and one client has at most three requests in flight. `robots.txt` is checked before collection (plain-text Accept header; Computing returns 406 otherwise); allow/disallow rules with wildcard and end-anchor matching and crawl delays up to 60 seconds apply, and a malformed delay in a group that applies to Rhythm or an HTML error page fails closed (a group for another agent cannot fail the policy). `scc.sogang.ac.kr` serves its robots.txt as unrendered ASP source that picks rules per host name; for that host only, `<% … %>` code blocks are removed and the rules of every branch apply (stricter, never looser; an unclosed block fails). Transient errors get at most three attempts with short backoff, connect/request/attempt deadlines and cancellable waits. HTTP 429 from a board's own host stops that board with a message instead of requesting the rest of the page; the notice and its files stay as they were for the next run. An attachment whose name has no supported document/raster extension is recorded as unsupported without being requested, and an unlisted file type never keeps a notice's text out of the archive. No login, access restriction or anti-bot bypass is used.

Studium uses a separate `Access::Studium` mode, restricted to `https://libseat.sogang.ac.kr:444/robots.txt`, `/SEAT/domian5.asp` and `/SEAT/roomview5.asp?room_no=<fixed room ID>`. This permission does not widen `Source` or `EmbeddedImage`. `studium/network.rs` checks robots for that origin, shares transport public-DNS pinning, pacing, cancellation and deadline protections, caps each page at 1,000,000 bytes, and refuses redirects and unexpected response types. A failed manual check is not automatically repeated; 401/403/429 do not trigger short retries. No login or access-control bypass is used.

For the seat origin only, Reqwest uses native TLS with a minimum of TLS 1.2: Schannel on Windows and Secure Transport on macOS. Hostname and certificate-chain verification stay enabled against the OS trust store; the app adds no roots, changes no system policy and never accepts invalid certificates. This supports the server's legacy cipher negotiation while retaining the fixed URL and pinned connection destination. OS trust and cipher policies can still reject it, and live compatibility is a separate claim on each platform. Other clients explicitly keep Rustls, including model downloads and remote AI: enabling Reqwest's `native-tls` feature must not silently change their default backend. The seat origin does not use the archive intermediate-chain supplement described below.

### TLS chain completion

`www.sogang.ac.kr`, `new-cms.sogang.ac.kr` and `eclass.sogang.ac.kr` omit their intermediate certificate. `archive/tls.rs` adds two bundled public intermediates as **untrusted candidates, only for those exact hosts**, then delegates all checks to WebPKI. The root store stays exactly Mozilla's `webpki_roots`; hostname, validity, signature, usage and path checks stay mandatory. No other host gets candidates. There is no invalid-certificate acceptance, new root or system trust change. Provenance and fixed-time tests are in `archive/certificates/README.md`.

### Resources

Limits: 4 MiB per list/article response, 10 MiB per inline image, 20 MiB per attachment, 256 MiB of completed resource bytes per job (charged before validation or disk writes; when the remaining budget, not the per-file cap, bounds a download, a size failure leaves the file `pending` for a later run), 64 KiB for robots, and a 100,000-page safety ceiling. Test budgets report `limited`, never complete history.

Resource URL, original filename, kind, MIME, bytes, state and SHA-256 are kept. Files use generated `resources/<sha256>.<validated-extension>` paths, never remote filenames, and are written through a `.part` file before SQLite references them. Images need PNG/JPEG/GIF/WebP signatures, PDFs a PDF signature; attachment extensions are restricted and active web types rejected. This is format validation, not antivirus scanning. Files are never opened or executed automatically; reveal only selects them in Finder or Explorer.

The `resources` sync mode ("자료 모두 내려받기") downloads `pending`/`failed` files of each subscribed board's current revisions, newest notice first, until the job budget is spent; like `skipped`, it leaves board status, counters, checkpoint and last success unchanged.

Local reads check containment, bound size and verify the stored SHA-256. Retry repairs corrupt bytes; a failed refresh keeps the last verified copy. There is no remote-image fallback. Cleanup of unreferenced files and storage quotas are not implemented.

The Rust sanitizer keeps a limited structural HTML subset, strips scripts, iframes, forms, styles and event attributes, and emits image references without `src`. Recursion stops at depth 64: a deeper subtree (legacy editors nest tables about 130 levels) is rendered iteratively as one block of its text and images without structure. More than 50,000 nodes is a parse error. `DocumentReader.svelte` builds a second restricted DOM, requests only integrity-checked local raster data URIs, and sends HTTP(S) links to the OS browser on explicit action. Missing or corrupt images become placeholders with repair actions. A failed automatic read-state write never hides content. CSP is an extra layer, not a replacement for the sanitizer.

## Managed models and downloads

`intelligence/models/` owns curated downloads, separate from notice transport. `catalog.json` pins Qwen3.5 2B/4B and Gemma 4 E2B/E4B Q4_K_M revisions, files, sizes and SHA-256 (see [AI evaluation](AI_EVALUATION.md#pinned-artifacts)). One-click installation accepts only `verified` entries. Inventory rows don't depend on the catalog: a row whose catalog entry was removed (9B, 0.8B) still opens, selects, removes and restores, and the UI marks it as no longer offered; its bytes are never deleted implicitly.

Each catalog entry may also pin an optional vision projector (mmproj): file, size, SHA-256 and a conservative memory estimate. Installing it is a separate explicit action (`ai_install_projector`/`ai_remove_projector`) sharing the single download slot; it is stored in `ai_projectors` with its own digest, resume state and status, at `models/<projector-sha256>.gguf` beside the weights. A projector is a `clip` GGUF, so its preflight checks the container and the committed digest without the text-model architecture rule. Its failure never changes the model row, and removing the model removes the projector's managed bytes and row. Restore marks a projector `missing` unless its file is still present with the recorded identity and its model remains installed in this installation.

Downloads use HTTPS to exact approved Hugging Face/CDN hosts with pinned public DNS per hop, normal TLS, no proxy and at most five reviewed redirects. A disk check reserves 1 GiB beyond the remaining bytes. Paths are generated: `models/<sha256>.part` and `models/<sha256>.gguf` under the default folder or the model's recorded custom destination (`model_storage.rs`). Resume needs a strong ETag, `Range`/`If-Range`, an exact `Content-Range` and the expected remaining size; a full `200` restarts. Files sync and pass GGUF preflight, exact size and committed SHA-256 before an atomic rename.

`ai_choose_model_directory` opens the native folder picker, validates the folder and write access, then saves it; cancelling changes nothing. On Windows any link or junction in the path is rejected; on macOS only a linked selected or `models` folder (system links such as `/var` are canonicalized). A new download captures its destination; existing and interrupted downloads keep theirs. A pre-existing final file in a chosen folder is adopted only if that inventory already received every byte, so removal never deletes bytes Rhythm didn't write. Both folder commands share AI/maintenance admission; `ai_preferences` cannot change the folder.

External registration references a canonical `.gguf` path without copying. Preflight accepts GGUF v2/v3 `qwen3`/`qwen35`/`gemma4` metadata; it is not full tensor or runtime validation. Registration computes the full SHA-256, and re-registering a changed file unloads cached weights first. Unregister never deletes external bytes. Managed removal checks containment, removes partial files first, records `missing` before the irreversible unlink and reconciles failures; documents and results stay. Loading and uncached analysis verify the complete file every time; the `sha2` assembly feature (macOS aarch64 only) speeds hashing but never replaces it.

## Inference process

`intelligence/server.rs` supervises upstream `llama-server`, bundled as Tauri resources under `llama/` and pinned to one llama.cpp build with per-archive size and SHA-256 (`scripts/llama-cpp.json`). `Worker` in `intelligence/mod.rs` owns it behind the same status/load/infer/unload/stop API the rest of the app uses. No process runs until a model is loaded or a request needs one; status without a process only checks that the bundled executable exists.

A vision load adds `--mmproj <projector> --image-min-tokens 1024 --image-max-tokens 2048`; the projector is part of the loaded-server identity, so switching it restarts the process. The server is accepted as vision-capable only when its log reports `loaded multimodal model`; an argument without that evidence is an error. A generation load starts `llama-server -m <model> --no-webui --no-slots --jinja --reasoning-budget 0 -np 1 -c <context> -lv 4` with all layers on the GPU, or `-ngl 0 --device none` for CPU. An embedding load replaces the chat flags with `--embedding --pooling <model> --embd-normalize 2 --batch-size 2048 --ubatch-size 2048` and uses an 8K context. On Windows the Vulkan build first lists devices and runs only on an NVIDIA one. The generation server listens on `<data>/run/llama.sock`; the embedding server uses `<data>/run/embedding/llama.sock`, each inside a `0700` directory. When that path exceeds the 103-byte Unix socket limit, or on Windows, it listens on 127.0.0.1 with an OS-chosen port read from its log, and a random key in a `0600` file (deleted once the server is ready) is required on every request. The supervisor waits up to 180 s for `GET /health`, then reads the device and offloaded layer count from the log to report the loaded backend. A Vulkan load counts as GPU only when every layer was offloaded.

Generation requests are one HTTP/1.1 exchange per connection to `/v1/chat/completions`, with a 600 s deadline: a fixed system instruction, the prompt, greedy sampling, thinking disabled and, for analysis, the closed generation schema as a JSON-schema `response_format`. Embedding requests use `/v1/embeddings` with a 120 s deadline and a bounded batch of 32. Responses need an exact `Content-Length` and are bounded to 4 MiB. Token counts and durations come from the server's `timings`. A context-overflow error maps to a Korean message containing `토큰 한도를 넘습니다`. Stdout is discarded; stderr is drained as bounded diagnostic lines.

One generation model and one sequence at most; the embedding classifier is a separate transient process. Loading another model, unloading and cancelling kill and reap the process; a late response is never reused, and the next request starts a fresh one. A crash is observed on the next status or request and never blocks archive or settings access. On Windows the process is in a kill-on-close job object.

macOS tries Metal first and falls back to CPU for the session after a load or request failure. On Windows the execution mode picks the build: `gpu` reports errors, `cpu` uses the CPU build, and `auto` falls back to CPU for the session after a device, load or request failure, but retries only that request on CPU after a context overflow (Vulkan context 8192 tokens; CPU and Metal 32768).

## Analysis, validation and cache

`intelligence/analysis/` (`mod`, `source`, `dates`, `validate`, `integrity`) reads a stored revision through `Store::document`; it never refetches the page or opens attachments. One persistent queue serializes inference. The default is explicit requests; opening an article only reads existing results. Cache lookup happens before any model inspection or server launch, and pending duplicates share one attempt.

**Cache identity:** document/revision + task + artifact SHA-256 + prompt version + output-schema version + a hash of output-affecting configuration (token limit, source bound, selector and evidence encoding, clock rules, decoding mode, thinking, sampling, repair policy, the `llama-server-v1` engine marker; plus the execution mode on Windows). The remote engine has no artifact hash: `model_sha256` is a derived SHA-256 of the engine id, normalized origin and model, and its configuration hash replaces the engine marker with `openai-compatible-v1` and adds the origin, model and timeout (`vision=none;image_source=none`). Local and remote results are separate cache entries; switching engines never deletes the other set. The `engine=llama-server-v1` marker is part of the local configuration hash; changing it makes stored results read as outdated. Current prompt version is **5**, selector **head-tail-keywords-v4**, stored schema **3**; the configuration hash also marks `vision=mmproj-v1` and `image_source=archived-local-v1`, so vision-era results are a new identity and text-only results read as outdated. Older results stay readable with provenance but never satisfy a newer key; the reader warns when a stored result's contract differs from the current one. Recovered pending attempts with an obsolete identity fail with retry guidance.

**Output (stored schema 3):** strict JSON with `short_summary`, `summary`, qualitative `uncertainty` and `facts`. Category is no longer generated: it comes from the embedding classifier and is shown independently. Fact kinds are deadline, event date, eligibility, documents, application method, link and action. Prompt 5 sends selected source passages as `{id,text}` objects and appends each attached archived image as `{id,text,image:true}`, and generation must return exactly `kind`, `label`, `value` and integer `evidence_id` per fact. The backend resolves each ID to the exact archived text and derives date and uncertainty before validating the stored schema. Invalid references, unknown or missing fields, invalid categories, malformed, empty, oversized or repetitive output, control tokens, unsupported evidence and ungrounded links are rejected.

**Dates:** a deadline or event date is normalized only from a single explicit date that appears in both the value and its passage, matched on digit boundaries. Claimed clock times must be supported for that date, with Korean and English AM/PM handled (`meridiem-v2`). Missing years, relative dates, ranges and multiple dates stay null. Literal grounding is not semantic entailment, and uncertainty is not calibrated confidence.

**Repair:** one schema or grounding failure allows one bounded repair with validation feedback. A second failure fails the job without replacing earlier good results; runtime errors never loop. Both generations are cancellable.

**Images and vision:** vision is opt-in per model. Without an installed projector, analysis is text-only and records `images_used`/`images_available` in the result provenance so the reader can say that archived images were not used. With one, the analysis attaches at most two already-`downloaded` rasters of the analyzed revision (each ≤ 6 MiB) as OpenAI-style `image_url` data-URI parts in the same user message; it reads bytes only through `archive::sync::local_resource` (containment, size, MIME and SHA-256) and never fetches. Pending, failed, oversized or corrupt images are skipped and counted, not fatal. Image objects are appended after the text passages, so their evidence IDs follow the text IDs. A fact that cites an image object is stored with `origin: "image"`, a server marker such as `[이미지 1]` instead of a quotation, `uncertainty: "ambiguous"` when it carries a date and `"unknown"` otherwise; the date is normalized only from the model's own value, never verified against pixels. Facts from one set of images are capped at four. When vision is active, a fact that cites a text passage but cannot be literally grounded there (for example a deadline read from the poster) is kept the same way with the generic marker `[이미지]` instead of failing the job; without attached images the strict text rejection is unchanged. Image text inherits the source-is-data rule. Attachments and iframe-only notices remain unreadable.

**Input bounds:** title and body ranges are selected from head, tail and important passages within 18 KiB of encoded source inside a 24 KiB prompt. Over budget, exact repeated passages are admitted once; table rows are separate evidence units; ordinary passages break at sentences or lines (500-character hard bound). Output is 128–4096 tokens (default 1024). Long documents record `partial` with processed and total characters, and the reader warns that omitted parts may hold dates or requirements. No chunk-and-merge or attachment text.

**Remote engine:** `intelligence/remote.rs` implements an opt-in OpenAI-compatible client beside the local supervisor. `AI 엔진 선택` stores `engine=openai-compatible` plus a normalized base URL, model, timeout (10–600 s), consent, an automatic-work switch with a per-local-day limit and a remote-classification switch. Consent is bound to the normalized origin; saving a different address clears consent, automatic work and remote classification before anything is sent. HTTPS is required, with plain HTTP limited to `127.0.0.1`, `::1` and `localhost` for local servers; proxies and redirects are disabled and the key is sent only to the configured origin. The key is read from and written to the OS credential store (Keychain or Credential Manager) and never to SQLite, backups, diagnostics or logs; the process keeps only a session cache. Cybercampus documents never reach it (see the Cybercampus connector). A request contains the fixed system instruction and the same user prompt as the local engine — notice title/body source objects and no personalization, profile, feedback, saved/read state, archive identity, device identity, images or attachments. Analysis is text-only; a local `mmproj` projector is never attached remotely. Responses are bounded to 1 MiB and the configured timeout; cancelling drops the HTTP request. On HTTP 400/422 the request retries with `response_format` `json_object`, then without it, and the negotiated format is cached per endpoint/model for the session; all ingress validators, grounding checks and the one-repair limit are unchanged, so the worst case is six requests per job. Provider 401/403/404/408/429/5xx errors map to Korean messages; sanitized provider text is bounded and redacted, and a key is never echoed. The result records the engine, model, origin/host and timeout, and the reader labels it as remote.

The model gets a fixed system instruction and JSON-quoted untrusted source data, no tools. Generated text renders only as escaped Svelte text. There are no model-driven commands or external actions.

Diagnostics are transient: at most 20 terminal reports in memory with stage timings, inference metrics and the fixed validator message of each failed validation, no source or generated text. Validator messages are written for the repair prompt; a job that still fails validation after the repair stores one fixed user-facing error instead.

## Embedding classification

`intelligence/classification.rs` runs a small pinned embedding model in the same bundled `llama-server`, but as a separate transient process, and classifies the latest revision of each notice. It embeds a bounded instruction + title + first 1000 body characters, compares the unit vector against authored Korean prototypes for the seven non-`기타` categories, and stores the raw score/margin plus the prototype config hash. The best match below `0.50` becomes `기타` with a low-confidence marker; the raw score stays local and the UI only shows the category and a low-confidence hint.

Config identity covers the prototype text, input shape, scoring and threshold; stored vectors survive a config change and are reclassified without re-embedding. A model change is a different SHA-256 scope. Removing a model removes its derived vectors and classifications, never archive content or analysis results. The classifier runs every five seconds while enabled, backfills existing latest revisions and picks up new ones, and never blocks collection. It yields while a generation analysis, model inventory operation or exclusive maintenance is active, and stops/reaps the embedding process after one minute without work. The process may coexist with a loaded generation model; both use separate runtime socket/key directories. There is no network, no ranking or notification input, and no automatic behavior before an explicit embedding-model install.

Stored vectors also drive similar notices and cross-post grouping, with no model call (`Store::ai_similar_notices`, #126). Candidates are the newest 2000 notices by publication date whose latest revision has a vector under the selected embedding model's SHA-256; vectors of other model hashes or older revisions are never compared. A target outside that window still uses its own latest-revision vector. Cosine (the dot product of unit vectors) ≥ 0.75 is similar. A duplicate needs cosine ≥ 0.97, the same whitespace-normalized lowercase title after leading bracketed board tags (`[공지]`, `(학부)`, `<…>`, `【…】`) are set aside, and the same sequence of digit runs in the title and body (full-width digits read as ASCII), so a copy with another date, time or amount stays separate. One title's tags must contain the other's, so `[학부]` and `[대학원]` stay apart while `[공지][학부]` matches `[학부]` and an untagged title. Contact numbers are left out of the body digits so an appended contact line does not split a copy: area-code numbers (`02-705-8123`), standalone three-digit-exchange numbers (`705-8123`), and three- or four-digit numbers after `내선`, `☎`, `Tel`, `전화` or `연락처`. A four-digit pair like `2025-2026` counts only after such a word, so year ranges still compare. Dates written in words (`삼월`, `다음 주 월요일`) are not compared. Duplicates are listed first, then the remaining matches up to the limit. `ai_similar_notices` returns five matches for the reader; `ai_duplicate_notices` returns only duplicates for up to 200 visible documents. The cosine score stays local. In the archive list a copy on the same page folds under its first row, which names the other boards and expands to show it; nothing is removed. While collapsed, the leader shows as unread when a folded copy is unread, and its toggle and screen-reader text give the count. Thresholds are not measured on real notices. Similarity never feeds ranking, notifications or learned topics.

## Energy policy

`intelligence/maintenance.rs` checks every five seconds while the app runs. Optional `recent` processing needs completed setup, an installed selected model and a focused main window. It considers at most 20 eligible latest revisions by collection time after session start, excluding historical backfill, startup history and revisions with any prior attempt. Attempts are capped per session.

Optional `backlog` processing is idle-only and needs completed setup, an installed selected model, at least five minutes of OS user inactivity, external power and a non-Eco profile. It considers the latest revision of every notice that has archived text and no attempt for that revision, newest publication first, and admits at most 20 attempts per rolling hour while the app runs. `intelligence/idle.rs` reports OS idle time (CoreGraphics on macOS, `GetLastInputInfo` on Windows) and the power source (IOKit, `GetSystemPowerStatus`); an unavailable probe admits nothing. A running backlog attempt is cancelled and reaped before an explicit worker/inventory action reuses the engine. A direct analysis is never cancelled; pending work is claimed by priority (direct 100, backlog 10), so a running backlog item finishes and the direct request runs before any further backlog item.

The same loop reaps the generation `llama-server` once it has served no load or request for `IDLE_UNLOAD` (60 s on every profile). The check runs before the download, AI-gate and store checks, so none of them can postpone it; a worker held by an analysis or command is in use and is left alone. The next request starts a fresh process. Explicit **불러오기** only warms the model; it is unloaded after the same idle minute. The embedding process unloads on its own one-minute timer.

| Profile | Automatic analysis | Scheduler cadence when interval is `0` |
| --- | --- | --- |
| Eco | None (explicit only) | 60 min |
| Balanced | Up to `min(automatic_limit, 3)` | 30 min |
| Performance | Up to `min(automatic_limit, 20)` | 15 min |

When the remote engine is selected, `recent` and `backlog` additionally require consent, `remote_automatic`, a stored key and a valid endpoint, and reserve a slot in the persisted per-local-day limit before admission; a failed or cached admission releases the slot. Direct user requests are never counted. Battery state is detected only to block backlog admission; Eco disables all automatic AI on AC and battery.

## Backup, restore and updater

`.rhythm-backup` is a ZIP with `manifest.json` (version 1, located by name, written last) listing each payload path, size and SHA-256. Creation copies the database with SQLite's online backup API in one step while holding the store's only connection, and adds only database-referenced resources; `models/` is excluded and external models stay references. Each file is read once and every resource must match its recorded size and SHA-256. An interrupted backup's snapshot is removed at the next launch. The archive is not encrypted.

Restore needs an awaited native confirmation (`window.confirm` is an async shim in the desktop app and must not be used). It extracts into hidden staging, verifies SQLite integrity, foreign keys and resource hashes, reconciles models (a managed model stays only if its local file matches the restored size and SHA-256; custom-folder models become external or missing references, never deleted; the folder preference is cleared), clears Windows activation tokens, and writes a journal. Rhythm then exits instead of relaunching, because a relaunched instance can race the exiting process for the single-instance socket and data lock. The next manual launch runs `recover_pending_restore` before `Store::open`, finalizes idempotently, disables remote inference (`engine=local`; consent, automatic work and remote classification cleared) and shows the outcome; the API key is not in the backup and stays in the OS credential store. A recovery error shows a native dialog and exits, keeping the journal and previous data. The previous profile is kept in `.rhythm-restore-previous-*` under the data root. `stage_restore` is the whole pre-exit path and is what the ignored large-profile benchmark measures. Each extracted file is flushed with `sync_all` (`F_FULLFSYNC` on macOS); Unix also syncs directories after each rename.

On Windows, restore additionally requires a local fixed NTFS volume, rejects reparse points, junctions and Cloud Files sync roots, moves with `MoveFileExW` (no replace or copy fallback) and stops on ambiguous recovery artifacts. Without directory fsync it survives process interruption, not power loss.

Backup, restore and updater share an app-wide `AdmissionGate`: maintenance closes admission, cancels and joins scheduler, archive, Studium and AI work, then reopens. Reopening admission starts no Studium check.

The updater verifies Tauri-signed artifacts against a build-time public key and requires the signed version to match the manifest (`requireSignedVersion`). The plugin registers only when `RHYTHM_UPDATER_PUBKEY` is set at build time; otherwise Settings shows manual update steps (`updater_configured`). Errors are mapped to Korean (`update_error`). The single endpoint is the `latest.json` of the latest published GitHub release; its `darwin-aarch64[-app]` entries point at the signed `Rhythm.app.tar.gz` and its `windows-x86_64[-nsis]` entries at the signed NSIS setup executable. The updater signature is not OS code signing: Gatekeeper and SmartScreen still treat the builds as unsigned on first install. `updater_restart` holds maintenance admission and stops and reaps a loaded `llama-server` before `install`, because the server runs from the install folder and the Windows plugin exits with `process::exit` (no `RunEvent::Exit`). Windows runs the NSIS installer in passive mode (`/P /UPDATE /R`). Install-location failures (read-only volume, translocated app, denied or cancelled authorization, an old bundle that could not be put back) map to Korean guidance.

Automatic checks (`run_auto_check`, keyed builds only, on by default) wake one minute after launch and then hourly, and check when the setting is on and the last successful check is a day old. They use a 30-second timeout, fail silently, keep the found update in `updater::State` and emit `updater://available`; the main window shows a dismissible banner that opens Settings → 데이터 및 정보. They never download or install.

## Packaging and CI

`src-tauri/tauri.conf.json` bundles `src-tauri/binaries/llama/` as the `llama/` resource directory. `scripts/stage-llama.mjs` fills it: it downloads the pinned archives for the host from llama.cpp's GitHub releases into `target/llama-cache/`, rejects any whose size or SHA-256 differs from the pin, and copies `llama-server` with only the libraries it loads (macOS) or with its DLLs plus the VC runtime it imports (Windows). `scripts/desktop.mjs` stages, then runs Tauri; it is not a cross-compilation helper. On Windows it delegates to `scripts/desktop-windows.mjs` (VC runtime, llama.cpp, NSIS); see [Windows](WINDOWS.md). Scripts never install toolchains or weights.

A default release build deletes `target/release/bundle/` and writes `target/release/distribution/`: the DMG or setup executable and its `.sha256`, plus the updater package files when both `TAURI_SIGNING_PRIVATE_KEY` and `RHYTHM_UPDATER_PUBKEY` are set (`scripts/updater-signing.mjs`). Release builds remap `$HOME`, `CARGO_HOME` and the checkout with `--remap-path-prefix`. `scripts/macos-release.mjs` (Developer ID signing and notarization) is kept for a possible future decision and refuses to run without credentials; `scripts/update-manifest.mjs` builds `latest.json` from the staged signatures and `scripts/verify-update.mjs` independently verifies signatures, the manifest, the macOS archive and the embedded public key.

`ci.yml` runs each concern once, gated by changed paths (`scripts/ci-changes.mjs`): frontend checks and Playwright on Ubuntu, `cargo fmt` on Ubuntu, and Clippy plus tests on macOS 15 and Windows. Release builds run only on `main` or manual runs when packaging inputs change. `release.yml` builds both platforms on a version tag with the updater key from the reviewer-gated `release` environment, verifies the updater files and `latest.json`, and creates a draft release; publishing it makes the update visible to installed apps. Normal tests are network-free; opt-in live, benchmark and model tests are listed in `AGENTS.md`.
