# Architecture

## Boundaries

Rhythm v2 has two halves (#166). A **collector** (`crates/collector`, scheduled every 30 minutes, in practice about hourly, by `.github/workflows/collect.yml` in the separate public `rhythm-fetch/collector` repository) crawls the 172 public boards, embeds and classifies notices through Cloudflare Workers AI and publishes a signed feed ([FEED.md](FEED.md)) to the public R2 bucket `rhythm-feed`, served read-only by the feed Worker (`worker/`). The **app** is a Korean-first, local-first modular monolith: one Tauri main window and, while the classifier has work, one supervised `llama-server` embedding process. It mirrors the whole feed (identical for every user, requests carry no user data), fetches an opened notice's body and files from the school, collects Cybercampus itself and keeps every piece of personal data on the device. There is no login service, user account, telemetry or cloud storage of user data; the app never uploads anything. Only public notice text reaches an AI provider (the collector's Workers AI calls); search queries and Cybercampus notices are embedded by the local inference server, which is reachable only by Rhythm (a private Unix socket, or loopback with a per-launch key). AI summaries and the opt-in OpenAI-compatible remote engine were retired (#226).

```text
rhythm-fetch/collector (GitHub Actions, about hourly)        Cloudflare
  rhythm-collector: crawl boards → Workers AI embed    ──▶  R2 rhythm-state (private, versioned SQLite)
                    → classify → sign + publish        ──▶  R2 rhythm-feed  ──▶ Worker rhythm-feed.*.workers.dev
                                                                                      │ GET manifest/segments/snapshots
Rhythm app ◀──────────────────────────────────────────────────────────────────────────┘
  ├─ feed sync → SQLite mirror (notices, excerpts, dates, vectors, categories, board health)
  ├─ body/files on open ──▶ school board hosts (robots, approved routes)
  └─ Cybercampus, Studium, model download, updater ──▶ their own fixed hosts
```

Supported platforms are macOS Apple Silicon and Windows 11 x64. Platform code sits behind `cfg(target_os = "macos")`/`cfg(windows)`; both platforms share the bundle identifier `io.github.hiyabye.rhythm`, the schema and the backup format. The app data root (`<data>` below) is `app_data_dir()` on macOS and `app_local_data_dir()` (non-roaming `%LOCALAPPDATA%`) on Windows.

```text
Svelte 5 / TypeScript
        │ Tauri invoke
Rust application (src-tauri)
  ├─ storage: SQLite settings, archive, revisions, user state, FTS5, AI, personalization, proactive state
  ├─ extensions: built-in extension list and on/off registry
  ├─ feed: signed manifest check, snapshot/segment download → storage::feed apply
  ├─ archive: source catalog, native parsers, constrained HTTPS, Cybercampus sync controller
  │     ├─ opened feed notice → body + resources from the school
  │     └─ <data>/resources/ → verified local files
  ├─ studium: fixed reading-room catalog, pure parsers, shared manual/automatic controller, memory-only seat results
  ├─ proactive: in-process scheduler and notifications
  └─ intelligence: curated model manager, embedding classifier and local supervisor
        ├─ <data>/models/ or a chosen folder → verified managed GGUF files
        ├─ stored document revision → vector + classification → SQLite
        └─ HTTP/1.1 /v1/embeddings over <data>/run/embedding/llama.sock, or 127.0.0.1 + per-launch key
one llama-server embedding process (bundled resources, pinned upstream build)
  ├─ macOS: llama/metal/ → Metal, or CPU after a failure
  └─ Windows: llama/cpu/
```

The Cargo workspace has five members: the Tauri app (`src-tauri`), `crates/collector` (`rhythm-collector`, the v2 server collector, #174: its SQLite crawl state and the public-board crawl rules, ported from the app's crawler (removed in #178) without resources, PDF bodies or Cybercampus, run by its binary one bounded pass at a time with at most three hosts at once and the v1 client's user agent, optionally against the versioned state in private R2 (download newest, crawl, upload a new version, keep 48) over its own SigV4 client, storing each notice's dates from the shared extractor (#166 O1), and removing a notice only after two definitive "not found" answers a day apart from a weekly audit of recent notices (mechanical: the sitemap set difference), with daily, bounded retries of skipped notices, and embedding notices through Workers AI (f16 vectors per revision; new notices every run, a newest-first backfill within the daily Neuron allowance, a daily drift canary that stops new vectors on a drop, and the server categories: each vector classified against the category prototypes, cached per scope, and the signed feed of [FEED.md](FEED.md) published to the public R2 bucket: changed records as run segments, daily compaction and snapshots, the manifest only after the state upload)), `crates/embed` (`rhythm-embed`, the notice embedding contract below: instruction prefixes, bounded input, category prototypes, scoring and config hash; no runtime or I/O, shared with the collector so both sides produce comparable vectors), `crates/feed` (`rhythm-feed`, the signed feed format specified in [FEED.md](FEED.md): records, int8 vectors, manifest and Ed25519 signature checks; no I/O, shared by the collector's publisher and the v2 app) and `crates/sources` (`rhythm-sources`), the notice sources shared by the app and the collector (#166): board catalog and source-side record types, page parsers and sanitizer, the URL/address policy for automatic fetches (`policy.rs`), the constrained HTTPS transport (`transport.rs`) with its TLS chain completion (`tls.rs`) and robots policy (`robots.rs`), PDF text and notice date extraction. The crate knows no storage, filesystem or Tauri. Its `studium` Cargo feature adds the seat-server access mode and is the only path that enables reqwest's `native-tls`; only the app enables it, so the collector stays Rustls-only. The app re-exports the crate as `crate::archive::{catalog, dates, parser, pdf, tls, network}` and keeps sync, storage and commands. Collection never waits for classification. Release builds are ad-hoc signed (macOS) or unsigned (Windows) by policy; updates are authenticated separately by the Tauri updater signature, and the updater stays disabled in builds without a compiled-in public key.

The feed Worker (`worker/`, TypeScript, #175) is the only public endpoint of the v2 feed. It is read-only: it answers `GET` and `HEAD`, reads only the feed files of [FEED.md](FEED.md) under the production prefix of the `rhythm-feed` bucket (never another prefix such as test or state data), keeps a per-IP rate limit and logs nothing beyond Cloudflare's defaults. Requests carry no user data, and the Worker has no write path, no secret and no binding beyond the bucket and the rate limiter; the collector writes the bucket directly over R2's S3 API.

## Application ownership and commands

`src/App.svelte` owns navigation, the settings panes (one rendered at a time; the last pane is kept while the app runs) and themes. `src/lib/extensions.ts` maps each extension to the nav items and settings panes it adds; the shell shows only the core entries (오늘; 확장 기능, 일반, 데이터 및 정보) plus those of enabled extensions (휴지통 appears while a source extension is on or it still holds notices), and falls back to Today or 확장 기능 when the current one goes away. In `src/lib/`: `ExtensionSettings.svelte` is the extension on/off list; `ArchiveView.svelte` owns lists, search, Today (its recommendations and week pane each follow their extension, with an empty state when neither is on) and classification tags, hiding stored AI output while `ai` is off; `DocumentReader.svelte` reads a stored revision and takes document feedback; `SourceSettings.svelte` manages the subscriptions and jobs of one source extension's sources (with `CybercampusSettings.svelte` for the eClass login); `CybercampusTasks.svelte` is the 과제·마감 page, shown while the `cybercampus` extension is on; `CalendarView.svelte` is the 캘린더 month page (open eClass deadlines, notice dates from `calendar_notice_dates` with the every-notice-deadline toggle, and the user's todos, with todo editing for the selected day), rendered by `ArchiveView.svelte` so it shares the week pane's deadline rule and the reader; `PersonalizationSettings.svelte` owns profile, interests, learning and memory; `AiSettings.svelte` manages the classification model, retired models still installed and the model folder; `ProactiveSettings.svelte` exposes lifecycle and scheduler controls (`part="background"`) or notification controls and history (`part="notifications"`); `Popover.svelte` anchors a native light-dismiss popover to its `popovertarget` button and `Hint.svelte` uses it for row explanations. Times are shown and edited in the 12/24-hour format from `settings.clock_format` (`clock.svelte.ts` holds it; `TimeField.svelte` edits todo and quiet-hours times as 오전/오후 plus a 12-hour list, or a 24-hour list). `types.ts` mirrors Rust command payloads. `platform.ts` picks platform wording from the WebView user agent (never for security decisions).

Commands:

- Foundation: `get_snapshot`, `save_settings`, `set_extension`.
- Archive (`archive/mod.rs`): `archive_sources`, `archive_subscribe`, `archive_source_groups`, `archive_set_group`, `archive_summary`; `archive_query`, `archive_ranked_query`, `archive_document`, `archive_state`; `archive_trash`, `archive_restore`, `archive_purge` (휴지통); `archive_start`, `archive_cancel`, `archive_status`; `archive_retry_resource`, `archive_resource_image`, `archive_reveal_resource`; `archive_open_original` (explicit HTTP(S) navigation in the OS browser only). Opened feed notices (`archive/sync/body.rs`): `archive_fetch_body`, `archive_fetch_resources`.
- Feed (`feed/mod.rs`): `feed_sync` (one sync now; the scheduler loop runs it on its own), `feed_status`.
- Cybercampus (`archive/cybercampus/mod.rs`): `cybercampus_status` (saved login ID, rejection flag, current courses; never the password), `cybercampus_save_login` (logs in first and stores the login only when eClass accepts it; refused while a sync runs), `cybercampus_forget_login`, `cybercampus_courses` (the synced courses with each one's unread notices outside 휴지통, counted by the notices' category = course name; it reads no credential, so the sidebar can refresh it), `cybercampus_tasks`.
- Notice dates (`commands.rs`, `storage/notice_dates.rs`): `calendar_notice_dates` (an inclusive local-day range of at most 62 days; every date of a saved notice plus, while `settings.calendar_all_deadlines` is on, the deadlines of every notice of a subscribed source; outside 휴지통; at most 2000 rows) returns the toggle with the dates (a multi-day date is included when it overlaps the range), `calendar_set_all_deadlines` saves it, and `notice_dates` lists one notice's dates for its reader. Dates are found by `crates/sources/src/dates.rs` in the current title and body when an article is written or its body filled, and by a once-per-launch backfill for missing or stale extractions (`content_hash` or extractor version).
- Calendar (`commands.rs`): `calendar_todos` (an inclusive local-day range of at most 62 days), `calendar_create_todo`, `calendar_update_todo`, `calendar_set_todo_done`, `calendar_delete_todo`; writes are refused while the `calendar` extension is off. `calendar_create_todo` accepts an optional `document_id` for a notice outside 휴지통; updates keep the existing link. Reads return the link as null while the notice is in 휴지통.
- Todos carry an optional `reminder_minutes`, validated against whether the todo has a time; `calendar_reminder_activation` (`proactive/mod.rs`) returns a clicked reminder's day once (see Notifications).
- Calendar export (`calendar_export.rs`, #191): `calendar_export` writes an RFC 5545 `.ics` file to the path the user picked in the native save dialog: every todo not done (any day) and, while the `cybercampus` extension is on and its source subscribed, the open eClass deadlines under the calendar's rule (due time set, unsubmitted, due or late window not past). Notice dates are not exported. Untimed todos are all-day events; timed todos are floating local times; eClass times (KST) are written in UTC, dated-only ones as all-day. UIDs are stable (`todo-<id>@…`, `eclass-<course>-<category>-<item>@…`) so a re-import can update events. Nothing to export is an error and writes no file. The store lock is released before the file is written.
- Studium (`studium/commands.rs`): `studium_snapshot`, `studium_save_preferences`, `studium_set_view_room`, `studium_start`, `studium_status`, `studium_cancel`, `studium_save_interval`, `studium_automatic_start`, `studium_automatic_pause`, `studium_save_favorites`, `studium_save_alert`, `studium_notification_activation`. Native views (`studium/views.rs`): `studium_open_mini`, `studium_close_mini`, `studium_mini_status`, `studium_mini_set_on_top`, `studium_mini_show_main`; the status payload contains `open` and `always_on_top`, with no raw geometry IPC. Only an explicit manual start or a session started with `studium_automatic_start` admits school requests; snapshots/status and one-shot notification activation are local reads. Saving preferences, opening or changing a display, and toggling always-on-top never starts a job or sends an alert.
- Proactive: `proactive_snapshot`, `proactive_save`, `proactive_history`, `proactive_clear_history`, lifecycle status and explicit close-to-background/hidden-start/login updates, `notification_authorization` (status, no prompt) and `notification_request_permission` (explicit user action only).
- AI (`intelligence/commands.rs`): `ai_snapshot`; `ai_install`, `ai_cancel_download`, `ai_remove`; classification preferences and results (`ai_classification_preferences`, `ai_classifications`, `ai_classification`); `ai_similar_notices`, `ai_duplicate_notices`; `ai_choose_model_directory` and `ai_reset_model_directory`.
- Personalization: `personalization_get`, `_save_profile`, `_save_interest`, `_remove_interest`, `_set_learning`, `_reset`, `_get_feedback`, `_set_feedback`, `_recommendations`.

Every command is declared twice in Rust: `main.rs` registers it in `generate_handler!` and `build.rs` lists it in Tauri's app manifest, which generates an `allow-<command>` and a `deny-<command>` permission. App commands are denied unless a capability grants them, so `capabilities/default.json` gives the `main` window exactly the commands its code invokes and `capabilities/studium-mini.json` gives the mini window only `get_snapshot`, the seat-check reads and controls and its own window commands. Adding a command needs the handler list, the manifest and the capability of each window that invokes it; `tests/capabilities.test.mjs` fails when they drift, because Playwright's mocked IPC cannot detect a missing permission.

`AppState` owns an `Arc<Mutex<Store>>`, the archive controller and client, the Studium controller, seat-notification owner and native mini/tray owner, the extension registry, the classification controller (which owns its embedding worker), the model-install controller and an AI mutation gate. SQLite guards are never held across network, worker or large-file hashing awaits; hashing uses `spawn_blocking`. Search and reader generation guards keep stale responses from replacing newer views.

Before `Store::open` can recover interrupted work, `core::lock_data_dir` takes a process-lifetime OS file lock on `<data>/rhythm.lock`. A second owner gets a Korean diagnostic and exits normally before opening the store or worker. Single-instance handling runs before that lock. The OS releases the lock when the process ends; an old lock file alone means nothing.

Rust owns persistence; browser previews never substitute localStorage or simulate success. A startup or migration failure stops launch instead of replacing user data. Theme changes are optimistic and revert on save failure.

### Archive tables

| Table | Purpose |
| --- | --- |
| `sources` | Catalog identity, group, pick (`selected`) and effective subscription, support flag, last attempt/success/error, per-attempt counters, resumable page, history and seed completion |
| `documents` | Current identity and metadata, sanitized HTML and normalized text, unique on `(source_id, external_id)` |
| `document_revisions` | Append-only meaningful snapshots, including the original fetched JSON/HTML, reader content and hash |
| `document_state` | Read/saved flags and timestamps, independent of content |
| `resources` | Per-revision image/attachment metadata, download state, local path, size, MIME, SHA-256 |
| `feed_state` | The last applied feed seq, the `generated_at` and base URL of the last accepted manifest, the `generated_at` of the one before it, the last successful check and the last attempt's result |
| `feed_boards` | Each board's collector health (`last_success_at`, `consecutive_failures`, `history_complete`) from the last accepted manifest |
| `feed_embeddings`, `feed_classifications` | The feed's vector (as published: f32 scale + 1,024 int8) and category of a notice's current revision, read for notices with `from_feed`; the local model's tables cover every other notice |

`Store::feed_apply_snapshot`/`feed_apply_segment` (`storage/feed.rs`) apply one decoded records file of `docs/FEED.md` in one transaction and move the cursor. A feed notice is a `documents` row with the feed's `revision_hash`; each new feed revision adds a revision row without an original, whose resources come from the record's links as `pending`, and until the notice is opened `body_text` holds the excerpt (`body_pending`), so search, ranking and previews cover it unchanged. Its dates are the feed's (the date backfill skips `body_pending` notices). A v1 notice whose latest revision hashes to the feed's `revision_hash` (`rhythm_feed::revision_hash`) is adopted with its body; otherwise the feed's revision replaces it. A snapshot replaces every feed vector and category and removes the notices with `from_feed` it no longer lists; a v1 notice the feed never described stays (user decision, 2026-11-18). A removal deletes the notice (returning resource files no other notice uses) unless it is saved, which keeps the row with `removed_at`. A permanent deletion from 휴지통 wins over later upserts; records for unknown boards, Cybercampus or invalid fields are skipped and counted, never failing the file. Nothing a snapshot applies becomes a notification candidate (it advances the proactive baseline); `feed_apply_segment(.., quiet)` does the same for the segments a sync applies after a snapshot, so a first sync never notifies. The notices a snapshot or a quiet segment adds, and those the collector's history import found (`historical`), start read, so a backfill does not flood the unread count; later arrivals start unread and notices already archived keep their read state. The app collects only Cybercampus (below); public boards arrive only through the feed.

**Feed sync** (`src-tauri/src/feed/`, #177). `feed::sync` follows FEED.md "Applying the feed": it fetches `manifest.json` and its `.sig`, verifies them against the compiled-in key (`TRUSTED_KEYS`, `key_id` `7fdf378f071d58dc`), follows a signed `moved_to` (at most three hops; any public HTTPS host name, user decision 2026-11-18), accepts the manifest only if its `generated_at` is not older than the stored one (`Store::feed_accept`, which also stores the base and board health), then applies either the segments from the cursor, nothing when the cursor is the newest seq, or the snapshot and the segments after it. **New boards (#80):** earlier syncs skipped the records of a board missing from the catalog. With a cursor and catalog boards absent from `feed_known_boards`, the sync first applies those boards' records from the snapshot and every later segment (`Store::feed_backfill`: those boards only, read, no notification, the baseline advanced, the cursor untouched), then follows the cursor without those boards' records (`feed_apply_segment(.., skip)`), so an older revision never follows a newer one. `feed_remember_boards` records the catalog's boards only after every planned file applied, so a sync that stops early backfills them again. Each file is checked against its manifest size and SHA-256 before decoding and applied in its own transaction; resource files a removal orphaned are deleted after the store lock is released. A failed file stops the sync with the files before it applied. `UnsupportedFormat` records `update_required` and keeps the mirror. `feed::Controller` runs one sync at a time; the scheduler loop runs it at launch and 30 minutes after a success (5 minutes after a failure, longer when a 429 asks) while `sogang_notices` is on, whether or not the opt-in scheduler is (user decision P2, a default-on exception like the update check), and `feed_sync` runs it on request. Maintenance, exit and turning `sogang_notices` off cancel it between files. `feed_status` reports the accepted `generated_at`, the last successful check, the last result and error, `stale` (manifest older than 3 hours) and the subscribed boards with at least 3 consecutive collector failures (user decisions, 2026-11-18). The transport (`feed/transport.rs`, #46) is separate from the archive client: HTTPS on port 443 to the feed base only, pinned public DNS answers, no proxy, no redirects, no cookies or user data, `Accept-Encoding: identity`, 15 s connect and 45 s idle timeouts, the manifest capped at 1 MiB, the signature at 4 KiB and every other file at its listed size (at most 128 MiB). Files are content-addressed and fetched once, so it sends no conditional requests. The UI shows the feed in the 게시판 settings pane (`FeedSettings.svelte`: age, last check, failing boards, 지금 받기; an offline result is a quiet note; each public board's tile and status popover in `SourceSettings.svelte` show its health from `feed_boards` through `SourceInfo.feed`, with no collect controls) and a banner above 받은 소식 when the feed is stale or needs an app update.

**Body on open** (`archive/sync/body.rs`, #177). The reader shows a `body_pending` notice's title, metadata, excerpt and feed dates at once (`DocumentDetail.summary_only`, true for any revision without an original that carries a feed hash) and calls `archive_fetch_body`. `sync::body::Bodies` fetches the article through the archive client under the crawl rules (`parser::detail_url` from the stored canonical URL, robots.txt reused per host for an hour, the client's pacing and approved routes, `Access::Source`, no validators), parses it and `Store::fill_feed_body` fills the latest revision in place: original, title/metadata, body, content hash, `body_state`, `body_pending=0`, the fetched resource references (unchanged URLs keep their rows, dropped ones are deleted and their unused files removed after the lock), dates re-extracted from the body and local excerpt vectors dropped. It stays the same revision, so freshness and notifications are unchanged. The fetched article's `rhythm_feed::revision_hash` is compared with the feed's: a mismatch keeps the fetched text, takes its hash (so the feed's later record of that revision keeps the body) and the reader labels it 원문이 수정됨; the feed's vector stays until the feed describes a newer revision. A main-board PDF-viewer notice downloads its viewer PDF (scc robots, existing hash-verified storage) and uses its text, keeping the feed's hash without comparing; a scanned PDF leaves it metadata-only. Any failure keeps the excerpt and the reader offers 다시 시도; nothing is fetched for a notice the school deleted (`removed`, shown as 원문 삭제됨) or with `sogang_notices` off, and maintenance, exit and turning the extension off cancel a fetch.

**Files on open** (#177). Once a notice's body is here (fetched on open or archived by v1), the reader calls `archive_fetch_resources` for a latest revision that has `pending` resources and reloads when it returns, so images appear in place. `Bodies::resources` (`Store::pending_downloads`) downloads only `pending` rows of the latest revision, never before the body arrived (its fetch replaces the feed's links), for a removed notice or with `sogang_notices` off, and not for Cybercampus (its session sync owns them). The rules are those of the v1 crawler: `download_resource` with the board's robots.txt (the hourly per-host cache), another image host's own robots.txt (per call), the per-file caps and one job's budget per call; a school 429 stops the call. Each failure is recorded on its row, so a `failed`, `too_large` or `unsupported` file is not requested again on the next open and waits for 다시 내려받기 (`archive_retry_resource`). Concurrent calls for one notice wait for each other; downloads write their own partial file (`resources/<sha256>.<n>.part`) so two opens or an open and a retry installing the same file do not collide. Maintenance, exit and turning the extension off cancel it.

`Store::upsert_article` commits document, revision, user-state initialization and resource references in one transaction. The revision hash covers canonical URL, title, author, category, publication date, sanitized body/text and resource identities, not view counts, collection time or raw response churn. An unchanged check only updates validators and check time. Revisions never replace read/saved state, and old snapshots stay selectable. A downloaded resource is reused only for the same document, URL and role, so a remote file overwritten at the same URL is not detected; explicit retry can replace that revision's reference. There are no deletion/tombstone semantics or automatic retention cleanup.

Original responses are stored as revision data and never injected into the webview. A parse, network or write failure never replaces the last good article.

On reopen, running source jobs become `interrupted` and keep their page; interrupted model downloads become cancelled but keep partial bytes and validators.

Settings shows database plus WAL size; archive summaries separately total referenced resource bytes, deduplicated by path. Neither is a full disk-usage report.

## Personalization and ranking

`004_personalization.sql` keeps the legacy `settings.interests` text and imports its terms into structured rows; equivalent Korean/English labels share one normalized identity with aliases. The legacy value is cleared only by an explicit personalization reset. `documents.last_revision_at` changes only when a meaningful revision is committed.

| Table | Purpose |
| --- | --- |
| `personalization_profile` | Optional university, department, study level; learning switch |
| `personalization_interests` | Explicit or learned topic, normalized identity, aliases, priority 1–5, polarity, evidence summary |
| `personalization_feedback` | One idempotent row per document (`interested` / `not_interested`) |
| `personalization_evidence` | Deduplicated save/positive-feedback events per topic, document and kind |
| `personalization_activity` | Monotonic interaction sequence for refreshing learned memory |
| `personalization_suppressed` | Sequence baseline so removed inferred interests do not return from unchanged evidence |
| `source_extensions` | Source → built-in extension; a missing or disabled extension removes the source from recommendations, not from the archive |

Only saves and explicit positive feedback are behavioral evidence; opening, reading, searching and negative feedback create no topic memory. Learning needs evidence on at least two different documents, expires evidence after 180 days and recomputes after changed feedback/save state or at the next snapshot after a day. Negative feedback adjusts only its document and never hides a source or topic. Explicit interests are never overwritten by learned ones, and canonical explicit aliases prevent duplicate learned rows. Editing a learned memory promotes it to explicit; removing one records a sequence baseline.

Evidence topics come only from titles and original source categories, at most 32 terms per action, filtered by a small Korean/English sensitive-term list (lexical, not semantic). Body text and AI output are never used.

`Store::personalization_recommendations` is deterministic and never calls the worker or a model; its only AI input is the similarity term below:

- Each matching explicit topic: `12 + 3×priority` (15–27). Learned topic: at most 6. Explicit negative topics subtract their amount.
- Positive feedback: +24 for 30 days, +12 to day 180, +6 to day 365. Negative feedback caps the item score at −40 to day 180, −20 to day 365 (the item is not hidden).
- Saved +8; exact university/department/study-level match +4/+8/+2. Subscription is not a term: candidates come only from subscribed sources and notifications only from active ones, so it would add the same points to everything (user decision, 2026-11-24).
- Freshness: non-historical publication 0–6 over 30 days; recently collected older or undated non-historical +2; meaningful revision of an older item in the last three days +4. Historical backfill gets no freshness.
- Similarity (#177 PR 7, user decisions 2026-11-20), only while the `ai` extension is on: a candidate's latest-revision vector (`vector_join`: the feed's, or the selected local model's while one is installed) is compared with the 50 most recent saved or interested notices (interest within 365 days; never one marked not interested or in 휴지통) and the 50 most recent not-interested notices of the last 365 days, the candidate itself excluded. The closest saved/interested cosine `c` adds `floor((c − 0.75) / 0.20 × 6)`, capped at 6, unless a not-interested notice is at least as close. The reason names that notice (`저장하거나 관심 표시한 ‘<title, 30 characters>’ 공지와 비슷함`). A notice without a vector, or a damaged one, gets no term. The same term enters notification scores; with full freshness it reaches at most 12, so it cannot meet Important (≥ 16) alone. Measured on 6,713 feed vectors of a copied profile: cosine to unrelated notices has a median near 0.60, while dense clusters (award news) hold hundreds of notices above 0.9, hence the small cap. A release-build benchmark with 2,003 vectored notices and 50 anchors took about 49 ms per list (16 ms without the term).
- Classifications are never scored.

Candidates come only from subscribed sources whose owning extension is on (the feed mirrors every board), through bounded indexed slices: 500 latest published, 250 recent non-historical, 250 meaningful updates, 100 saved, 100 feedback, 250 source, 250 category and 250 FTS matches (at most 1,950 before deduplication). At most 32 terms are matched against FTS5; each candidate exposes only a 320-character body prefix. Today requests eight rows; scores are not persisted. Explanations come from the same scoring branches. Order is score, then publication time, then document ID, descending. A first pass limits one source to half the list; a second pass fills the rest in score order. Personal evidence and results never leave the device or enter diagnostics.

## Korean local search

`ArchiveQuery` scopes to one board (`source_id`) or to the boards placed directly in one settings group (`group_id`, not its nested groups, regardless of subscription); setting both, or an unknown ID, is rejected. `subscribed_only` keeps notices of subscribed sources: the feed mirrors every board, so the feed pages (오늘, 받은 소식, 기회) set it, their 정보원 select lists only subscribed boards, and 검색, 보관함 and 휴지통 cover the whole archive. `archive_summary` counts unread and new-since-sync notices of subscribed sources only, like those pages; the archived and saved counts cover everything. Both list commands and the category list apply the scope. `storage/archive.rs::archive_query` searches title and normalized body, never navigation or footer text. Whitespace-separated terms are ANDed; each may match title or body. Terms of three or more characters provide quoted trigram MATCH candidates; parameterized, escaped LIKE checks enforce substring semantics for every term and handle one- and two-character Korean terms. Punctuation is data, not query syntax. Embedded NUL is rejected. Limits: 512 query characters, 32 terms, 100 rows per page (the UI uses 30).

Results have deterministic publication-date/ID order, source/category and saved/unread filters, and a plain-text excerpt. `Highlighted.svelte` renders text and `mark` nodes, not HTML from SQLite. Search and user state work offline and with the notice extension disabled.

`ai_category` (#125) keeps notices whose latest revision has that classification: the feed's for a feed notice, otherwise the installed embedding model's under the current config hash (see "Embedding classification"); it must be one of the current categories. Unclassified notices never match. While the `ai` extension is on, both list commands return `ai_categories`: a count per category, in the classifier's order, under every other filter and the text terms (relevance search's meaning-only hits are not counted), plus the number of unclassified notices. The archive shows the categories with notices as **AI 분류** chips, separate from the board's own category (**게시판 분류**), and notes how many unclassified notices a chosen category leaves out. The filter is display only. The ignored 5,000-record benchmark checks correctness and reports warm debug timings (about 6 ms inbox, 13 ms short Korean, 49 ms broad mixed queries on the development Mac; with half the notices classified by the feed and half locally, about 26 ms for the inbox with AI counts and 41 ms for an AI category, against 21 and 33 ms when every row is local, measured 2026-11-20); it is not a speed gate. The filter and counts share `CURRENT_CATEGORY`, which looks up only the table of the notice's origin.

**기회 (#87, user decisions 2026-11-22).** A page the `ai` extension adds. `ArchiveQuery.opportunities` keeps notices whose current category (`CURRENT_CATEGORY`, as above) is one of `storage::archive::OPPORTUNITY_CATEGORIES` (공모전·대회, 인턴·채용, 교육·프로그램, 행사·활동) and is rejected while the `ai` extension is off; `ai_category` may narrow it to one of them, and `ai_categories` counts within them. A notice is *closed* when it has `deadline` rows in `notice_dates` and all of them lie before the local day; closed notices are left out unless `include_closed`. The order is the nearest `deadline` row on or after today (untimed after timed on the same day), then notices with none, newest first; `ascending` is ignored. The page returns `deadlines`: each listed notice's nearest open deadline, or its latest passed one marked `closed`. The deadline order and D-day are display only: categories and dates still never enter ranking, recommendations or notifications.

`archive_ranked_query` is the search page's default **관련도순** order (the date orders still use `archive_query`). Text matches use the same conditions, ranked by the number of terms in the title, then FTS5 `bm25` when a term has three or more characters, then newest. When `classification::Controller::query_vector` can embed the query, reciprocal rank fusion (k = 60) merges the first 200 text matches with semantic hits; later text matches follow in text order and are excluded from the fused head, so every text match appears exactly once and `total` counts the fused head plus the remaining text matches. Semantic hits compare the query vector with latest-revision vectors (the feed's for a feed notice, the selected local embedding model's for any other), within the newest `SIMILARITY_WINDOW` (2000) notices that pass the source/category/saved/unread filters, and keep at most 20 hits scoring at least 0.20 and within 0.08 of the best (measured on synthetic fixtures; see `docs/AI_EVALUATION.md`). A damaged vector or another dimension only drops that notice from the semantic side. `meaning_only` lists hits that match no term; the list marks them **검색어는 없지만 뜻이 비슷한 공지**. The query is embedded with Qwen3's web-search instruction (`SEARCH_INSTRUCTION`), not the classifier instruction the stored vectors carry. It runs only when classification is on and the selected local model is installed and not failed; no model, a paused classifier (maintenance) or a busy inventory/backend operation, search is text-only. Embedding holds the classifier batch guard, starts the embedding process on demand (it unloads after a minute idle like classification), and caches the last query vector so paging does not re-embed it. Semantic search never feeds personalization, notifications or learned topics.

It runs after the article step and resource retry, and after every non-Cybercampus board run as a backfill of stored responses (`pdf_viewer_candidates`, no notice refetch, at most 10 PDF downloads per job; failed downloads wait for an explicit retry). A PDF without a text layer leaves the notice metadata-only with the PDF attached. A refetch keeps last-good content unless the viewer shows a PDF the notice never referenced.

## Cybercampus connector

`archive/cybercampus/` (#86) reads the logged-in user's own eClass (ilos LMS) data. Its request flow follows [rycont/eclass-cli](https://github.com/rycont/eclass-cli) (used with its author's permission under MIT terms); the Rust parsers are a port onto `scraper`, checked against pages captured from one account on 2026-11-06 and covered by synthetic fixtures (`archive/cybercampus/fixtures/README.md`).

- **Source and data model.** One catalog source, `cybercampus` (family `cybercampus`, owned by the `cybercampus` extension), so subscription, `archive_start`, the scheduler, cancellation and status are the archive controller's: `Controller::execute` dispatches the family to `cybercampus::sync` instead of the list/detail pipeline. Course notices are ordinary documents with `external_id` `<course key>-<notice seq>` and `category` = course name; their attachments (`/ilos/co/efile_download.acl`, which redirects to `/ilos/co/file_download_v2.acl`) and editor images (`/ilosfiles/editor-file/`) download with the session through the shared `install_resource` step (same size caps, format checks and hash paths); images on other hosts are recorded as unsupported. Courses and deadlines are not notices: `cybercampus_courses` holds the synced term's courses and `cybercampus_tasks` holds assignments (list + detail page: open date, deadline, late deadline, submission status/time) and the site's TODO items of other kinds (quizzes, lectures), keyed `(course, category, item)`, `pending` when the TODO list shows them.
- **Sync.** Terms come from `YearInfo` on the course-registration page; the newest of the first three terms that lists courses is synced (TA rooms and past terms are not). Per course: enter the room (`eclass_room2.acl`, which sets the session's current course), read every notice-list page (`start` is a 1-based row offset, 20 per page, at most 25 pages), fetch a notice only when it is new or its list title/preview fingerprint (stored in `documents.modified_at`) changed, then its `efile_list.acl` fragment; read the assignment list and fetch a detail page only for open or not-yet-stored assignments. One TODO request covers all courses. A failed course keeps its stored rows and the job reports it. The first successful sync archives notices as historical and sets `seed_complete`, so it never announces existing notices. eClass dates without a year (`10월 23일 (금)`) take the course year or the next one, whichever matches the shown weekday.
- **Session and credentials.** `client.rs` sends requests only to `https://eclass.sogang.ac.kr` on fixed read-only routes (plus `/ilosfiles/editor-file/`), with pinned public DNS, no proxy, the archive TLS chain completion, manual same-origin redirects (cookies kept per hop), a 700 ms gap, 30 s per request and 4 MiB page / 20 MiB file caps. Cookies stay in process memory. The login (학번 + SAINT password) is stored only in the OS credential store (`credentials.rs`, service `io.github.hiyabye.rhythm.cybercampus`), never in SQLite, backups or logs, and is sent only to `/ilos/lo/login.acl`. A redirect to the login page or a login form body means the session expired; the request logs in once more and repeats. When eClass rejects the login, `rejected` stops every further automatic attempt until the user saves a login again, so a changed password cannot lock the account through scheduled syncs.
- **Read-only boundary.** No submit, post, delete or confirmation route is allowed. Fetching a notice counts as a view on eClass, as opening it in a browser does; unchanged notices are not fetched again.
- **Privacy.** Cybercampus documents are personal data. AI work on them is local only (the remote engine was retired, #226); local classification and search treat them like other documents.

## Studium seat checks

`studium/rooms.rs` defines seven fixed room identities and capacities. `studium/parser.rs` is independent of transport, SQLite and the UI; it decodes bounded UTF-8/CP949 bytes and validates room identity, counts, every seat number and the school's own timestamp. Optional normalized marker origins are parsed in `parser_layout.rs`. `StudiumView.svelte` owns the selected-room editor, per-room progress, displayed room, count/number results, favorites and alert rules; `StudiumSeatMap.svelte` displays the optional geometry. Seat collection is separate from the notice archive and AI; seat alerts share the existing notification permission, quiet-hours and rate policy.

`storage/studium.rs` persists one to seven unique selected room IDs, a display room belonging to that set, and the automatic interval (schema 27, default 5 minutes, integers 2–60). Saving the set adds targets, chooses a valid display room, then removes excluded targets in one transaction. Removing the current display room falls back to the first selected room in catalog order. Input or write failure preserves the previous preferences. The display room and interval may change during a check; the selected set may not. Disabled-extension writes are refused.

Schema 28 stores preferred seat numbers separately by fixed room ID, including rooms not in the selected lookup set. `studium_save_favorites(room_id, seat_numbers)` validates unique integer numbers from 1 through that room's capacity, then transactionally replaces only that room's preferences; empty input clears them. Reads skip a stored number above the current catalog capacity, and an alert rule whose minimum exceeds it reads as off at that capacity, so a later capacity reduction never fails the page; the stored row stays until a changed save replaces it. Migrations 028/029 still pin capacities in their CHECKs, so changing a room's capacity needs a table-rebuild migration. Edits are allowed during a check or automatic session and start no request. `Snapshot.favorites` contains all seven room keys with sorted arrays, empty when unconfigured. Only these user preferences persist, not observed availability. The UI accepts comma/whitespace-separated numbers with explicit save/cancel, preserves an edited draft across polling and save failures, and resets unsaved favorites and search when the viewed room changes. Exact single-number search filters the current validated empty-number list locally while leaving the total remaining count visible. Favorites intersecting that same list receive a star and emphasis. Count-only, failed and unchecked results never establish preferred-seat availability or a zero search result. Old results explicitly label highlights and search counts as a previous observation, with current availability unknown.

`studium/controller.rs` owns one job shared by manual and automatic checks and its bounded, per-room memory results. A start clears the selected rooms' old values and marks them `loading`; one common-status request is followed by one detail request per selected room, in sequence. A validated detail response supplies its own counts, numbers and timestamp together, even when its counts differ from the common page. An invalid or older detail response leaves only validated common counts (`count_only`, numbers absent); access denial is an error. Common-page failure clears the selected rooms, and a room failure clears that room while preserving other rooms' successes from this job. Validated zero remaining seats has an empty number list; unknown or failed results have no counts. Cancellation preserves completed rooms and clears unfinished rooms. Job identity prevents old cancellation or completion from changing a later job.

`studium/controller/automatic.rs` owns a session-only timer, off at every launch. Explicit automatic start admits an immediate check, or adopts an existing manual job without replacing it. Every later deadline is measured from the latest check's completion; a manual check while automatic mode is waiting resets that gap. Missed intervals do not accumulate. The monotonic clock stops during macOS sleep, so the waiting timer also wakes every 30 seconds and runs once the shown wall-clock `next_check_at` has passed; a clock moved backward never postpones the monotonic deadline. Backup, restore or update ends an unpaused session with one explicit error, whether the timer was waiting or had just reached the closed gate. Saving an interval starts no request and leaves the current reservation unchanged; the new value applies after the next completion. A waiting timer holds no admission lease. Each actual check uses the same Store/admission/controller boundary and lease as a manual job. Pause cancels and joins the timer and its automatic job outside the Store lock while preserving any manual job. HTTP 401, 403 or 429 stops the automatic session and exposes an error instead of repeatedly retrying it; the controller decides by the HTTP status carried in `network::FetchError` (the transport error type), never by its message text. `Snapshot.running` describes the current check; `automatic.active`, `next_check_at` and `error` independently describe the session.

The states are `not_checked`, `loading`, `ready`, `count_only`, `failed` and `cancelled`. Source time is interpreted as KST and stored in memory as UTC; responses more than 300 seconds old or 60 seconds in the future fail validation. The UI reevaluates age while displaying a result. Receive time never replaces a missing source timestamp. The fetched HTML never enters the WebView or persistent storage.

Enabling the extension, opening its page, changing preferences and app startup cause no seat requests. UI polling reads local status every 500 ms only while a check is running; between checks, including automatic-mode waits, the page and mini view refresh on `studium://state-changed`, which the display worker emits after every controller change even when the tray update fails. The mini skips hidden-document polls, and interval, favorite and alert drafts survive these reads. Idle views also react to local state-change events. Disabling signals cancellation under the Store lock, then waits without it, closes the mini window and clears results; room preferences, interval, favorites, alert settings and window geometry stay. Maintenance and exit stop and join the timer, check, display worker and notification handoffs/callbacks before proceeding. Maintenance recovery, re-enable, reopen and restore never restart automatic checks, reopen the mini window or evaluate old results for alerts. Reopen/restore starts with no seat results or map; backups include settings, mini-window geometry and minimal alert dedupe/rate state, with no automatic enablement or seat observations. Activation tokens are invalidated on startup and restore. Predictions and reservations are not implemented.

### Studium seat map

The same validated detail response supplies counts, empty numbers, source time and optional `SeatData.layout`/`layout_error`. `parser_layout.rs` accepts all catalog seats as unique `Layer<number>` divs sharing one parent, with bounded absolute `left`/`top` values in CSS pixels. Values are exact integer thousandths of a pixel, at most 8192 source pixels; minima are subtracted from both axes, positive extents are checked and marker coordinates remain on the same scale. Duplicate IDs/positions, missing seats, mixed parents, unknown units or malformed coordinates reject geometry without discarding that response's verified counts/numbers. Wrapper width/height do not define physical seat size. An older, invalid or wrong-room detail still uses the existing count-only fallback with no numbers or map. No extra URL or HTTP request is added.

The main view's map is collapsed initially and renders normalized numbered SVG text markers only: ○ empty, × occupied, ★ preferred and bold underlining for an exact empty-number search match. Color never carries the state alone; all numbers retain contrast. It draws no physical seat outlines, walls or doors, and never executes the source HTML/CSS/scripts. The numeric list remains the alternative, and the map has an accessible count summary and one named keyboard scroll region instead of hundreds of tab stops. A 24-pixel margin prevents endpoint labels from clipping. Zoom is bounded to 50–200%; zoom, native scrolling, reset and search are local-only and write no settings. Room/job/source/receive identity changes reset the collapsed view and zoom, while same-result status reads preserve them. Removing focused controls restores the map toggle or connected room heading without taking focus from another control or page. The map labels source time in Korea using the selected 12/24-hour format and stale geometry as historical. Layout errors preserve the original number/count display, and coordinates/results remain memory-only. The mini view stays a summary.

### Studium seat alerts

Schema 29 keeps per-room rules independently off by default: `remaining >= minimum` or at least one preferred number in the verified empty-number list. Fresh successful manual and automatic results are eligible; `count_only` supports the count rule, while failed, unchecked, stale or unknown preferred-number results neither qualify nor rearm a prior alert. The first qualifying observation may reserve one attempt. Only a later successful non-match rearms that room; failed observations preserve its latch. Changing a rule or its preferred numbers increments its version, rearms future observations and invalidates old room tokens, but does not evaluate existing results or send. UI edits use explicit save/cancel and preserve drafts across polling and failure.

`studium/notification.rs` owns transient candidates, bounded native-response waits and one-shot pending activation. It admits no notification handoff without the Studium and proactive extensions, global notification enablement and native authorization. Source freshness, current controller generation/cancellation and rule version are rechecked at handoff. Quiet hours use the existing local-clock policy; attempts share the proactive monotonic rate clock and combined limit of three per ten minutes. Quiet-hours/rate rejection leaves the latch available for a later fresh observation, rather than replaying old seat data. Under the Store lock, reservation writes the attempt, consumes the latch and creates a hashed 30-minute one-use capability before OS handoff. A failed or uncertain handoff after reservation remains consumed and is never automatically retransmitted. Attempt accounting is pruned after seven days; live tokens are capped at 64. No counts, observed numbers, source times, HTML or seat history are persisted.

Windows uses the existing verified install identity and sender with the separate `rhythm-win://studium/<token>` target; macOS uses its native sender response. Valid activation consumes the token, rechecks enablement/rule version/selected room, persists the displayed room and emits `studium://notification-clicked` with that room ID. `App.svelte` subscribes before reading `studium_notification_activation`, queues a click before its core snapshot is ready, and ignores an older fallback response after a newer event. Every valid click can refresh the open Studium page, including another click for the same room; no new seat check or alert starts. Native callbacks, disable, maintenance and exit share final cancellation boundaries. Actual OS display/click and macOS compilation of this seat-alert path remain unverified; mocked senders and IPC do not establish them.

## Synchronization, scheduler and lifecycle

`archive/sync.rs::Controller` admits one archive or resource-retry job at a time. Since #178 it collects only Cybercampus, the one source the app still fetches itself (`archive::app_collected`): `archive_start` refuses a request naming a public board (no IDs means Cybercampus), and its modes are `refresh`, `incremental` (the scheduler's), `resources` and `skipped` (a no-op for Cybercampus, whose skipped notices are listed again by the next sync). Public boards arrive only through the feed; their bodies and files come from opening a notice ("Body on open", "Files on open"), and `archive_retry_resource` still retries one file of any notice, filling a metadata-only PDF-viewer notice's body from a retried viewer PDF. A v1 PDF-viewer notice whose PDF was never downloaded gets the file on open but not its text. Admission keeps the source only when it is subscribed and its owning extension (`source_extensions`) is on, under the same store lock that disabling uses. Disabling a source extension sets the controller's cancel flag under that lock and admission resets it only for enabled sources, so commit boundaries check the flag alone. The running source has its own cancel flag: unsubscribing it (`archive_subscribe`) stops the sync, recorded `cancelled` but not a job failure, while job cancellation and extension disabling also set the job's flag. Settings groups (`archive/catalog.rs::groups`, stored in `source_groups`) nest public boards; Cybercampus has none. A grouped board is subscribed only when its pick (`selected`) is on and every enclosing group is on; `Store` recomputes that in `sources.subscribed` whenever a pick, a group or the catalog changes, so the scheduler, ranking and notifications read only `subscribed`. A pick under a group that is off is refused. `SyncStatus.active` lists the source collecting now.

**Public-board crawl rules.** The collector (`crates/collector/src/crawl.rs`, a port of the app's crawler, which #178 removed) is their only implementation; the app keeps the parsers, robots policy and transport it fetches opened notices with.

- **Historical:** start at the persisted `next_page`, follow public pagination, deduplicate pins and IDs (a page listing the same IDs as an earlier one stops the board, unless it lists only pins: a board whose newest notices are all pinned shows the same pins on several pages), and checkpoint only after no article on the page failed transiently (see below). Existing text is not refetched. `history_complete` becomes true only at the last public page, never at a safety or test limit.
- **Incremental:** start at page one and recheck recent pages and pins with ETag/Last-Modified validators. The recheck window is the first three pages, capped at 30 regular rows (#80: the main site's 50-row pages read only page one); known notices past it are not refetched, and discovery continues past it until a page of known regular records marks the frontier. Repeated pins never establish the frontier. k2web lists show each row's title and the CMS honours no validators, so a known k2web notice in the window is refetched only when its listed title differs from the stored one (lists cut long titles at about 44–50 characters, so a listed title that begins the stored one counts as unchanged) or it was reported missing or removed; body-only edits arrive through the deletion audit (user decision, #80 step 3: re-reading the window of every k2web board on their one server would take about 49 minutes per run).
- **New boards:** at most `NEW_BOARDS_PER_RUN` (20) boards that never finished a first pass start per run, in catalog order; the rest wait without a health row, so adding many boards at once never pushes a run past its timeout (user decision, #80 step 3).
- **Per run** (#80, user decisions 2026-11-22): every board's incremental pass and upkeep run first, so new notices never wait for a backfill. The history phase follows for boards whose incremental pass succeeded and whose `history_complete` is false: boards on one server take turns of at most `--articles` notices, least progress first, and servers take rounds in turn (a server never holds a worker for the whole window), until `--history-minutes` after the crawl started. A turn the deadline stops records `limited` and keeps its checkpoint; it is not a failure. Boards are grouped by server (see the transport below), one board per server at a time.
- **First incremental seed:** with no local documents, fetch at most three pages as historical records, without counting them as new or marking history complete.
- **Scope:** incremental sync is not an audit of every old edit; the collector's deletion audit is separate.

**Article failures.** A *transient* failure (network, deadline, server error, cancellation, redirect, or a response of the wrong content type, which is more likely a block page than the notice) holds the page checkpoint, fails the board and is retried on the next run. A notice that fails transiently on three runs in a row (failures at least ten minutes apart, `transient_failures`, user decision 2026-11-23) is recorded as skipped instead, so a page that times out on every run cannot stop its board for good. A *permanent* failure belongs to the fetched response: the body does not parse or its encoding is unsupported. It is recorded as skipped (reason and response SHA-256), any last-good content stays, and the checkpoint advances, so one bad notice cannot stop a board. A later fetch that archives or confirms the notice removes the record. Passes leave a skipped notice to the collector's daily retries (AGENTS.md), except that the history pass refetches one an older collector `VERSION` skipped, so a parser fix reaches the skipped notices at or past the history checkpoint within the history budget; for the incremental frontier a skipped notice counts as known, so it never pages a pass into unimported history (which would fetch old notices as new). A retry that fails transiently uses an attempt and waits another day; in the app only Cybercampus records skipped notices (`skipped_articles`), listed per source (count plus the 20 most recent).

Counters describe the current attempt; checkpoints are cumulative. A resource failure is nonfatal to article archival but surfaces as a failure on explicit retry. Completing pagination does not promise every resource was downloaded.
The scheduler (`proactive/scheduler.rs`) is an in-process Tokio task that wakes every 15 seconds, not an OS service. When enabled and unpaused it reconciles a task for each app-collected source (Cybercampus) that is subscribed with its owning extension on, while the `proactive` extension is on, and runs due sources sequentially with incremental sync. Public boards have no task (migration 040 deleted the old rows), so the interval and energy profile apply to Cybercampus alone and the feed keeps its own 30-minute cycle. Interval `0` follows the energy profile (Eco/Balanced/Performance: 60/30/15 minutes); explicit intervals are exact values from 15 to 720 minutes. Retry interval is 5–120 minutes (default 15). Outcomes, next-run times and errors persist. Disabling, pausing, changing subscriptions or the extension, and shutdown all cancel work. Nothing runs while the computer sleeps or the app is closed. Scheduled results are tied to the admitted controller task, and the scheduler keeps servicing notification discovery while an import runs, without starting a second archive job.

`core/lifecycle.rs` owns tray, window and login behavior. Every lifecycle feature defaults off. Login registration changes only on explicit user action, is checked against actual OS state and rolls back if persistence fails. The registration is named after the bundle identifier: the production identifier keeps the entry released builds already created (macOS `Rhythm.plist`, Windows Run value `Rhythm.io.github.hiyabye.rhythm`), and every other identifier gets its own entry, so a validation or test build cannot read, replace or delete the installed app's login registration. A login launch honors hidden start; a manual launch stays visible unless `--hidden` is passed. Close-to-background works only if the tray installed; otherwise closing quits. Exit signals scheduler and archive cancellation, waits without holding SQLite, then stops the worker.

Every feature beyond the core shell (Today, 일반, 데이터 및 정보, 확장 기능) is a built-in extension in `extensions/mod.rs`; nothing is loaded from outside the app. Each is opt-in, and its flag lives in `extension_preferences`. Turning one off keeps its durable data and preferences:

## Notifications

Notifications are opt-in and independent of the scheduler. Discovery runs after archive commits and on every scheduler wake, after the feed sync, so feed arrivals become candidates like collected ones (#177). Candidate identity is document + revision + kind. Migration 005 set a revision ceiling so upgrades never announce old notices; a historical first seed is excluded, but a later meaningful revision of an old notice can qualify. A revision qualifies only when its title or body differs from the previous revision. Two archived bodies compare as text (HTML or text); beside a feed revision not yet opened, which holds only the excerpt, they compare by `body_hash` (migration 039, feed format 1.1), or by the first 320 characters when either revision has no hash (a 1.0 publisher, or archived before 039). A candidate of an inactive source (unsubscribed board, extension off, notice in 휴지통) gets only a dedupe row, no history event: the feed mirrors every board, so suppressed events would crowd real decisions out of the bounded history, and the dedupe row keeps it from replaying once the source is active (user decision, 2026-11-20). Policy, source and negative-interest checks repeat before delivery; rejections are stored as `suppressed` with a reason. Events reference archive identities and read titles from archived revisions; no notice body is copied.

| Setting | Values |
| --- | --- |
| Sensitivity | `important` (preferences and score ≥16), `interested` (explicit-interest match), `all` (any eligible item). Negative feedback or negative-interest matches always suppress |
| Quiet hours | Local wall-clock range (default off, 22:00–07:00); eligible events are deferred, not consumed |
| Rate | At most three attempts per ten minutes, bounded candidate batches |

Event states: `pending → claimed → attempted | deferred | failed`, then `delivered` after activation confirmation, or `suppressed`. Claims have a five-minute lease; delivery attempts cap at three with capped exponential backoff (maximum four hours). Schema 6 reserves rate slots in a durable ledger before handoff, so clearing or pruning history never resets rate accounting or dedupe. A crash between reservation and handoff can use a slot without a visible notification. A backward clock change pauses the watermark until wall time catches up.

- **macOS:** native UserNotifications through the async `mac-usernotifications` 0.3.1 sender. A handoff is only `attempted`; an event is `delivered` only after the activation response. Responses are processed independently of the scheduler's delivery cycle: each alert closes itself after 30 minutes and at most 12 responses are tracked, so an ignored alert cannot stall later work. Authorization status maps not-determined/denied/authorized/provisional/ephemeral (timeout or error = unavailable). Denied or undetermined permission blocks attempts, but quiet-hours deferral still applies.
- **Windows:** WinRT toasts with the installed AUMID and protocol activation (`rhythm-win://notification/<token>` for production, `rhythm-win.<identifier>://notification/<token>` for non-production builds via `core::windows_identity` and `scripts/installer-hooks.nsh`, which also isolate the AUMID, `<productName>.lnk` shortcut and `Run` entry and refuse non-production installers using `productName: "Rhythm"`); the protocol registration must resolve to the expected executable first. Status is authorized/denied/unavailable from notifier settings and install identity; there is no prompt, and the explicit button sends one test notification. The final policy check, token creation, attempt reservation and synchronous handoff share one store lock. Schema 7 stores only a hash of the random, expiring, one-use token bound to the event attempts; a validated click for the current attempt marks delivery. Discovery claims nothing unless authorization is `authorized`. Clicks during shutdown are refused, and restore clears tokens in staging.
- **Other hosts:** no sender; status is unavailable.

**Todo reminders (#189).** The scheduler loop checks reminders after notice delivery on every pass (and every 15 seconds during a sync) while notifications are on, with no scheduler enablement needed. `Store::calendar_due_reminders` lists todos not done whose reminder moment (time, or 09:00 for an untimed todo, minus `reminder_minutes`) has come while the todo itself is still ahead: its time, or the end of its untimed day. A reminder missed while Rhythm was closed is therefore sent late only within that window and silently dropped after it. `calendar_reminder_reserve` repeats the calendar, notification, quiet-hours and todo checks and the shared three-per-ten-minutes limit under the handoff's Store boundary, then records the attempt, a click token and the `reminder_sent` latch together; a reminder held back stays due for a later pass, and a reserved one whose handoff fails is not sent again. Editing the day, time or reminder clears the latch. Each reminder is its own notification (`할 일 알림`, title and day/time in the 12/24-hour setting). macOS uses the same async sender and bounded response tasks; Windows uses `rhythm-win://reminder/<token>` with the synchronous handoff under the Store lock. A click consumes the token, restores the window and emits `calendar://reminder-clicked` with the todo's current day; `calendar_reminder_activation` is the one-shot fallback before the listener exists. Tokens are cleared at startup, on restore and when the calendar or proactive extension turns off.

A click restores the existing window and emits `proactive://notification-clicked` with stable archive identities. The main-window capability grants only event `listen`/`unlisten`; `App.svelte` unlistens on teardown and falls back to a one-shot snapshot activation if the click arrived before it subscribed. `ProactiveSnapshot.notification_permission` stays `"unknown"`; Settings uses the separate authorization commands. Notification text includes the source name and title. No AI request is involved.

## Transport, resources and safe rendering

The transport (`rhythm_sources::transport`, re-exported as `archive::network`) uses Reqwest/Rustls. Automatic requests need exact approved HTTPS hosts and routes on port 443 (main, Computing, Engineering, the Electronic/System Semiconductor community boards, the k2web CMS boards on `new-cms.sogang.ac.kr`, the Mechanical sitemap/article routes and the Semiconductor board list/detail, filedown and editor-image routes). URLs with credentials, fragments or unsafe encoded separators are rejected. DNS answers must be public and are pinned per connection; proxies and automatic redirects are off. The sync policy layer follows at most three same-origin redirects, re-running URL/DNS/TLS checks and robots authorization before each hop; transport only returns redirect targets. HTTP(S) resource references are kept as metadata so an old HTTP image doesn't discard the article, but only approved HTTPS routes are downloaded. Main images under `/dataview/board/<id>/<file>.(png|jpg|jpeg|gif|webp)` are an approved route, as is `scc.sogang.ac.kr/Download3` with exactly the PDF-viewer query above (other `scc` routes, including its HTTP article images, are not). The community hosts approve only their `/kor/community` (and ee `/kor/recruit`) article pages plus ee `/aseoul_bbs/down.php`; their robots-disallowed `/se2/`, `/data/` and sse `/bbs/` routes are never requested, so those resources are recorded as unsupported. The Cybercampus connector does not use this transport; its session client applies the same DNS, proxy, redirect and TLS rules to its own fixed eClass routes (see above). Requests carry an access mode: `Source` allows only those routes; `EmbeddedImage`, used for image resources only, also allows any other public HTTPS host name on port 443 (no IP literals, no other `*.sogang.ac.kr` route). Each such origin's robots.txt is loaded once per job and cached (including a failure); a 4xx robots.txt from such a host means no rules (RFC 9309), while a school host's error stays fatal. Third-party attachments are not downloaded.

Requests are paced per server (#80): a server, identified by the lowest of the public addresses its host resolves to, gets one request at a time, each started at least 650 ms after the previous one, whatever hostnames it answers for (`ee` and `sse` share one); the gate is held until the response headers arrive. Different servers do not wait for each other, and one client has at most three requests in flight. `robots.txt` is checked before collection (plain-text Accept header; Computing returns 406 otherwise); allow/disallow rules with wildcard and end-anchor matching and crawl delays up to 60 seconds apply, and a malformed delay in a group that applies to Rhythm or an HTML error page fails closed (a group for another agent cannot fail the policy). `scc.sogang.ac.kr` serves its robots.txt as unrendered ASP source that picks rules per host name; for that host only, `<% … %>` code blocks are removed and the rules of every branch apply (stricter, never looser; an unclosed block fails). Transient errors get at most three attempts with short backoff and cancellable waits. Each attempt has an 8 s connect deadline, 20 s for the response headers and for any pause within the body, and 90 s for the whole body (pages of 1–2 MB took over 20 s from the collector's GitHub runner); a 120 s bound covers the attempt including the pacing wait. A deadline is reported as a timeout, not a dropped connection. HTTP 429 from a board's own host stops that board with a message instead of requesting the rest of the page; the notice and its files stay as they were for the next run. An attachment whose name has no supported document/raster extension is recorded as unsupported without being requested, and an unlisted file type never keeps a notice's text out of the archive. No login, access restriction or anti-bot bypass is used.

Studium uses a separate `Access::Studium` mode, restricted to `https://libseat.sogang.ac.kr:444/robots.txt`, `/SEAT/domian5.asp` and `/SEAT/roomview5.asp?room_no=<fixed room ID>`. This permission does not widen `Source` or `EmbeddedImage`. `studium/network.rs` checks robots for that origin, shares transport public-DNS pinning, pacing, cancellation and deadline protections, caps each page at 1,000,000 bytes, and refuses redirects and unexpected response types. Each transport call has one attempt. With automatic mode off a failed manual check is not repeated; automatic mode waits the normal completion gap after ordinary failures and stops entirely on 401/403/429. No login or access-control bypass is used.

For the seat origin only, Reqwest uses native TLS with a minimum of TLS 1.2: Schannel on Windows and Secure Transport on macOS. Hostname and certificate-chain verification stay enabled, but the OS root store is replaced by one pinned root, Sectigo Public Server Authentication Root R46 (`crates/sources/src/certificates/README.md`), so roots installed by the user or other software cannot vouch for the server; the app changes no system policy and never accepts invalid certificates. A move to another CA fails closed until the pin is reviewed. This supports the server's legacy CBC-only cipher negotiation while retaining the fixed URL and pinned connection destination. OS trust and cipher policies can still reject it, and live compatibility is a separate claim on each platform. Other clients explicitly keep Rustls, including model downloads: enabling Reqwest's `native-tls` feature must not silently change their default backend. The seat origin does not use the archive intermediate-chain supplement described below.

### TLS chain completion

`www.sogang.ac.kr`, `new-cms.sogang.ac.kr` and `eclass.sogang.ac.kr` omit their intermediate certificate. `rhythm_sources::tls` adds two bundled public intermediates as **untrusted candidates, only for those exact hosts**, then delegates all checks to WebPKI. The root store stays exactly Mozilla's `webpki_roots`; hostname, validity, signature, usage and path checks stay mandatory. No other host gets candidates. There is no invalid-certificate acceptance, new root or system trust change. Provenance and fixed-time tests are in `crates/sources/src/certificates/README.md`.

### Resources

Limits: 4 MiB per list/article response (16 MiB for a main-site or k2web notice, whose inline `data:` images the sanitizer drops; `parser::article_limit`, #80; the collector records a notice over its limit as skipped rather than letting it hold the board's history), 10 MiB per inline image, 20 MiB per attachment, 256 MiB of completed resource bytes per job (charged before validation or disk writes; when the remaining budget, not the per-file cap, bounds a download, a size failure leaves the file `pending` for a later run), 64 KiB for robots, and a 100,000-page safety ceiling. Test budgets report `limited`, never complete history.

Resource URL, original filename, kind, MIME, bytes, state and SHA-256 are kept. Files use generated `resources/<sha256>.<validated-extension>` paths, never remote filenames, and are written through a `.part` file before SQLite references them. Images need PNG/JPEG/GIF/WebP signatures, PDFs a PDF signature; attachment extensions are restricted and active web types rejected. This is format validation, not antivirus scanning. Files are never opened or executed automatically; reveal only selects them in Finder or Explorer.

The `resources` sync mode ("자료 모두 내려받기", Cybercampus only) downloads `pending`/`failed` files of each subscribed board's current revisions, newest notice first, until the job budget is spent; like `skipped`, it leaves board status, counters, checkpoint and last success unchanged.

Local reads check containment, bound size and verify the stored SHA-256. Retry repairs corrupt bytes; a failed refresh keeps the last verified copy. There is no remote-image fallback. Cleanup of unreferenced files and storage quotas are not implemented.

The Rust sanitizer keeps a limited structural HTML subset, strips scripts, iframes, forms, styles and event attributes, and emits image references without `src`. Recursion stops at depth 64: a deeper subtree (legacy editors nest tables about 130 levels) is rendered iteratively as one block of its text and images without structure. More than 50,000 nodes is a parse error. `DocumentReader.svelte` builds a second restricted DOM, requests only integrity-checked local raster data URIs, and sends HTTP(S) links to the OS browser on explicit action. Missing or corrupt images become placeholders with repair actions. A failed automatic read-state write never hides content. CSP is an extra layer, not a replacement for the sanitizer.

## Managed models and downloads

`intelligence/models/` owns curated downloads, separate from notice transport. `catalog.json` pins one entry, the Qwen3-Embedding 0.6B Q8_0 revision, file, size and SHA-256 (see [AI evaluation](AI_EVALUATION.md#pinned-artifacts)). One-click installation accepts only `verified` entries. Inventory rows don't depend on the catalog: a row whose entry was removed (the retired generation models, #226) still opens, removes and restores, and the UI lists it as no longer offered; its bytes are never deleted implicitly.

Vision projectors are no longer installed. A retired model's `ai_projectors` row and managed bytes are removed with the model, and restore marks a projector `missing` unless its file is still present with the recorded identity and its model remains installed in this installation.

Downloads use HTTPS to exact approved Hugging Face/CDN hosts with pinned public DNS per hop, normal TLS, no proxy and at most five reviewed redirects. A disk check reserves 1 GiB beyond the remaining bytes. Paths are generated: `models/<sha256>.part` and `models/<sha256>.gguf` under the default folder or the model's recorded custom destination (`model_storage.rs`). Resume needs a strong ETag, `Range`/`If-Range`, an exact `Content-Range` and the expected remaining size; a full `200` restarts. Files sync and pass GGUF preflight, exact size and committed SHA-256 before an atomic rename.

`ai_choose_model_directory` opens the native folder picker, validates the folder and write access, then saves it; cancelling changes nothing. On Windows any link or junction in the path is rejected; on macOS only a linked selected or `models` folder (system links such as `/var` are canonicalized). A new download captures its destination; existing and interrupted downloads keep theirs. A pre-existing final file in a chosen folder is adopted only if that inventory already received every byte, so removal never deletes bytes Rhythm didn't write. Both folder commands share AI/maintenance admission; `ai_preferences` cannot change the folder.

External GGUF registration was retired with summaries; an existing external reference can still be unregistered, which never deletes its bytes. Preflight accepts GGUF v2/v3 `qwen3` (the embedding model) and the retired `qwen35`/`gemma4` metadata; it is not full tensor or runtime validation. Managed removal stops the embedding process first when it may map the file, checks containment, removes partial files first, records `missing` before the irreversible unlink and reconciles failures; documents stay. The classifier verifies the complete file once per model identity before its first use; the `sha2` assembly feature (macOS aarch64 only) speeds hashing but never replaces it.

## Inference process

`intelligence/server.rs` supervises upstream `llama-server`, bundled as Tauri resources under `llama/` and pinned to one llama.cpp build with per-archive size and SHA-256 (`scripts/llama-cpp.json`). `Worker` in `intelligence/mod.rs` owns it for the classifier, which is its only user. No process runs until the classifier or a search query needs one.

A load starts `llama-server -m <model> --no-webui --no-slots -np 1 -c 8192 -lv 4 --embedding --pooling <model> --embd-normalize 2 --batch-size 2048 --ubatch-size 2048` with all layers on the GPU (macOS Metal), or `-ngl 0 --device none` for CPU. The server listens on `<data>/run/embedding/llama.sock` inside a `0700` directory. When that path exceeds the 103-byte Unix socket limit, or on Windows, it listens on 127.0.0.1 with an OS-chosen port read from its log, and a random key in a `0600` file (deleted once the server is ready) is required on every request. The supervisor waits up to 180 s for `GET /health`, then reads the device and offloaded layer count from the log to report the loaded backend.

Requests are one HTTP/1.1 exchange per connection to `/v1/embeddings`, with a 120 s deadline and a bounded batch of 32 inputs of at most 8 KiB. Responses need an exact `Content-Length` and are bounded to 4 MiB; a malformed, duplicate, non-finite or wrong-length vector rejects the batch. Stdout is discarded; stderr is drained as bounded diagnostic lines.

A failed request reaps the process and the next one starts a fresh one; a late response is never reused. A crash is observed on the next status or request and never blocks archive or settings access. On Windows the process is in a kill-on-close job object. On macOS nothing ends a child with its parent, so SIGTERM, SIGINT and SIGHUP take the normal exit path, and the server's pid goes to `run/embedding/llama.pid`: at the next launch, after the data-directory lock, `stop_orphan` ends a server that a killed or crashed Rhythm left behind, only if its command line is a `llama-server` naming that directory (a reused pid is left alone), then deletes the file (#273). Inventory changes and the updater wait until the process is reaped (`stop_confirmed`).

macOS tries Metal first and falls back to CPU for the session after a load or request failure. Windows ships and runs only the CPU build.

## Embedding classification

**Feed or local (#177).** A notice the feed described (`from_feed`) takes its vector and category from `feed_embeddings`/`feed_classifications`; any other notice from the local model's `notice_embeddings`/`notice_classifications`. Only Cybercampus notices are embedded locally (#178); a v1 public notice the feed never described keeps the local rows it already has. A feed row counts while its scope names the feed model (`storage::intelligence::FEED_MODEL`), whatever its config hash, so a collector config change keeps working in apps not yet updated; another model leaves the feed notice unclassified (user decision, 2026-11-20). Local rows on a feed notice stay but are never read. The feed's int8 vectors are normalized on read and compared with local f32 vectors directly (the two encoders agree within the CPU-vs-Metal baseline, #170). Categories, the AI 분류 filter and similar/duplicate notices of feed notices need only the `ai` extension, no installed model; semantic search still needs the local model to embed the query.

`intelligence/classification.rs` runs the pinned embedding model in the bundled `llama-server` as a transient process and classifies the latest revision of each Cybercampus notice, using the contract in `crates/embed`. It embeds a bounded instruction + title + first 1000 body characters, compares the unit vector against authored Korean prototypes for the ten non-`기타` categories (학사, 수업, 장학, 연구, 학과 소식, 공모전·대회, 인턴·채용, 교육·프로그램, 행사·활동, 생활·시설), and stores the raw score/margin plus the prototype config hash. Prototypes are embedded with the same instruction prefix as notices; that instruction still lists the original categories because stored vectors and semantic search carry it. The best match below `0.68` becomes `기타` with a low-confidence marker; the raw score stays local and the UI only shows the category and a low-confidence hint.

Config identity covers the prototype text, input shape, scoring and threshold; stored vectors survive a config change and are reclassified without re-embedding. A model change is a different SHA-256 scope. Removing a model removes its derived vectors and classifications, never archive content. The classifier runs every five seconds while enabled, backfills existing latest revisions and picks up new ones, and never blocks collection. It yields while a model download or exclusive maintenance is active, and stops/reaps the embedding process after one minute without work. Migration 033 deleted vectors of the retired remote embedding endpoint, so such a profile classifies again only after the local model is installed. There is no network, categories never feed ranking or notifications, and nothing runs automatically before an explicit embedding-model install.

Stored vectors also drive similar notices and cross-post grouping, with no model call (`Store::ai_similar_notices`, #126). Candidates are the newest 2000 notices by publication date whose latest revision has a vector: the feed's for a feed notice, the selected embedding model's SHA-256 for any other (none without an installed model); vectors of other models or older revisions are never compared. A target outside that window still uses its own latest-revision vector. Cosine (the dot product of unit vectors) ≥ 0.75 is similar. A duplicate needs cosine ≥ 0.97, the same whitespace-normalized lowercase title after leading bracketed board tags (`[공지]`, `(학부)`, `<…>`, `【…】`) are set aside, and the same sequence of digit runs in the title and body (full-width digits read as ASCII), so a copy with another date, time or amount stays separate. One title's tags must contain the other's, so `[학부]` and `[대학원]` stay apart while `[공지][학부]` matches `[학부]` and an untagged title. Contact numbers are left out of the body digits so an appended contact line does not split a copy: area-code numbers (`02-705-8123`), standalone three-digit-exchange numbers (`705-8123`), and three- or four-digit numbers after `내선`, `☎`, `Tel`, `전화` or `연락처`. A four-digit pair like `2025-2026` counts only after such a word, so year ranges still compare. Dates written in words (`삼월`, `다음 주 월요일`) are not compared. Duplicates are listed first, then the remaining matches up to the limit. `ai_similar_notices` returns five matches for the reader; `ai_duplicate_notices` returns only duplicates for up to 200 visible documents. The cosine score stays local. In the archive list a copy on the same page folds under its first row, which names the other boards and expands to show it; nothing is removed. While collapsed, the leader shows as unread when a folded copy is unread, and its toggle and screen-reader text give the count. Thresholds are not measured on real notices. Apart from the capped ranking term in [Personalization and ranking](#personalization-and-ranking), which notification scores share, similarity never feeds ranking, notifications or learned topics.

## Energy policy

Energy profiles only pick the scheduler cadence when its interval is `0`: Eco 60 min, Balanced 30 min, Performance 15 min. No AI work depends on the profile; the classifier runs only after an explicit model install and stops its process after a minute without work.

## Backup, restore and updater

`.rhythm-backup` is a ZIP with `manifest.json` (version 1, located by name, written last) listing each payload path, size and SHA-256. Creation copies the database with SQLite's online backup API in one step while holding the store's only connection, and adds only database-referenced resources; `models/` is excluded and external models stay references. Each file is read once and every resource must match its recorded size and SHA-256. An interrupted backup's snapshot is removed at the next launch. The archive is not encrypted.

Restore needs an awaited native confirmation (`window.confirm` is an async shim in the desktop app and must not be used). It extracts into hidden staging, verifies SQLite integrity, foreign keys and resource hashes, reconciles models (a managed model stays only if its local file matches the restored size and SHA-256; custom-folder models become external or missing references, never deleted; the folder preference is cleared), clears Windows activation tokens, and writes a journal. Rhythm then exits instead of relaunching, because a relaunched instance can race the exiting process for the single-instance socket and data lock. The next manual launch runs `recover_pending_restore` before `Store::open`, finalizes idempotently and shows the outcome. An older backup is migrated on the next `Store::open`, so migration 033 runs again and removes a saved remote API key from the OS credential store. A recovery error shows a native dialog and exits, keeping the journal and previous data. The previous profile is kept in `.rhythm-restore-previous-*` under the data root. `stage_restore` is the whole pre-exit path and is what the ignored large-profile benchmark measures. Each extracted file is flushed with `sync_all` (`F_FULLFSYNC` on macOS); Unix also syncs directories after each rename.

On Windows, restore additionally requires a local fixed NTFS volume, rejects reparse points, junctions and Cloud Files sync roots, moves with `MoveFileExW` (no replace or copy fallback) and stops on ambiguous recovery artifacts. Without directory fsync it survives process interruption, not power loss.

Backup, restore and updater share an app-wide `AdmissionGate`: maintenance closes admission, cancels and joins scheduler, archive, Studium and AI work, then reopens. Reopening admission starts no Studium check.

The updater verifies Tauri-signed artifacts against a build-time public key and requires the signed version to match the manifest (`requireSignedVersion`). The plugin registers only when `RHYTHM_UPDATER_PUBKEY` is set at build time; otherwise Settings shows manual update steps (`updater_configured`). Errors are mapped to Korean (`update_error`). The single endpoint is the `latest.json` of the latest published GitHub release; its `darwin-aarch64[-app]` entries point at the signed `Rhythm.app.tar.gz` and its `windows-x86_64[-nsis]` entries at the signed NSIS setup executable. The updater signature is not OS code signing: Gatekeeper and SmartScreen still treat the builds as unsigned on first install. `updater_restart` holds maintenance admission (which keeps classification paused) and stops and reaps a running embedding `llama-server` before `install`, because the server runs from the install folder and the Windows plugin exits with `process::exit` (no `RunEvent::Exit`). Windows runs the NSIS installer in passive mode (`/P /UPDATE /R`). Install-location failures (read-only volume, translocated app, denied or cancelled authorization, an old bundle that could not be put back) map to Korean guidance.

Automatic checks (`run_auto_check`, keyed builds only, on by default) wake one minute after launch and then hourly, and check when the setting is on and the last successful check is a day old. They use a 30-second timeout, fail silently, keep the found update in `updater::State` and emit `updater://available`; the main window shows a dismissible banner that opens Settings → 데이터 및 정보. They never download or install.

## Packaging and CI

`src-tauri/tauri.conf.json` bundles `src-tauri/binaries/llama/` as the `llama/` resource directory. `scripts/stage-llama.mjs` fills it: it downloads the pinned archives for the host from llama.cpp's GitHub releases into `target/llama-cache/`, rejects any whose size or SHA-256 differs from the pin, and copies `llama-server` with only the libraries it loads (macOS) or with its DLLs plus the VC runtime it imports (Windows). `scripts/desktop.mjs` stages, then runs Tauri; it is not a cross-compilation helper. On Windows it delegates to `scripts/desktop-windows.mjs` (VC runtime, llama.cpp, NSIS); see [Windows](WINDOWS.md). Scripts never install toolchains or weights.

A default release build deletes `target/release/bundle/` and writes `target/release/distribution/`: the DMG or setup executable and its `.sha256`, plus the updater package files when both `TAURI_SIGNING_PRIVATE_KEY` and `RHYTHM_UPDATER_PUBKEY` are set (`scripts/updater-signing.mjs`). Release builds remap `$HOME`, `CARGO_HOME` and the checkout with `--remap-path-prefix`. `scripts/macos-release.mjs` (Developer ID signing and notarization) is kept for a possible future decision and refuses to run without credentials; `scripts/update-manifest.mjs` builds `latest.json` from the staged signatures and `scripts/verify-update.mjs` independently verifies signatures, the manifest, the macOS archive and the embedded public key.

`ci.yml` runs each concern once, gated by changed paths (`scripts/ci-changes.mjs`): frontend checks and Playwright on Ubuntu, `cargo fmt` on Ubuntu, and Clippy plus tests on macOS 15 and Windows. Release builds run only on `main` or manual runs when packaging inputs change. `release.yml` builds both platforms on a version tag with the updater key from the reviewer-gated `release` environment, verifies the updater files and `latest.json`, and creates a draft release; publishing it makes the update visible to installed apps. Normal tests are network-free; opt-in live, benchmark and model tests are listed in `AGENTS.md`.
