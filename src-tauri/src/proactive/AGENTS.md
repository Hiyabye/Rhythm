# Lifecycle, scheduler and notifications

Area instructions for `src-tauri/src/proactive/`, `src-tauri/src/core/lifecycle.rs` and `storage/proactive.rs`. The root `AGENTS.md` (project-wide rules) applies too.

- `src-tauri/src/proactive/`: `scheduler.rs` runs persisted source tasks while the app is open; `notification.rs` discovers, filters, batches and routes notification actions; `reminders.rs` sends due todo reminders from the scheduler loop. `core/lifecycle.rs` owns tray/window/login behavior; settings and durable event/task state live in `storage/proactive.rs` (with `storage/proactive/{model,tasks}.rs`) and schema migrations 005–007.

## Invariants

- **Lifecycle behavior:** All lifecycle and proactive features default off: autostart, hidden login start, close-to-background, scheduler and notifications. Tray installation failure leaves the app usable but must reject close-to-background. Login registration changes only after explicit user command, is checked against actual OS state and is rolled back if persistence fails; never infer OS registration from stored preference. The entry name comes from the bundle identifier (`core::lifecycle::autostart_name`): only `io.github.hiyabye.rhythm` keeps the released names (macOS `Rhythm.plist`, Windows Run value `Rhythm.io.github.hiyabye.rhythm`), and any other identifier gets its own entry, so a validation or test build never reads, overwrites or deletes the installed app's registration. On Windows (#70), `core::windows_identity`, `scripts/installer-hooks.nsh` and `scripts/desktop-windows.mjs` likewise derive the AUMID (`identifier`), protocol scheme (`rhythm-win` for production, `rhythm-win.<identifier>` otherwise), Start Menu shortcut (`<productName>.lnk`) and `Run` value from the build's identifier and product name, and refuse non-production installers that leave `productName` as `Rhythm`. Single-instance handling runs before data-directory lock/store initialization. A login launch honors `start_hidden`; ordinary manual launch remains visible, explicit `--hidden` applies only to manual launch. Shutdown stops scheduler work and joins/cancels archive work. Do not assert tray, login registration or notification delivery works on unobserved operating systems.
- **Scheduler:** This is an in-process task loop while the app is open, waking every 15 seconds; it is not a persistent OS background service and performs no work while Rhythm is closed. Persisted per-source tasks exist only for app-collected sources (`archive::app_collected`: Cybercampus) and are reconciled from its subscription, scheduler enablement and the owning extension being enabled; public boards arrive only through the feed, have no task (migration 040 deleted the old rows) and `archive_start` refuses them. Every wake also runs the feed sync when due (`run_feed`), independent of scheduler enablement and before the source tasks. Interval `0` selects the energy-profile default (Eco 60, Balanced/default 30, Performance 15 minutes); explicit intervals are exact values from 15 through 720 minutes. Respect pause, retry/backoff, cancellation, task outcome and source toggles. Keep archive work in one job at a time through the existing controller, and never hold SQLite mutex guards across async network/worker/filesystem work.
- **Native senders:** macOS uses the native UserNotifications APIs through the async `mac-usernotifications` 0.3.1 sender (vendored, see root `AGENTS.md`); Windows uses WinRT toasts with the installed AUMID and a verified per-user `rhythm-win:` protocol registration. Linux has no sender; do not imply a plugin-backed sender or support path. Request authorization only on explicit user action. Do not treat API handoff as evidence of OS authorization/display/receipt; keep to the native evidence and limits recorded in `docs/ROADMAP.md#verification-status` (repository root).
- **Notification pipeline:** Notifications are independently opt-in. Candidate/event identity is document + revision + kind. Feed arrivals are candidates like crawled revisions (discovery runs every scheduler wake, after the feed sync); a revision qualifies only on a title or body change, and beside a not-yet-opened feed revision (excerpt only) bodies compare by `body_hash`, falling back to the 320-character excerpt (`proactive_candidates`, #177). A candidate of an inactive source (unsubscribed, extension off, 휴지통) gets only a dedupe row, no history event (`proactive_pass_inactive`, user decision 2026-11-20); event states/attempts/defer/claim lease and dedupe survive app restarts, bounded history pruning does not permit replay. A migrated database establishes a revision ceiling so upgrades do not announce old notices. Do not notify during local quiet hours; defer rather than consume eligible events. Enforce bounded candidate batches and at most three notification attempts per ten-minute window. Sensitivity modes use the same deterministic personalization score: Important requires preferences and score ≥16; Interested requires explicit-interest match; All admits any otherwise eligible item. Negative feedback or negative-interest matches always suppress. Inactive/unsubscribed/disabled sources suppress. On macOS, a native UserNotifications handoff is only an attempt, not delivery; mark delivered only after an action callback. On Windows the final policy check, token creation, attempt reservation and synchronous WinRT handoff share one store lock (`handoff_validated`); a handoff is `attempted`, and only a validated one-use schema-7 activation token tied to the current attempt marks events delivered. Token hashes and bounded expiry stay local, restore invalidates them, and a click arriving during shutdown is refused. Windows discovery claims nothing unless authorization is `authorized` (verified install identity and protocol owner), even in quiet hours; macOS keeps its quiet-hours deferral. Do not add a provider beyond these two without an explicit product change. After an asynchronous macOS send, process the OS response independently of the scheduler's delivery cycle so waiting for a click/dismissal cannot stall future scheduler work; bound response waiting and stop handling. A macOS alert closes itself after 30 minutes, and the scheduler tracks at most 12 pending responses so an ignored alert cannot stop later deliveries. `proactive_snapshot.notification_permission` remains `unknown`; the settings surface separately invokes native authorization-status and explicit permission-request commands. Request authorization only after explicit user action. macOS status maps not-determined/denied/authorized/provisional/ephemeral, with timeout/error as unavailable; Windows has no permission prompt: status is authorized/denied/unavailable from notifier settings and install identity, and the explicit button sends one test notification (never enables notifications). Other hosts report unavailable. Click activation restores the existing window and carries stable archive identities; the main window subscribes to `proactive://notification-clicked`, falls back to snapshot pending activation if the event precedes subscription, and unlistens when unmounted.
- **Todo reminders (#189, user decisions):** per-todo and off by default (`reminder_minutes`: 0/10/30/60/1440 before a timed todo, 0/1440 before 09:00 of an untimed one). They need the calendar and proactive extensions, global notifications and OS authorization, and run only inside the scheduler loop while Rhythm is open (`proactive/reminders.rs`, no scheduler enablement needed). A reminder missed while closed is sent late only while the todo is still ahead, never after. Quiet hours and the combined three-per-ten-minutes limit (notices, seat alerts and reminders share `delivery_attempt_count`) hold a reminder back without dropping it; `Store::calendar_reminder_reserve` makes the final check and records attempt, token and `reminder_sent` latch in one transaction under the handoff's Store boundary, and a reserved reminder is never resent. Editing day, time or reminder rearms it. Clicks use one-use hashed tokens (`rhythm-win://reminder/` on Windows) that only open the calendar on the todo's day; startup, restore and disabling the calendar or proactive extension clear them. Mocked IPC and store tests do not verify native display or click.
- **Proactive data boundaries:** Keep all proactive state local; events store archive identity references while notification titles are read from archived revisions. Do not add remote notification services, title/body telemetry, external notification actions, or implicit autostart/collection. Backend-validate and bound settings/task/event inputs. Quiet hours use local wall-clock time; persisted timestamps are UTC.
- Proactive state comes from migrations 005–007 (contents in the `docs/ARCHITECTURE.md` schema table). Notification event states are pending/claimed/attempted/deferred/delivered/suppressed/failed. Reserve attempts before OS handoff; history clearing/pruning must not reset rate accounting or dedupe. Preserve the revision ceiling on upgrades. Add migration, default-off, task reconciliation, failure/retry, quiet-hours, sensitivity/negative-feedback, dedupe and action-activation tests for proactive changes.
